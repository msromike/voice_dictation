VOICE DICTATION - SPIKE NOTES

Findings from real investigation, kept for reference. Not a task list.


WHISPER (faster-whisper, large-v3, cuda)

Short clips (~140-180ms) of real captured audio can produce confident,
plausible-but-false text ("Let's go.", "Thank you.") instead of an empty
result. Pure synthetic silence or random noise of the same length does not
reproduce this -- only real mic transients did.

transcribe() latency does not scale with clip length. 10ms-2000ms clips all
took ~190-200ms after model warm-up. First call after model load pays a
one-time ~500-700ms warm-up cost, unrelated to input length.

Two concurrent transcribe() calls on the same loaded model instance do not
crash or corrupt output, but serialize -- a concurrent pair takes ~2x one
call's time, no parallel speedup.

MIN_RECORDING_SAMPLES stays at 6400 (0.4s): it already filters the exact
duration range where hallucination was observed.


CPU CORE TOPOLOGY (Windows, hybrid P/E chips)

Windows reports performance versus efficiency cores through
GetLogicalProcessorInformationEx with RelationProcessorCore. Each record
carries an EfficiencyClass byte at offset 9 of the record; higher is faster.
Walk the buffer by each record's own Size field. Verified working on an
i7-9700K: eight physical cores, all reporting class 0.

The rule that falls out needs no special cases: count physical cores per
efficiency class and request the count in the HIGHEST class as cpu_threads.
All-performance chips return everything. All-efficiency chips -- the modern
N-series Celerons are built entirely from them -- also return everything,
correctly, because they are homogeneous. Only mixed chips return a subset.

Chosen against a hard affinity mask, which would guarantee placement where a
thread count only hints at it. Reasons: the barrier argument for excluding
efficiency cores assumes CTranslate2 partitions work statically, and its
threading is compiled C++ that cannot be inspected from the venv. With
dynamic scheduling a slow core simply takes fewer chunks and excluding eight
real cores becomes a straight loss. A thread count is correct under either
model. Overturned by a hybrid machine measuring pinned against unpinned --
neither machine here is hybrid, so this cannot be settled locally.

Windows migrates threads between core types continuously while they run, so
a thread count is a hint and never a guarantee. That is a known limit of the
choice above, not an oversight.


AUDIO CORPUS AND TRANSCRIPT LOG (cannot be paired)

The FLAC corpus and transcript_log.txt cannot be joined, and no later effort
recovers it. FLAC filenames carry a microsecond timestamp; transcript lines
carry nothing at all. The counts do not reconcile in either direction: the
console writes a blank line after every transcript, FLAC files are written
for captures too short to ever be transcribed, and the log predates FLAC
capture being switched on.

Consequence for any tuning work: there is no ground truth. The usable
substitute is a pseudo-reference -- run the highest-quality configuration
over a sample, treat its output as truth, and measure every other
configuration as divergence from it.


VRAM MEASUREMENT (Windows, consumer NVIDIA)

Per-process VRAM cannot be read on Windows consumer cards. nvidia-smi
--query-compute-apps returns used_memory as [N/A] for every process under
the WDDM driver model, and no permission level changes it. Do not spend time
on it again.

What works: nvidia-smi --query-gpu=memory.used sampled before a load and at
peak, taking the delta. Whole-GPU, so anything else changing on the desktop
during the sample pollutes it.

The trap underneath: Windows lets CUDA allocations spill into system RAM
rather than failing when VRAM runs out. A model that does not fit still
runs, slowly and silently. Measured on this machine, an RTX 3070 Ti reports
8192 MiB total, and the desktop's share swings widely: roughly 6000 MiB on
one earlier reading, 1886 MiB with the app closed on 2026-10-22 (twice). So
any timing run has to record free VRAM at its start, or a spilled run gets
recorded as a slow configuration.


COMPUTE TYPES (CTranslate2 4.8.1)

Supported sets differ by device and by GPU generation. Re-derive with
ctranslate2.get_supported_compute_types(device) rather than trusting a list.
On this machine, CPU offered int8, int8_float32, int16 and float32; an RTX
3070 Ti additionally offered float16, bfloat16, int8_float16 and
int8_bfloat16.

bfloat16 requires Ampere. Pre-Ampere cards -- a 2070 and anything else in
the Turing generation -- do not have it. So a compute type measured as
fastest here cannot ship as a constant: the shipped code has to probe what
the device supports and walk an ordered preference list.


DISPLAY DPI (Windows, Tk)

A process that has not declared DPI awareness reads the system DPI as 96,
whatever the display is set to. Tk shares the trap -- winfo_fpixels('1i')
and tk scaling both report ~96 there too. No library avoids this;
awareness is a process-level declaration, so a probe must run under the
same conditions as the app or the number is fiction that looks plausible.

Windows and Tk disagree on the figure even with awareness set:
GetDpiForSystem() reports the configured setting, Tk derives its own from
reported physical screen dimensions (measured 168 vs 167.876). Reading DPI
from Tk instead of ctypes would shift every scaled dimension by a pixel or
two, and would make vdict/tray/dpi.py depend on a live Tk root.


AUDIO PLAYBACK (sounddevice/WASAPI)

sd.play() opens a new WASAPI stream per call -- that stream-open is what
causes an audible click on every play. A single persistent sd.OutputStream,
written to repeatedly, has no click.

WASAPI auto_convert (sd.WasapiSettings(auto_convert=True)) correctly
resamples a fixed-rate source (tested 192000 Hz) down to a device's native
rate (tested 48000 Hz) -- correct duration and pitch, confirmed both from a
live numpy array and from a real WAV file round-tripped through disk.

A crashed process (unhandled exception, stream never closed) does not lock
the output device -- Windows reclaims the WASAPI session on process exit,
confirmed by immediately reopening the same device from a fresh process.

An open but unfed WASAPI stream was suspected to click on the next real
write after idling. WRONG, or at least incomplete: feeding it silence
continuously (never idle) did not fix it. The artifact persists -- a brief
burst of white noise, not a clean click/pop, landing specifically right
after a tone plays. White noise (not a pop) points at a buffer underrun
(driver has nothing valid to output for an instant) rather than a waveform
discontinuity. Leading theory: the writer thread is a blocking-write push
model (Python decides when to hand off each chunk); a pull model (PortAudio
calls back for more data on its own real-time thread, same pattern already
used for microphone input) would remove the Python-scheduling dependency
entirely. Not yet implemented or confirmed.

Checked and ruled out as causes: np.empty() uninitialized memory (never
used anywhere in this codebase -- everything is np.zeros/.astype()),
dtype mismatch (every array reaching .write() confirmed float32, matching
the stream's own dtype="float32"). Confirmed real but likely too small to
be the cause: the shipped tones' fade-out never reaches exactly 0 at the
last sample (off-by-one in the fade math, ~0.05% of full scale residual) --
worth fixing whenever the WAV assets get regenerated, not the prime suspect.


TONE CLICK -- TWO INDEPENDENT CAUSES

sd.play()'s per-call stream open, above. And the waveform ending on a non-zero
sample, which the driver reproduces as a step.

The second is audible only on a high-resolution chain with well-damped
drivers; ordinary speakers mask it. A no-click result on cheap equipment is
not evidence.

A cosine fade over the final 1ms removes it. The WAV assets and the persistent
OutputStream are workarounds for that cause, not a preference.


DICTATION CAPTURE RATE

Roughly 570 clips a day on this machine, swinging between 120 and 956. That
projects to about 208,000 captures a year: tens of megabytes of database rows,
and roughly 34 GB of FLAC.

Re-derive rather than trusting these figures -- count files under
FLAC_CORPUS_DIR, or rows in captures, across a known span. The rate is one
person's habit and moves with it.

Rows are permanent at that size; audio is the only store worth rotating, and
nobody has measured how much of it voice-ID actually needs.


VOCABULARY IS THE CHEAPEST SETTING TO MAKE LIVE

initial_prompt is a per-call argument to STTEngine.transcribe(), and the
vocabulary string is read from vocabulary.txt rather than config.json. It is
not baked into the loaded model. Vocabulary is therefore the cheapest setting
to make live, not the most expensive -- it only looks expensive because it is
hoisted into a local before the daemon's loop starts.

Read while the live-vocabulary idea was written. Re-check against STTEngine.transcribe's signature
rather than trusting this line.

Reading it per dictation, measured 2026-09-30. Real 581-byte file, zero
terms (comments only): load_vocabulary median 0.13 ms, max 0.41 ms over
1000 reads. Same file plus 500 office words (4541 bytes): median 0.28 ms,
max 0.63 ms. shutil.copyfile to a .bak: median 0.5 ms either size.

:1550 keeps previous_tokens[-(max_length // 2 - 1):], max_length 448 at
:722. The 500 words encode to 1055 tokens with large-v3's tokenizer, so

WHISPERMODEL SWAP RELEASES CUDA MEMORY

Four cycles of load small/float16, transcribe, del, gc: each load +808 MiB,
each delete back to +165 MiB over baseline, loaded peak drifting 3 MiB
across the four. The 165 MiB is the CUDA context and cuBLAS workspace, paid
once per process and never growing. Reload in place is safe.


EMBEDDABLE PYTHON LOADS CUDA FROM THE TREE

python-3.12 embeddable zip, site enabled in python312._pth, pip
bootstrapped, faster-whisper plus nvidia-cublas-cu12 and nvidia-cudnn-cu12
installed into its own site-packages. With CUDA_PATH removed and every cuda
and nvidia entry stripped from PATH, ctranslate2 found the device and
transcribed on the GPU. The mechanism is stt.py's existing prepend of
site-packages/nvidia/*/bin to PATH; ctranslate2's own add_dll_directory
covers ROCm only. Only the driver comes from the machine.


MODEL LOCATION

Loading by name puts the model in the profile cache, outside the tree.
create_usb_stick.bat copies every cached snapshot as real files, so a machine
installed from the stick never downloads one.


PUNCTUATION RESTORATION

rpunct is a dead end: it hard-pins pandas==1.2.4 and torch==1.8.1, 2021
exact versions with no Python 3.12 wheels, and the source build fails
against current Cython. Unmaintained, do not retry it.
oliverguhr/fullstop-punctuation-multilang-large via the
deepmultilingualpunctuation package, CPU-only: model load ~3s once at
startup, restoration call ~88ms average. Threshold tested at 25
words/sentence, an untuned placeholder. 52 real transcript_log.txt lines
flagged only 1; HOLD mode's release-and-re-press between thoughts may
already prevent the run-ons this targets. Toggle mode has no such
discipline.


PHONETIC CODES COLLIDE ON ORDINARY WORDS

jellyfish (maintained, MIT, prebuilt wheels, Rust-backed) gives metaphone,
soundex, nysiis and match_rating_codex as pure algorithms. "Trey" and
"Tray" share a metaphone code, so the mechanism works for the motivating
case. Bare code equality is not safe: "cloud" and "clod" both collide with
"Claude", "true" with "Tray", "pity" with "PTT". A bare match silently
rewrites an everyday word to a name.

WHISPER MODEL LADDER (Mike's GPU testing, i7 9th gen + 3070 Ti)

VRAM watched live. GPU curated three: small.en / medium.en / large-v3,
one per card tier (4GB+/6GB+/8GB+), biggest-that-fits. large-v3-turbo is
a nuanced alternate, not a fourth tier. CPU by compute concept, not
measured: tiny.en / small.en / medium.en, same family, no distillation.
large-v3-turbo on CPU: its speedup prunes only the decoder (32 layers to
4); the encoder, which is what CPU struggles with, stays large-size, so it
costs about what large-v3 costs. Reopens if the workload becomes
decoder-bound, which ambient mode's long chunks would do. distil-small.en
rejected: a distillation tradeoff to explain for marginal gain. Reopens if
a CPU user reports small.en too slow. Per-tier speed on real hardware is
unverified.

MICROPHONE DEVICES (sounddevice/PortAudio/WASAPI, from the retired input-device plan)

Read from PortAudio's and sounddevice's source (github.com/PortAudio/portaudio,
github.com/spatialaudio/python-sounddevice), then confirmed
on real hardware: PDP mic, a Behringer mixer input, a webcam mic, all
exercised through vdict/daemon/portaudio_io.py.

  - Pa_Initialize's WASAPI backend does a fresh IMMDeviceEnumerator query
    every call -- reinit sees whatever is connected now, not a cached
    answer. CONFIRMED: the mixer appeared and disappeared correctly across
    enable/disable cycles. reinit latency 0.02-0.03 s over 5 runs.
  - A failed stream never says why. Sixteen WASAPI failure paths collapse
    into one generic thread-death signal; PortAudio's real-time callback
    contract forbids the slow work needed to preserve which one occurred.
    CONFIRMED: stream.active goes False on its own when the device
    disappears mid-stream, no exception, no status flag. That flag is the
    only detection signal there is.
  - A failed open or start always raises PortAudioError, whatever the
    cause, including another app holding the device in WASAPI exclusive
    mode. Traced through sounddevice's single _check() and CONFIRMED with
    a real exclusive-mode hog process.
  - Pa_Initialize/Pa_Terminate must be called from the same thread (COM
    apartment affinity; get it wrong and cleanup silently leaks). sounddevice
    auto-initializes on import, on whatever thread imports it first.
    SOURCE-ONLY, never tested: no tooling here isolates a silent leak.
  - Three devices enabled at once each resolved to the right index by
    name, no cross-matching.
  - Windows' default input does not reflect user intent: the webcam
    promoted itself to Default Device unprompted, twice. The "default
    disappears, does Windows auto-promote" test was dropped as moot once
    the design stopped reading the default at all.

CLIPBOARD ROUND-TRIP AND DELIVERY (keyboard.py, 2026-10-24)

Format round-trip through win32clipboard, EnumClipboardFormats order kept:

  MEASURED text: CF_UNICODETEXT, CF_TEXT, CF_OEMTEXT, CF_LOCALE all
  byte-identical after a save/replace/restore cycle.

  MEASURED image: CF_DIB, CF_DIBV5, DataObject, Ole Private Data and
  System.Drawing.Bitmap byte-identical. CF_BITMAP cannot be written back --
  GetClipboardData returns a GDI handle, not bytes -- but Windows
  re-synthesizes it from the restored CF_DIB and it reappears in the
  enumeration, so skipping it loses nothing.

  MEASURED rich text: HTML Format, Rich Text Format and the text formats
  byte-identical.

  MEASURED CF_HDROP: reads back as a tuple of paths, so SetClipboardData
  raises TypeError on it. Rebuilding the DROPFILES struct restores it --
  20-byte header (pFiles=20, pt 0,0, fNC=0, fWide=1), then each path UTF-16LE
  null-terminated, then one more null. Windows' own GetFileDropList read the
  restored path back correctly.

  Skip set, all GDI handles: CF_BITMAP 2, CF_METAFILEPICT 3, CF_PALETTE 9,
  CF_ENHMETAFILE 14, CF_OWNERDISPLAY 0x80, CF_DSPBITMAP 0x82,
  CF_DSPMETAFILEPICT 0x83, CF_DSPENHMETAFILE 0x8E.

History exclusion:

  MEASURED: RegisterClipboardFormat("ExcludeClipboardContentFromMonitor-
  Processing") returned 49987 here; written with four zero bytes. A control
  string written without the flag appeared in Win+V, the string written with
  it did not. Clipboard history was on
  (HKCU\Software\Microsoft\Clipboard, EnableClipboardHistory = 1).
  It matters more than it looks: the history monitor asks for the text the
  instant it is announced, which would fire the delivery receipt before any
  paste happened.

Delivery -- why there is no delay constant:

  MEASURED: announcing CF_UNICODETEXT as a null handle (delayed rendering)
  and sending Ctrl+V, Notepad asked for the text 6.0 / 6.3 / 6.5 ms later,
  3 runs of 3. WM_RENDERFORMAT arriving is proof the paste landed, so the
  restore waits on an event and not on a guess about machine speed.

  MEASURED: an earlier run of the same spike read 103.7 / 103.9 / 104.0 ms.
  That was pyautogui's default 0.1s PAUSE delaying hotkey()'s return, and
  with it the message pump -- not the paste. keyboard.py sets
  pyautogui.PAUSE = 0.

  MEASURED: the whole inject() -- snapshot, announce, paste, receipt,
  restore -- returned in 16.8 ms with an image on the clipboard, and the
  image was intact afterwards.

  _RECEIPT_TIMEOUT = 1.0s is a backstop for "nobody ever asked" (no text
  field focused, elevated window). Being wrong about it delays a restore;
  it cannot cause a wrong paste, which is exactly what a fixed delay can.

  CONFIRMED IN THE APP 2026-10-24, Mike at the keyboard: clipboard sentence
  survives a dictation, screenshot survives a dictation, dictations land
  where he is typing, and Win+V lists no dictations.

  UNVERIFIED: no target other than Notepad was timed, and the numbers above
  are from one machine. The design does not depend on either.

Clipboard owner on its own thread (keyboard.py, 2026-10-25):

  MEASURED: after _restore the hidden window owns the clipboard. With that
  window's thread not pumping, another process's EmptyClipboard took
  5003.6 / 5007.7 / 5011.2 ms -- Windows gives up on WM_DESTROYCLIPBOARD
  after 5 s -- and the owner never saw the message. a8f7255's main loop did
  not pump between captures, so after any dictation the next copy in any
  app stalled that app 5 s (5003.6 ms with a8f7255's KeyboardInjector).
  With the owner idling in MsgWaitForMultipleObjects([wake], INFINITE,
  QS_ALLINPUT) and pumping on wake, the same copy took 0.2 ms and the
  owner saw WM_DESTROYCLIPBOARD.

  MEASURED: WM_RENDERFORMAT reaches an owner waiting in
  MsgWaitForMultipleObjects([], ms, QS_ALLINPUT) -- pywin32 accepts the
  empty handle list -- from a reader on another thread of the same process
  and from another process alike, 0.7 ms each, the same as the
  PumpWaitingMessages + sleep(0.001) poll it replaces.

  MEASURED, Win32 EDIT control as target: inject() from a non-owner thread
  107 ms on the first call; 100 paste_async in a burst landed 99 in
  11.65 s; receipt wait median 0.5 ms; one paste hit the 1 s backstop and
  did not land. UNVERIFIED why: the likeliest is the EDIT's single
  OpenClipboard colliding with a clipboard listener woken by the previous
  restore, which a8f7255 would lose the same way. Shift held (injected)
  before a paste was up after it, and the paste landed.

  MEASURED: a Tk Text widget fires <<Paste>> on the fake Ctrl+V but never
  sends WM_RENDERFORMAT, so delayed-rendered text does not land in Tk. The
  app has no Tk paste target; test scripts use an EDIT control instead.

Modifiers around the fake Ctrl+V (keyboard.py, 2026-10-25, after Step 6):

  CONFIRMED IN THE APP, Mike at the keyboard: with the one-way fake Shift
  release, holding Ctrl+Shift and tapping V typed "vvvvvvvv" after the
  first paste. The fake Ctrl+V's trailing Ctrl key-up had told Windows
  Ctrl was up as well, so the following taps were bare letters.

  Built instead: the keyboard hook records physical modifier state from
  non-injected events (_track_modifier); _send_ctrl_v lifts the modifiers
  that would change Ctrl+V's meaning, presses Ctrl only if it is not held,
  sends V, and puts back what is still physically down. MEASURED, recorded
  pyautogui calls: Ctrl+Shift held -> up shiftleft, press v, down
  shiftleft; nothing held -> down ctrl, press v, up ctrl; Shift lifted
  mid-paste -> not put back. Hook ignores an injected Shift key-up and
  tracks WM_SYSKEYDOWN. Same EDIT burst on this build: 100 of 100 landed
  in 10.8 s, receipt median 0.4 ms, max 2.4 ms, clipboard text identical
  before and after.

  UNVERIFIED by script, by design: a physical key cannot be injected, so
  the hook -> set -> lift -> restore path end to end is Step 6 Test 4.

Three threads, one stdout (output.py, 2026-10-25):

  CONFIRMED IN THE APP: the output window showed
  "[NOTE] Nothing dictated yet -- nothing to paste.ready|Voice Dictation
  v1.0.0 READY" as one line, then blank lines, then a dot a second for the
  rest of the session. The pipe-reader thread and the main thread printed
