 ==============================================================================
 GOAL & MARKET VIABILITY
 ==============================================================================
 The vision: Integrate a local LLM (Ollama) to search back through a year or two
 of ambient dictation transcripts.
 
 The utility is real. The market for a private, local-only "second brain" is 
 fervent (developers, writers, privacy advocates). It will not wilt on GitHub 
 IF the installation experience remains dead simple. The graveyard of AI tools
 is filled with projects requiring users to manually install vector databases
 and configure pip environments. If this ships with the same "one-click" batch
 installer as the core app, it is a killer app.
 
 
 ==============================================================================
 THE HARDWARE REALITY & SCALABILITY
 ==============================================================================
 Running Faster-Whisper, an embedding model, and an 8B generative LLM concurrently
 demands a minimum of 12GB VRAM (or a Mac with 16GB+ unified memory). A standard 
 8GB VRAM consumer laptop will choke if forced to run all three simultaneously.
 
 SOLUTION: Adaptive Resource Modes
   - Exclusive Mode (<= 8GB VRAM): Opening the RAG search window gracefully 
     unloads Whisper and loads Ollama. The user types their query. Closing the 
     window unloads Ollama and reloads Whisper.
   - Concurrent Mode (12GB+ VRAM): Both remain loaded. The user gets instant 
     queries and can dictate their search verbally.
 
 The embedding model (e.g., nomic-embed-text) is negligible. It requires <500MB 
 memory and runs entirely on the CPU in milliseconds, leaving the GPU untouched 
 for the heavy LLM.
 
 
 ==============================================================================
 SQLITE SCHEMA & VECTORIZATION
 ==============================================================================
 SQLite remains the only database required. Using an extension like `sqlite-vec`,
 vectors are stored natively alongside the data. No external vector DB is needed.
 
 SCHEMA SPLIT
   1. Source Table (transcripts): id, timestamp, raw_text, audio_path.
   2. Vector Table (vec_transcripts): transcript_id (FK), embedding_vector.

 LOCAL CORRECTION -- THE SOURCE TABLE ALREADY EXISTS AND IS NOT CALLED THIS.
 It is captures, in userdata/dictation_history_PRIVATE.db, created by init_db
 in vdict/common/corpus_db.py, and it is wider than the four columns above
 -- it carries outcome, mode, speaker, and the foreground window title and
 process name that give retrieval its strongest context signal. Building a
 transcripts table as written would split the corpus in half with no error to
 say so. Only the vector table is new work.
 The table's governing rule, in commit 26b1d40 -- record observations, never
 derivations -- names embeddings specifically as a thing kept out of captures, which is the
 same split this section describes, reached independently.

 LOCAL CORRECTION -- SCALE, MEASURED. At the capture rate in spike-notes.txt
 under DICTATION CAPTURE RATE, two years is well under half a million vectors.
 That is small enough that scanning every one of them beats indexing: the
 class of problem vector databases exist to solve does not arise here.

 LOCAL CORRECTION -- THE EXTENSION LOADS, HALF-PROVEN. sqlite-vec needs
 sqlite3.enable_load_extension, which not every Python build enables. Verified
 present and working in this venv: Python 3.12.10, SQLite 3.49.1. NOT checked
 under the embeddable Python build that portable-folder-build-sheet.txt puts
 in the tree -- that is a different binary, and if it cannot load extensions
 this design needs a different mechanism entirely. Check it before committing
 to sqlite-vec, not after.

 BATCH PROCESSING, NOT SYNCHRONOUS
 Whisper writes raw text to the Source Table continuously and instantly. 
 Vectorization is decoupled. A background CPU thread wakes up periodically 
 (e.g., every 5 minutes), scoops up any rows missing from the Vector Table, 
 embeds them in a batch, and inserts them using the exact same ID. This guarantees 
 the dictation hot-path never blocks on vector math.
 
 
 ==============================================================================
 THE OLLAMA HANDOFF (INTERACTIVE CHAT)
 ==============================================================================
 Ollama does not query the database. The vector search is pure math executed by
 SQLite, completely independent of the generative LLM.
 
 1. SEARCH: The user asks a question. The app embeds the question into a vector,
    asks SQLite for the 5 closest transcript IDs, and JOINs them to get the 
    raw English text.
 2. PROMPT: The app wraps the retrieved transcripts and the user's question 
    into a single text prompt.
 3. CHAT: The app sends this text block to Ollama as the first message in a 
    chat session. 
 
 The user experiences a seamless, interactive back-and-forth chat. When the 
 user asks a follow-up, the app sends the chat history back to Ollama. If the 
 topic shifts, the app performs a fresh SQLite vector search and injects the 
 new transcripts into the ongoing context window.
