TONES THAT SAY WHAT HAPPENED

Today the tones are start, stop, too-short, timeout and ready. Two outcomes
are silent: a press dropped because the engine was still transcribing or
pasting (the engine drops a press whose release arrived while it was busy;
the user is not told), and a transcript that was captured but never landed

Four conditions, existing high/low/double-low tones only, no new asset, no
new slider:
  happy path              high, low
  captured not delivered  high, double-low
  nothing captured        high, high+double-low (bundled close, fires
                           where too-short/timeout already fire)
  busy                    double-low alone, no leading high -- fires the
                           moment the press is dropped, not later

the delivery outcome is known. The clipboard thread knows that outcome: a
paste receipt arrived or the backstop timed out.

B13. PUNCTUATION-RESTORATION POST-PROCESS -- UPTALK PRODUCES RUN-ONS
==============================================================================
Whisper's punctuation prediction reads rising terminal intonation (uptalk)
as "not finished" rather than a completed statement, even across genuine
pauses -- produces long run-on transcripts with little or no punctuation
for speakers with this pattern.

Spiked; measurements in spike-notes.txt, PUNCTUATION RESTORATION.

Working candidate: oliverguhr/fullstop-punctuation-multilang-large via
the deepmultilingualpunctuation package (pip install, loose version
floors, no pandas dependency -- installs clean). Its own __init__ calls
pipeline(..., grouped_entities=False), removed from current transformers
in favor of aggregation_strategy="none" -- one-line patch needed, rest of
the package's logic is untouched and correct.

Hybrid design, not blanket replacement: stripping and rebuilding every
transcript's punctuation risks losing correct punctuation Whisper already
had, and the restoration model has its own real failure modes (verified:
misplaced question marks, comma-for-period swaps on ambiguous phrasing).
Gate with pysbd (pip install pysbd, pure rule-based, no model) --
segment() the transcript, compute words-per-detected-sentence. Below
threshold, trust Whisper, skip the restoration model entirely. Above
threshold (unpunctuated run-ons collapse to one giant "sentence"), invoke
restoration as a targeted rescue.

MEASURE IT RATHER THAN WAITING. The captures table carries transcript text,
duration and outcome per capture -- run pysbd over it and compute
words-per-detected-sentence across the rows. That is the incidence figure
this entry was waiting for, and it is queryable now.

TUNING WORKFLOW, only if the shipped defaults prove insufficient: a
separate, explicit tuning session -- PTT disabled, Whisper unloaded, the
largest local Ollama model that fits loaded in its place. Ollama reads the
transcript corpus, runs it through the restoration model, evaluates the
output, and iterates -- a guided, step-by-step interaction is fine, does not
need to be fully autonomous. Human reviews the result (e.g. opens the
transformed text file) before anything is "locked in." Whatever gets
decided is written back as tuning parameters, Ollama unloads, Whisper
reloads, dictation resumes.

Human-in-the-loop review is what makes this trustworthy -- without it,
"tuned" only means "Ollama liked its own output," not "matches what was
actually said."

Two different amounts of work hiding under "write tuning parameters":
adjusting a handful of hyperparameters/thresholds (Ollama reasoning over
candidates, genuinely tractable) versus actually fine-tuning the small
model's weights (a real training loop with a loss function -- Ollama could
help produce labeled examples for that, but would not run the training
itself).

Prototype as a standalone sidecar script first, not in-app. Cheapest way
to prove the risky part (does this actually improve punctuation quality)
without touching the app's menu, process management, or model-loading code
at all. Integrating it into the app is a separate decision from building
it -- it could stay a documented external tool in the README.

B21. PHONETIC VOCABULARY CORRECTION -- HOMOPHONE SPELLING DRIFT
==============================================================================
Whisper sometimes picks the wrong spelling of a word it heard correctly --
homophone confusion, not mishearing (e.g. "Trey" instead of "Tray"). This
is a disambiguation problem: Whisper hears the right sound, picks the
wrong written form because it has no way to know which one is meant.

vocabulary.txt already exists for this, but only works at decode time via
initial_prompt -- adding a term means restarting the engine, which is
cumbersome enough that it doesn't get used in the moment a term is missed.

Spiked with jellyfish; the metaphone results and the collision list are in
spike-notes.txt, PHONETIC CODES COLLIDE ON ORDINARY WORDS. Needs a second
signal before trusting a swap (e.g. requiring the transcribed word to
already look name-like, or be otherwise unrecognized) -- not designed, real
remaining work, not solved by the spike.

Would read vocabulary.txt live, as a text post-process after every
transcription -- never touches Whisper's decode path or initial_prompt,
so adding a term is live on the next dictation, no restart. Solves the
reload-cumbersome complaint as a side effect of the approach, not a
separate fix.

Same corpus problem as B13: no real data yet on how often this ambiguity
actually occurs, or what a safe second signal should look like in
practice. MEASURE IT RATHER THAN WAITING. Query the captures table for
transcripts containing name-like tokens and check how often the wrong
spelling appears. That is the incidence figure this entry was waiting for.

LIVE VOCABULARY
==============================================================================
vocabulary.txt is read once when the engine starts, so a new term needs a
model reload before it works. Read it fresh on every dictation instead, so
a term works on the next press. Why: "adding a term means restarting the
engine, which is cumbersome enough that it doesn't get used in the moment a
term is missed" (B21). Cost MEASURED in spike-notes.txt VOCABULARY: well
under a millisecond per read.

  - Each good read copies the file to vocabulary.txt.bak. If vocabulary.txt
    is missing, restore from .bak first, keeping curated words, else reseed
    from the template; log a note either way.
  - Nice to have: warn when the vocabulary is over Whisper's prompt limit.
    faster-whisper keeps only the last 223 tokens (spike-notes.txt
    VOCABULARY); 500 words came to 1055, the first ~400 silently dropped.
    Count with the loaded model's tokenizer; one output-window note naming
    how many words at the top are ignored, only when the file changed.
    Never block or trim ourselves. Tokenizing cost per read: UNVERIFIED,
    measure first. templates/vocabulary.txt gains a line: Whisper reads
    only about the last 100 words, most important at the bottom. And its
    examples become phrases as spoken: a bare word did nothing, phrases
    took Claude from 5 of 8 to 8 of 8 (spike-notes.txt VOCABULARY).

B19. SETTINGS -- MIC TEST BUTTON WITH LEVEL METER
==============================================================================
A "Test" button next to the microphone dropdown. Click it, speak, watch a
live dB bar respond -- direct, empirical confirmation the selected device
is actually receiving signal, instead of trusting any indirect signal
(Windows default-device state, our own resolution logic, anything else).
Same convention as Discord's "Let's Check", Windows' own Sound settings,
Zoom, OBS -- click-to-test needs no explanation, everyone already knows
the pattern.

Mainly for the "semi-maven" -- someone who picked a device that opens fine
but isn't actually wired up right (routing, wrong jack, disabled channel)
and has no way to tell without dictating and seeing nothing happen.

Mechanism: on click, open a short-lived stream on whatever's currently
selected in the dropdown, read amplitude from the callback, render a bar.
A plain button handler. One deliberate click opens one stream, rather
than a stream potentially opening and closing repeatedly as someone
browses the list. portaudio_io.start_hold/stop_hold are the unwired
primitives with this shape.

If the device is busy (WASAPI exclusive mode held by another app, or by
this app's own active dictation), the probe stream fails to open --
fail quietly, no bar shown, not a crash.

==============================================================================
MIC HANDLING -- NO SYSTEM DEFAULT, RECOVERY WITHOUT A RESTART
==============================================================================
Today a missing or unopenable mic exits the engine and the app shows a
modal that quits; the next launch reads a flag file and opens Settings
without starting the engine. The dropdown offers "System Default". Design,
condensed from the retired input-device plan (in git); measurements in
spike-notes.txt MICROPHONE DEVICES.

NO SYSTEM DEFAULT, ANYWHERE. Windows' default input does not reflect user
intent (a webcam promoted itself to default, twice, on real hardware). The
dropdown lists real device names only, and audio.device is always populated
once first run completes.

DETECTION, TWO TOOLS FOR TWO MOMENTS. Is the configured device still
around: a cheap list-membership check, no stream open, used at launch and
to validate the dropdown. Did the recording attempt fail: the real open at
PTT press, handled as that attempt's own outcome.

Dropdown queries fresh every time it is pulled down, not once at
Settings-open. Plug in, pull down, device appears. That IS the hot-swap
mechanism -- no watcher. The query is reinit THEN enumerate; enumerate
alone returns stale data. tk.OptionMenu has no on-open hook; menu.py's
Help menu uses postcommand for the same job, copy that.

ONE RESPONSE TO EVERY FAILURE. PortAudio never says why a stream died, so
there is one FAIL handler for all three moments: at launch (named device
absent), at PTT press (absent, held exclusively elsewhere, or the open
throws), and never for mid-recording (device pulled while recording:
truncated audio, accept what was captured, log a quiet note).

RECOVERY, THE ONLY PATH: fail -> modal -> Settings -> pick from the
dropdown -> Save -> attempt the real open immediately, right there in
Settings. Opens clean: beep, dictate. Fails again: stay in Settings, say so
inline ("that device exists but can't be opened -- maybe another app has
it exclusively -- pick another"). The engine never exits on a mic fault;
it loads fully regardless of mic state and the ready beep just does not
fire until one works. The flag file spanning two launches goes.

THIS APP NEVER REQUESTS EXCLUSIVE MODE: no latency to gain against
Whisper's own time, and it would lock every other app out of the mic.

Settings and the recovery modal both get a button that opens Windows'
Sound Recording tab: rundll32.exe shell32.dll,Control_RunDLL mmsys.cpl,,1.

ONE MODULE OWNS ALL sounddevice CONTACT. vdict/daemon/portaudio_io.py has
the primitives, built and unwired (enumerate_inputs, resolve_by_name,
reinit, open_probe, start_hold, stop_hold); nothing imports it. audio.py's
_find_device_id resolves by substring and goes away in favor of
resolve_by_name, exact match. Whatever the build does not call is dead and
gets deleted then.

B24. AMBIENT LISTEN MODE -- CONTINUOUS TRANSCRIPTION, OPTIONAL SPEAKER ATTRIBUTION
==============================================================================
A second, selectable mode alongside today's PTT dictation -- mutually
exclusive, not simultaneous, not a separate app. Same engine
(STTEngine, model selection, tray shell), different capture loop and
different output target. Phases: capture and transcribe, then attribution,
then search (B28).

MOTIVATION
Passive background transcription for meeting-heavy roles -- a
searchable, timestamped record of a day's conversations without
active note-taking. Validated against a real use case (management
role, back-to-back meetings), and market-precedented (Otter.ai,
Fireflies.ai, Read.ai already succeed doing exactly this). Legal/
consent questions are the user's to navigate, not this tool's to
gate -- same posture as any dual-use recording capability.

PIPELINE
  - Continuous capture, no PTT trigger. Async double-buffer: capture
    never blocks on transcription -- next chunk records while the
    current one transcribes.
  - 5-minute chunks flushed to disk as timestamped FLAC files, not
    passed in-memory. Decouples capture cadence from transcription
    cadence. FLAC, not raw WAV -- lossless, encode cost is sub-second
    even at max compression on modern hardware, and Whisper never reads
    the file directly either way (already decodes to a raw sample array
    before transcribing), so there's no compatibility cost to writing
    compressed from the start. No WAV anywhere in this path.
  - Disk-based FIFO queue, oldest-first, plain directory scan -- no
    scheduler package needed (one producer, one consumer, one
    machine). Backlog bounded by disk space, not memory; self-
    revealing if it falls behind (stale timestamps visible to user).
    Real per-chunk throughput unverified -- confirm on real hardware
    when built.
  - No overlap, no dedup between chunks. A sentence split across two
    timestamped entries is acceptable -- cut doesn't mean lost.

SILENCE HANDLING
  - Whole-chunk pre-check (RMS/amplitude heuristic) before calling
    Whisper at all -- near-total silence skips transcription entirely,
    logs "[silence, skipped]" instead of risking hallucinated filler
    text (the well-known "thank you"-on-silence phenomenon).
  - vad_filter=True stays on for this mode too -- different
    granularity than the pre-check (trims partial silence within a
    chunk that has real speech), not redundant with it.

OUTPUT
Timestamped disk log only. No cursor injection -- that's PTT mode's
delivery mechanism, not this one's. First useful view: what got recorded
today, as text, in a text editor.

ATTRIBUTION -- THREE INCREMENTAL TIERS, each independently shippable
  Tier 1: Pure transcription. No speaker awareness at all.
  Tier 2: Diarization without attribution. Speaker A/B/? labels,
    always on by default -- privacy-safer than tier 1 (structure
    without PII), no enrollment system, no added risk.
  Tier 3: Diarization with attribution. Persistent voice-ID via
    embeddings, each distinct voice assigned a permanent GUID.
    Separate GUID-to-name lookup table (empty until user labels it) --
    naming is just filling in one row, never touches the embedding-
    matching layer. UI: present a snippet of an unresolved "Speaker ?"
    voice, prompt for a typed name. Same person surfacing as two GUIDs
    (different mic, sick voice, etc.) self-corrects for free -- typing
    the same name for both produces an identical-looking transcript
    to an actual merge, no explicit merge operation needed.
  Then lookup by person and day: what Bob said, on what date, with the
    text. A query on the captures table's speaker, start_time and text
    columns once tier three fills the speaker column.

ACCEPTED LIMITATIONS, NOT BUGS
  - No retroactive relabeling. Naming a "Speaker ?" only applies going
    forward; past log entries using that placeholder stay as-is.
  - False merges (two different real people collapsing into one GUID)
    have no correction lever, unlike false splits (which self-correct
    via re-naming) -- mitigated by biasing the similarity threshold
    conservative (favor staying unresolved over confidently guessing
    wrong). For voices that are genuinely hard to tell apart, the
    realistic steady-state is mostly-correct with a persistent
    "Speaker ?" residue, not silent misattribution -- self-explaining
    to the user, accepted as-is, not designed around further.

NOT DESIGNED IN DETAIL YET
Exact chunk duration and silence threshold tuning, which diarization/
embedding library, the naming-snippet UI itself, Settings integration
for the mode toggle.

SPIKE IDEA: play YouTube (or any audio source) out loud and let ambient
mode's own mic capture it, instead of downloading audio. No ToS question,
and mic-captured audio is the better test anyway -- real room acoustics
and speaker response baked in. A single video only tests Tier 2 (telling
concurrent speakers apart within one file); validating Tier 3's actual
hard problem (same person recognized across separate sessions) needs the
same identifiable voice across multiple separate sessions -- play a
different video from the same channel each session. Two-step test:
segmented clips as-is (per-sample consistency), then grouped into
~5-minute assemblies with realistic silence gaps (production-chunk
accuracy). Don't merge the whole corpus into one file for either step.

DEV-ONLY CAPTURE FLAG. A second entry in dev-flags.toml -- an absent file
means every flag is off. It gates whether ambient mode's processed chunks
are retained instead of deleted, which is what feeds real multi-speaker
corpora through the actual ambient pipeline and keeps the output for
validation. Production default is always delete. NOT a bare code constant
and not a config field: a constant ships with the source, and a folder
handed to someone on a stick would record them. dev-flags.toml is
gitignored and never on the copy list.

==============================================================================
B30. FLAC RETENTION -- A SIZE BUDGET THE USER PICKS
==============================================================================
Anyone who turns audio capture on prunes by hand every week or two, or lets
the folder grow until they notice it. Nothing in the app manages it.
Measured rate in spike-notes.txt DICTATION CAPTURE RATE: tens of gigabytes
a year for one heavy user.

THE CONTROL
A Settings dropdown: roughly 1 GB, 5 GB, 10 GB, unlimited. A number the user
already understands, not a retention window they have to convert into one.

THE MECHANISM IS AGE, NOT SIZE
Deletion goes by age. write_timestamped_flac in vdict/common/audio_io.py files
clips under YYYY/MM/DD, so dropping a month is one directory removal, not a
query. Oldest directories go until the folder is under budget. Rows are never
touched: they are small, permanent, and every query runs off them alone.

DELETION IS THE PART THAT GOES WRONG
Nobody has measured how much audio voice-ID actually needs, and you can
delete later but not undelete.

Same Settings area as the corpus opt-in item, which is the switch this prunes
behind. Ambient mode needs the identical control on a far larger volume --
build one, not two.

==============================================================================
B27. SELECTION TRANSFORM
==============================================================================
Speak at selected text and have it replaced. Mechanically cheap: copying does
not deselect, so Ctrl+C then Ctrl+V lands the replacement on the live
selection with no cursor bookkeeping, and the app already owns both halves.

Three hazards to design against. The selection can die while the user is
still talking, so the copy happens at press and not at release. The paste
replaces whatever is selected AT PASTE TIME, which may not be what was
copied. An empty selection silently transforms a stale clipboard, so clear it
first and check something arrived.

Windows UI Automation reads and replaces text without the clipboard, which
avoids all three and keeps formatting -- but coverage across applications is
inconsistent, so clipboard stays as the fallback.

This edits documents rather than appending to them. A bug here destroys work
rather than leaving a stray word.

B28. SEARCH THE CORPUS BY MEANING
==============================================================================
Ask a question in English and get back what you actually said about it,
months ago, from a corpus that never left the machine. Embeddings in SQLite
via the sqlite-vec extension, retrieval by pure vector math, a local LLM
(Ollama) reading the retrieved rows and answering.

Design lives in vector-analysis-investigation.txt. Read its provenance
header first -- it is outside work and nothing in it was measured here.

WHY IT IS NOT QUEUED. It adds an embedding model and a generative model to
a dictation tool, which changes what the product is. It also assumes a
corpus of ambient transcripts, and ambient mode is B24, unbuilt.

WHAT MAKES IT POSSIBLE LATER IS ALREADY BUILT. Text tied to a timestamp tied
to an audio file is the whole substrate, and that is the captures table, see
init_db in vdict/common/corpus_db.py. Embeddings are derived from the text and
can be computed over the entire history at any time, so the embedding model
is not chosen now and choosing it early is the worse decision -- vectors
from two models do not share a space, so any model change discards every
vector ever stored.

THE HARD PART IS NOT THE DATABASE. Captures are utterances, not documents
(median 7.3s, see spike-notes.txt, CAPTURE LENGTH), and one embedded
seven-second fragment carries almost no meaning on its own. Deciding what a
retrievable unit is -- grouping consecutive captures, embedding windows
rather than single rows -- is the feature. The storage and search half is
arithmetic at this scale.

FIRST CONCRETE STEP, whenever it is pulled: prove sqlite-vec loads, then
backfill vectors over whatever rows have accumulated. Both run without
touching the engine, and the backfill improves the longer it waits.


==============================================================================
CODE SEAMS -- WHERE ONE FACT LIVES IN SEVERAL FILES
==============================================================================
From the retired hand-rolled ledger's modularity pass (in git). Not bugs;
each is a string or a schema that several modules must agree on with
nothing enforcing it. Worth drawing a boundary around only when touching
that code anyway.
  1. Output categories: the table in common/output.py and the literal
     special cases in console.py's drain ("loading", "ready", "transcript",
     "rec", "done"). One owner for the vocabulary and the rendering rule.
  2. ptt.button names: keyboard.py BUTTON_MAP, session.py format_bind,
     ptt_capture.py's display names, config.py's untyped field. One module
     owns names, display names and validation; a bad value heals through
     load_settings instead of crashing the engine.
  3. Hardware probing: WASAPI enumeration in audio.py, settings.py and
     portaudio_io.py; the CUDA PATH edit in stt.py and settings.py. One
     device module, one PATH edit at import.
  4. Corpus schema: CREATE in corpus_db.py, CaptureRow and the INSERT in
     vdict_daemon.py. Move the row next to the table.
  5. Tones: a self-contained block inside vdict_daemon.py that wants to be
     daemon/tones.py.
  6. Vocabulary file handling spread over config.py, app.py and menu.py.
     One owner, split from config.
  7. Engine code never touches a widget; every engine-to-tray hop goes
     through the output queue. Documented by comment only.
