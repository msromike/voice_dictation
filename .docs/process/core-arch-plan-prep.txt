P4. SPLIT vdict_tray.py INTO vdict/tray/ -- NEEDS ITS OWN PLAN + BUILD SHEET
==============================================================================
D7's subject. One file absorbing everything (current size and the full
state map live in vdict-encap-plan.txt's MEASURED section) -- app
bootstrap, tray icon/menu, the console/output window, the Settings dialog,
the emerging Save/orchestrator logic, hotkey capture UI, fault-modal
dispatch, error logging, window geometry persistence, and more.

WHY THIS IS SAFE TO DO NOW, NOT DEFERRED TO AFTER CORE-ARCH
Splitting is only risky if the pieces have to guess at core-arch's exact
final shape. They don't, if each piece presents a clean API instead of
just relocating code -- core-arch's own restructuring then becomes one
more caller of interfaces that already exist, the same relationship Tray
already has with STTEngine/AudioCapture/PTTListener. Encapsulation is the
load-bearing idea: hide how a piece works behind what it presents, and
internal reorganization on either side -- this split, or core-arch's
later changes -- stops depending on the other.

TARGET STRUCTURE
Pieces move into the existing vdict/tray/ package (currently just
hotkey.py), not a new location. Rough count of genuinely distinct
concerns currently tangled into one file: app bootstrap, tray icon/menu,
console/output window, Settings dialog (already split into per-section
methods), the Save/orchestrator logic (Tray itself), hotkey capture UI
(_PTTCapture -- distinct from vdict/tray/hotkey.py's low-level Win32
wrapper), fault-modal dispatch, error logging, window geometry
persistence, misc UI (About box, Save-As-log, help menu sync). Already
past ten before splitting anything further.

WHAT DOESN'T BECOME ITS OWN FILE
Subprocess management (start_vdict, _stop_daemon, restart_daemon,
_run_shutdown_steps) disappears entirely once there's no separate daemon
process to manage -- not relocated, gone. Vocabulary reseed and config
load/heal logic are already migrating into vdict/common/config.py per
CONFIG PERSISTENCE and LIVE-READ SETTINGS -- not tray-side concerns
either.

SCALE WARNING -- WHY THIS ISN'T ONE MORE TERSE PREP BULLET
P1-P3 (drained) were each one function or one mechanical move. This is splitting
1520 lines into roughly a dozen files -- same sound principle as those,
much more surface area for something subtle to go wrong: shared state two
new modules both secretly need, an import cycle, something that looked
self-contained and wasn't. Needs its own plan and build sheet before real
coding starts, same discipline core-arch and input-device-plan.txt both
already got, not folded into a single prep-item paragraph.

WINDOW GEOMETRY PERSISTENCE -- DESIGN DECISION 2026-08-02
Registry, not one-off per-window save calls: each window registers once
(e.g. track(window, config_field)); a single save_all(config) call asks
the registry for every currently-open tracked window's live position and
writes all of them in one shot. Called at process exit only.

No crash-safety requirement -- losing an unsaved drag to a crash is
accepted, so no per-move or per-settle disk write is needed, only an
in-memory cache of the live geometry (same idea as today's
_remember_geometry) plus one flush at exit.

This is what closes D20's bug class by construction, not by enumeration:
a new window is covered by one track() call, not a new shutdown-step edit
someone has to remember. Build against today's load/save-on-exit pattern;
the API doesn't change shape once core-arch's shared live Config object
lands, only what save_all(config) is handed.
