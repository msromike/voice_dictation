PASS 1 -- THE FRAMEWORK
Atomic: one event loop owns the main thread. SEAMS builds Qt alongside Tk
with nothing shared, so the two loops never meet. Parity is checked against
qt-parity-inventory.txt, which holds every menu item, binding, tray action,
dialog and menu-free behaviour a user can reach -- push-to-talk included.
Not the implementation: reproducing a Tk accident is not parity.
  - The app runs under QApplication. Every window rebuilt.
  - The tray icon is Qt. pystray goes, and its background thread with it.
  - No widget sets its own appearance. One QSS file holds all of it, carrying
    today's colours. Themes come later; the mechanism cannot.
  - Worker output reaches the console through signals. output_queue, the
    100ms tick and console.drain() stop existing, and something else reports
    the daemon's exit -- the tick does that too today.
  - console.py is renamed to the output window, code side included. README and
    the View menu already say Output Window; "console" reads as a terminal and
    has already produced a wrong inference about how it works.
  - pynput leaves the tray. Both Settings captures become an event filter on
    the dialog reading ordinary Qt events -- no global hooks, no
    root.after(0, ...) marshalling. UX unchanged: the armed button greys via
    the stylesheet, left-click ends the capture, Escape still means two
    things. pynput survives in the daemon only.
  - Single instance is enforced through Qt. win32event.CreateMutex goes.
  - geometry.py and dpi.py are deleted. Window state persists through a
    QSettings INI file in userdata. See SETTLED.
  - RegisterHotKey on the main thread; WM_HOTKEY arrives through a native
    event filter on the application. hotkey.py loses its thread and pump.
  - Modals are Qt, except the two crash-path dialogs. See SETTLED.
  - Clipboard reads and writes are Qt. pyperclip goes, and so do the console's
    two Tk clipboard paths.
  - Config keeps its current pydantic shape, held by one QObject with a
    single changed signal. See SETTLED.
  - Every non-Qt survivor carries the fact that keeps it.
  - First step of the build sheet: derive the dropped-dependency set from
    requirements.txt and from every import in the tree, reading INDENTED
    import lines, never file tops. sounddevice, pystray, pyperclip and
    win32event are a starting point, not the set.

AFTER PASS 1 -- INDEPENDENT, IN ANY ORDER

AUDIO. Separable because it owns no windows. Must land before input-device
work, or portaudio_io.py gets wired and a deletion becomes a rework.
  - Capture and playback run through Qt. sounddevice goes.
  - Capture is file-centric: QAudioSource Int16 frames stream into a
    soundfile FLAC as they arrive, and Whisper reads the path. One capture
    path for PTT and ambient. soundfile stays; it is the encoder.
  - Tones are numpy into a QAudioSink, generated with a 1ms cosine tail.
    Deleted, not ported: vdict/sounds' three wav files, _load_tone, the wave
    import, _resolve_output_device, the persistent OutputStream, _tone_queue,
    _current_tone, _current_tone_pos and _output_callback.
  - Pitch is C5 and G5 at A443, a perfect fifth -- 526.82Hz and 789.34Hz. The
    shipped WAVs measure A440; generating the tones is what turns pitch into a
    number rather than an asset. A preference, not a constraint: the interval
    carries the meaning, so do not "correct" it back to A440.
  - Device changes arrive as signals rather than being polled for. A mic
    unplugged mid-capture stops the source with IOError and Qt never
    resumes it: that capture ends with an error outcome, and the source is
    rebuilt when audioInputsChanged shows the configured device back.
    stateChanged is unconnectable from PySide6 6.11.1; poll state() and
    error(). MEASURED in spike-notes.txt.
  - Settings has a mic test with a live level meter. Reference
    implementation is Qt's own examples/multimedia/audiosource. Why and
    how: B19 under POLISH.

B3. TONE VOLUME CONTROL -- REFINEMENT
==============================================================================
THE PROBLEM
Tone volume is two module constants, TONE_VOLUME_HIGH and TONE_VOLUME_LOW in
vdict_daemon.py. Ear-tuned on one machine, imposed on every user.

WHY NOT JUST USE THE WINDOWS VOLUME MIXER
The daemon is pythonw.exe, the tray is ALSO pythonw.exe, and the venv
redirector stub means each appears TWICE. The mixer shows up to four
identical "pythonw" entries with no way to tell them apart.
REOPENED BY THE PORT: one process and the embeddable interpreter (no venv
stub) is ONE mixer entry. Whether the mixer then suffices is a question for
the sheet, not settled here.

THE WORK
  - The Config model gains two volumes, 0-100, defaults matching the two
    constants so existing behaviour is unchanged.
  - Settings gains two sliders, start tone and stop tone. Zero is off, which
    is how someone silences one and keeps the other.
  - The value multiplies into the generated tone, read at the point of use
    through the shared live Config holder. A standalone per-call
    config.json re-read is NOT a substitute: save_settings() writes
    non-atomically (truncate then write), so a read landing mid-write raises.
  - The two defaults are not equal because the high tone reads louder than the
    low at equal amplitude. Do not normalise them. Pitch itself belongs to
    qt-port-plan.txt's AUDIO deliverable, not to this item.
  - The 1ms cosine tail is not this item's to decide or to drop -- see
    spike-notes.txt TONE CLICK.
  - too_short and timeout both play the low double at the low volume, same as
    stop. They follow the stop slider. No third control.

  QUESTION: ready plays the low double at the low volume too, but it fires
  once at launch rather than inside a dictation cycle. Does it follow the
  stop slider, or is silencing the startup chime its own control?

B8. WINDOW CONTROLS -- MINIMIZE, X AND EXIT SHOULD DIFFER -- REFINEMENT
==============================================================================
The confirm dialog needs icon=WARNING.

THE PROBLEM
X kills the app, and with it dictation. Under one process and ambient mode,
closing the window must never stop recording. The confirm dialog exists to guard a
behavior users do not expect; conventional actions do not need one.

ALREADY TRIED AND REJECTED
X -> tray while minimize -> tray. That was the pre-release behavior: two
controls, one outcome. Returning to it needs a reason the two controls should
do the same thing.

THE ARRANGEMENT
  Minimize -> taskbar, native behavior. Not configurable.
  X        -> hide to tray. Default.
           -> confirm dialog (icon=WARNING), then exit, when
              ui.close_button_exits is on.
  Exit     -> tray menu and File > Exit, both already exist, no dialog --
              deliberate, conventional actions, nothing to guard.

  - The Config model gains ui.close_button_exits, default False.
  - Settings gains "Close button exits the app". The label names X, not the
    minimize button.
Re-verify the hotkey raises a taskbar-minimized output window.

SIDE EFFECT, WANTED
An open output window means a taskbar button exists, which answers "I lost the
tray icon". The app only disappears when the user asks it to.
QT: closeEvent on the output window does the arrangement above. The
confirm dialog, icon warning, fires only on the X path when
ui.close_button_exits is on; tray Exit and File > Exit never confirm.

B22. SETTINGS MODEL DROPDOWN -- DEVICE-AWARE + SHOW-ALL ESCAPE HATCH -- NEW FEATURE
==============================================================================
Two related ways B17's static curated list falls short, both requiring
the dropdown to react rather than just list:

DEVICE-AWARE FILTERING
CPU and GPU users want different curated sets, not one list serving
both. The dropdown's model options should follow whichever compute
device is currently selected in the same dialog.

THE AXIS IS IN QUESTION. Both lists sort by hardware budget. The user is
choosing how good and how fast their English is; VRAM is a filter, not a
choice. Turbo fell into the show-all hatch because it fits no budget tier,
which is the taxonomy failing rather than the model. Reconsider the axis
before rebuilding the dropdown -- a language picker may replace the model
picker for most users.

MODEL LISTS: the measured GPU ladder and the CPU reasoning are in
spike-notes.txt, WHISPER MODEL LADDER. Inference tuning re-measures both.

ENGLISH-ONLY VARIANTS: every size above uses its .en variant, not the
multilingual one -- app isn't localized, Whisper's
.en models are smaller, faster, AND slightly more accurate on English
audio than their multilingual counterpart of the same size, no tradeoff
either direction. large-v3 is the one forced exception: OpenAI only
ever trained .en variants for tiny/base/small/medium -- large-tier
models (including large-v3-turbo, in the show-all list) are
multilingual-only, no .en version exists to switch to.

CUDA detection already exists -- settings._has_cuda() (Compute
Device section) already probes and disables the GPU option when no CUDA
device is found. Reuse it, don't reinvent the probe.

SHOW-ALL ESCAPE HATCH
Neither curated set exposes turbo variants outside their bucket, older
large versions, or the rest of the distil-* family. An "advanced" or
"show all" option surfaces the full available_models() list for anyone
who goes looking.

Both likely share one population function, called with a different
filter depending on device-vs-show-all. Not designed in detail. No gate,
no P-item.

==============================================================================
B19. SETTINGS -- MIC TEST BUTTON WITH LEVEL METER -- NEW FEATURE
==============================================================================
A "Test" button next to the microphone dropdown. Click it, speak, watch a
live dB bar respond -- direct, empirical confirmation the selected device
is actually receiving signal, instead of trusting any indirect signal
(Windows default-device state, our own resolution logic, anything else).
Same convention as Discord's "Let's Check", Windows' own Sound settings,
Zoom, OBS -- click-to-test needs no explanation, everyone already knows
the pattern.

Mainly for the "semi-maven" -- someone who picked a device that opens fine
but isn't actually wired up right (routing, wrong jack, disabled channel)
and has no way to tell without dictating and seeing nothing happen.

Mechanism: on click, open a short-lived stream on whatever's currently
selected in the dropdown, read amplitude from the callback, render a bar.
A plain button handler. One deliberate click
opens one stream, rather than a stream potentially opening and closing
repeatedly as someone browses the list.

If the device is busy (WASAPI exclusive mode held by another app, or by
this app's own active dictation), the probe stream fails to open --
fail quietly, no bar shown, not a crash.

B31. FIRST RUN -- ONE WELCOME DIALOG -- NEW FEATURE
==============================================================================
Today first run opens Settings half a second after launch and explains
nothing; dictation has already started on defaults. A new user copying the
folder alone has no one to tell them what to press.

ONE dialog, not a sequence of message boxes, then Settings opens once:
  - The microphone is required -- the one hard requirement; everything else

  - How to dictate: hold the PTT trigger, middle mouse button by default.
  - The output window hotkey is unset by default; hiding the window leaves
    only the tray icon to get it back, so nudge to bind one.
  - Compute device and model have sensible defaults; Settings changes them.
  - Minor settings (beeps and the like) -- a sentence at most.

Gated on ui.first_run, independent of audio.device, so first run is
re-tested by flipping one flag. It checks whether a device is configured,
the same check the mic fault path uses, but never reuses that fault modal:
a first-time user is not told "can't find your device" for a choice they
never made. Copy and dialog structure are the build sheet's.

EVIDENCE
==============================================================================
READ FROM THIS TREE  (grouped by the surface being rebuilt. A new fact files
into a group; cross-cutting is for facts no single surface owns.)

OUTPUT WINDOW
  - console.py zoom is hand-built: set_font_size, zoom_step, _zoom_wheel and
    the key bindings in Console.__init__. Re-derive their number from the
    bind() calls, never from a figure written here
  - THREE things write to the text widget, not one. drain() off the queue on
    the 100ms tick; _write_error, installed through install_screen and called
    synchronously by error_log from whatever thread raised, bypassing the
    queue entirely; and _animate_dots on its own 1000ms root.after loop, a
    second timer nothing else records. DELIVERABLES' console bullet names
    only the first. Replace the queue alone and the on-screen half of error
    reporting stops appearing -- silently, because the disk write still
    succeeds
  - worker output: module-level queue, 100ms Tk timer drains it.
    console.drain() is the tray's most complex function
  - the console text widget is permanently DISABLED; every write flips it to
    NORMAL and back. inactiveselectbackground exists only because a disabled
    widget never takes focus, so the inactive colour is the only selection that
    ever draws
  - console.drain decides a toast by reading root.state() != 'normal'

SETTINGS
  - settings.py's tk.OptionMenus are mic, PTT mode, model size and compute
    device. None has an on-open hook. The compute-device one reaches into
    ["menu"] to disable a single entry
  - settings.py opens with withdraw, -topmost on, update_idletasks, screen
    measurement, deiconify, update_idletasks, -topmost off, focus_force. All of
    it prevents a position flash
  - settings.py guards against stacked windows with a module global,
    winfo_exists and a caught TclError
  - two unrelated key-capture paths. hotkey_capture binds <KeyPress> on the
    button; ptt_capture runs global pynput hooks because it disables the button
    first, and a disabled widget receives no events
  - ptt_capture marshals every pynput callback back to the Tk thread with
    root.after(0, ...). pynput's listener runs on its own thread
  - Escape means cancel-capture or close-dialog depending on focus. The capture
    handler returns "break" so the dialog never sees it

MENU
  - menu.py: tk accelerator= is display text only, bound separately. The Help
    menu refreshes via tk.Menu postcommand
  - menu mnemonics are underline= character indices, and accelerator= is
    separate from the binding that implements it, so a label can disagree with
    its key
  - the live instance of that: Control-Key-equal zooms in and no menu shows
    it, so Ctrl+= works and is undiscoverable. Ctrl+MouseWheel and the
    right-click Copy menu are reachable with no menu entry at all

TRAY AND APP
  - app._tick does two jobs on that same timer, not one -- console.drain()
    and daemon_proc.poll(), which reports the daemon's exit once
  - app.py raises the window via
    win32gui.SetForegroundWindow(int(window.wm_frame(), 0)), and detects
    minimize via <Unmap> plus state()=='iconic'
  - icon.py picks an .ico frame via GetSystemMetrics(SM_CXSMICON) plus PIL
  - pystray runs its own background thread
  - "Show Output" carries pystray's default=True, and that is what makes a
    click on the tray icon raise the window. Nothing else records that
    behaviour; QSystemTrayIcon expresses it as an activation reason instead

MODALS AND CRASH PATH
  - faults.py builds modality from Toplevel + transient + grab_set
  - mic-fault recovery spans TWO launches. Close writes MIC_FAULT_FLAG_PATH
    and force-quits; the next launch reads the flag, logs a note, opens
    Settings and deliberately does not start the daemon. Rebuild the modal
    from the dialog alone and the resume half is lost with no symptom
  - app.py assigns report_callback_exception -- Tk routes every exception
    raised inside a callback there. It reports through a native MessageBoxW,
    not a Tk modal, because Tk may be what broke
  - a Tk modal runs a nested event loop; hotkey_capture unbinds before opening
    one. Qt dialogs do the same, so this hazard survives the port

WINDOW STATE AND DPI
  - geometry.py: Tk persists no window state, and it parses the geometry
    string with a regex. Windows keeps its own restore rect --
    update_idletasks() between geometry() and state("zoomed")
  - dpi.py: Tk exposes no scaling. Inverse trap -- Tk already scales point
    sizes, so fonts must NOT go through scale()
  - dpi.py's scale() wraps every pixel dimension in settings.py and faults.py.
    Deleting dpi.py touches all of them

ENTRY POINT
  - vdict_tray.py enforces single instance with win32event.CreateMutex and
    an ERROR_ALREADY_EXISTS check
  - vdict_tray.py builds a throwaway Tk root and messagebox for the
    already-running path, separate from app's

AUDIO
  - the daemon holds ONE sd.OutputStream open for the whole process life and
    queues tones into its callback, which writes silence when the queue is
    empty. The persistence is the point: closing and reopening puts a click
    on the first tones. That architecture is a workaround, not a preference
  - portaudio_io.py is built but unwired -- vulture flags every function

CROSS-CUTTING
  - appearance is set per widget in console.py (bg, fg, selectbackground,
    inactiveselectbackground, font) and in settings.py (the banner font, the
    version label's fg and font). No central definition
  - a symbol grep cannot see Tk's string-shaped API: the sequences passed to
    bind(), "break" returned to stop propagation, text indices "1.0" and END,
    the state() values normal/iconic/zoomed, "WM_DELETE_WINDOW", and widget
    state strings. Re-derive by reading the tray modules, never by grepping
    tkinter's names
  - three clipboards, not one: console.copy fires the <<Copy>> virtual event,
    console.copy_all uses root.clipboard_clear/clipboard_append, and
    daemon/keyboard.py uses pyperclip
  - the dead-widget test is tk.TclError plus winfo_exists, in console.copy and
    settings.open_settings
  - layout is pack() throughout. No grid, no place
  - deferred imports hide from a leading-import grep. Re-derive by searching
    for import lines that are INDENTED, never by reading the tops of files.
    That search returns: pyperclip and pyautogui in daemon/keyboard.py,
    huggingface_hub in stt.py, ctranslate2 AND sounddevice in settings.py,
    pynput in tray/ptt_capture.py, and tkinter itself twice -- ttk inside

    moves, so a dependency sweep that reads only file tops reports them gone

  - three deliberate decisions the rebuild must carry, none of them in a code
    comment today. They become comments when the rebuilt code is written:
      "Loading model" is left unterminated on purpose -- the console appends

  - the tray reaches into the daemon. tray/ptt_capture.py imports BUTTON_MAP

    daemon's PTTListener. A Qt capture emitting a different string breaks

    this port's scope; it is the most user-reachable behaviour in the app
  - session.py, const.py and transcript.py contain no Tk mechanisms

MEASURED  (one session, one machine, default input 'Microphone (PDP Audio
Device)'. Re-run against a different device before trusting any of it.)
  - press-to-first-sample, five trials each, same device same session:
    QAudioSource 13-17ms, sounddevice 40-52ms after a 157ms first call that
    is PortAudio cold init. Qt is faster and pays no cold penalty.
  - a beep through QAudioSink does not block capture. 121 reads across 1.2s,
    largest gap 11.9ms which is the read cadence itself. No error either side.
  - QCoreApplication is enough. No GUI application object is needed to
    capture or play.
  - the default input accepts 16kHz mono Int16 directly, isFormatSupported
    true, so nothing resamples.
  - QAudioDevice.id() is a Windows MMDevice endpoint id, shaped
    {0.0.1.00000000}.{guid}. Whether it survives a replug is still open.
  - tones need a cosine fade over the final 1ms or they click. A QAudioSink
    built and destroyed per tone is clean, so no persistent stream.

==============================================================================
DESIGN
==============================================================================
Four things hold open work, and they close in order. SCRATCHPAD is discovery
not yet run -- it drains first. JUDGMENT waits on nobody and closes next,
because settling it may collapse items below. ASSUMED is a fact we need and
lack; each closes by spike or by an explicit decision to build without it.
BLOCKED waits on a named ASSUMED item and cannot close before it. The plan is
done when all four are empty -- not when the scratchpad is.

JUDGMENT  (both moved from core-arch-plan.txt, where they sat as blockers)
  - The log signal's payload. One event has to carry both a human sentence
    and a traceback, and each destination -- the output window, the error
    log -- decides whether to render it. Today log() and error_log() are
    separate calls, and error_log's screen flag splits its call sites two
    ways; re-derive by grepping error_log( for screen=. That flag is a
    per-call-site convention, so the capability belongs in the signal.
  - A mic change saved in Settings while a capture is running. The config
    holder's changed signal reaches audio mid-capture, and replacing the
    source out from under it is a different failure from a bad transcribe().
    Nearest measured case: spike-notes.txt UNPLUG MID-STREAM, where the
    source stops with IOError and the app ends that capture as an error.

SETTLED
  - All in on Qt, not a GUI-only port. Beat: moving only widgets, which leaves
    two device vocabularies to map between. Both overturn conditions have
    been tested and neither held -- see MEASURED.
  - Audio moves to Qt and can be its own sheet. All three gates cleared:
    latency, QCoreApplication, and the tone click. Beat: keeping sounddevice
    because the beeps worked -- they worked through forty lines of machinery
    that a 1ms fade makes unnecessary.
  - pynput stays in the daemon. PTT must fire while the app is unfocused with
    the cursor anywhere, which no widget event can do. Not the button naming --
    Qt names XButton1/XButton2. Beat: hand-rolled SetWindowsHookEx. Reopens if
    Qt gains a way to receive input while unfocused with the cursor anywhere.
  - pynput leaves Settings. Both captures become ordinary Qt events, read by an
    event filter on the dialog. Global hooks were only ever needed because
    ptt_capture disables the button, and a disabled widget receives no events.
  - the capture UX is unchanged -- the button greys while armed, the captured
    key appears on its face. Greyed is a stylesheet state, not a disabled
    widget, or it cannot receive the press.
  - left-click anywhere in the dialog is not a valid binding: it restores the
    previous value and ends the capture, while still doing whatever it was
    going to do. Clicking the armed button toggles the capture off, so "left
    click ends the capture" holds everywhere with no exception to teach.
  - Escape stays two things. The armed filter marks it handled; unhandled keys
    reach the dialog on their own.
  - pyautogui keeps synthesising the Ctrl+V. Qt injects no keystrokes.
    QGuiApplication.clipboard() does replace pyperclip.
  - geometry.py and dpi.py are deleted. Qt 6 has high DPI on by default and
    cannot disable it; restoreGeometry takes an opaque blob, so the regex
    parse and _clamp_to_desktop both go.
  - Appearance comes from one QSS file. Beat: per-widget setStyleSheet, which
    Qt makes equally available -- that is why this is a GOVERNING RULE and not
    a preference. Reopens if a widget genuinely cannot be styled from the
    sheet, which would be a Qt limitation rather than a design choice.
  - One process. The daemon becomes a worker thread; the stdout wire
    protocol, daemon_proc.py and the 100ms drain go with it. Beat: two
    processes kept for native-crash isolation. No native crash in
    ctranslate2 or CUDA has been observed on this machine; the one model
    fault in tray_error.log was a Python exception, which one process
    catches. Reopens if a native crash is observed -- the answer then is a
    watchdog relaunch, not a second process.
  - Config is the pydantic model as it stands, held by one QObject with a
    single changed(old, new) signal. Settings builds a new validated model,
    the holder swaps and emits, and each consumer with derived state -- the
    STT engine, audio, the hotkey -- compares the fields it owns and decides
    whether to rebuild. Beat: pydantic with reads at point of use, which
    tells nobody to reload; and a Property(notify=) per field, which is a
    signal per field for three listeners. Reopens if a fourth consumer
    needs per-field granularity.
  - The two crash-path dialogs stay native MessageBoxW through ctypes: the
    startup crash, which can fire inside QApplication's own constructor
    when the portable folder's plugin path is wrong, and the exception
    hook, which fires when Qt may be what broke. Every other dialog is Qt.
    Beat: Qt throughout, which has nothing to show a dialog with on the
    day it matters. Reopens never -- this is what exists at the moment of
    failure, not a toolkit preference.
  - Window state lives in a QSettings INI file in userdata, beside
    config.json, never QSettings' default registry backend. Qt round-trips
    its own saveGeometry blob; config.json stays the file a human edits.
    Beat: a base64 field in the pydantic model, which puts an opaque Qt
    value in a hand-edited file and needs our own encode line. A bad blob
    makes restoreGeometry return false and the window opens at its default,
    so no repair path is needed. Reopens if the portable copy list cannot
    carry the second file, which it can.
  - hotkey.py keeps RegisterHotKey and loses its thread: Qt has no
    global-shortcut API, and WM_HOTKEY posted to the main thread's queue
    reaches a native event filter on the application. MEASURED in
    spike-notes.txt. Beat: keeping the pump thread, which existed only
    because Tk could not receive Win32 messages.
  - Audio is file-centric through QAudioSource streaming into soundfile:
    16-bit FLAC written as frames arrive, Whisper reads the path, a killed
    process loses only the encoder's last buffer. Beat: QMediaRecorder,
    which records FLAC and shares the mic but writes 24-bit on the FFmpeg
    backend and 8-bit on the Windows one, with no sample-format setter.
    MEASURED in spike-notes.txt. Reopens if a Qt release adds a sample
    format to QMediaRecorder.
  - Config carries the mic's endpoint id beside its name. Match id first,
    name second, exact, no system default -- the rule input-device-plan.txt
    carries. The id survived four replugs and a reboot, MEASURED in
    spike-notes.txt. The name is what config.json and the dropdown show.
    Beat: name only, which two identical devices defeat.

SEAMS
==============================================================================
  - The entry-point switch is the one hard cut. Qt is built alongside the Tk
    tray, importing nothing, until that switch. Everything before it is inert.
  - Consequence of that cut, for whoever writes the sheet: every step before
    the switch produces code nothing runs, so the template's per-step launch
    gesture has nothing to launch. ALREADY WEIGHED: build a throwaway
    launcher that opens the Qt windows on their own, so each step has
    something to look at, and delete it at CLEANUP. Beat: accepting one large
    moment of truth at the switch, and flipping the switch early with a
    degraded app in between. Abandonment safety was never what was at risk --
    the Tk app keeps working untouched either way. Incremental verification
    was. Reopens if the throwaway launcher costs more to build than the
    step-by-step verification it buys.
  - Audio cuts away from the rest because it owns no windows, and needs no
    GUI application object to do it.
  - Appearance has no cut of its own; it lands on the stylesheet pass 1 ships.
  - Later work has no predetermined cuts. What replaces them: each piece must
    be independently shippable, so any one can be skipped without stranding
    the others.
