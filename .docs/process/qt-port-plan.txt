==============================================================================
GOAL
==============================================================================
Make this a Qt app. Port everything that makes sense to port -- ask what Qt
exposes before designing around what we have. Where hand-rolled code stays,
the code says why -- after a real decision, not by omission. Qt6 exposes
capabilities that did not exist when this app was designed: find them, and
decide whether each is useful now, useful later, or not at all. Anything worth
keeping gets written down, not left in the conversation that found it.

DELIVERABLES
==============================================================================
This list grows. A discovery pass that turns up something Qt makes possible
adds a deliverable here, and assigns it to a pass -- that is what the passes
are for, not scope creep to be resisted. GOAL's "useful now, useful later,
or not at all" is the filter; nothing else gates entry.

PASS 1 -- THE FRAMEWORK
Treated as atomic on the claim that one event loop owns the main thread, which
DESIGN still lists as unverified. Parity is checked against
qt-parity-inventory.txt, which holds every menu item, binding, tray action,
dialog and menu-free behaviour a user can reach -- push-to-talk included.
Not the implementation: reproducing a Tk accident is not parity.
  - The app runs under QApplication. Every window rebuilt.
  - The tray icon is Qt. pystray goes, and its background thread with it.
  - No widget sets its own appearance. One QSS file holds all of it, carrying
    today's colours. Themes come later; the mechanism cannot.
  - Worker output reaches the console through signals. output_queue, the
    100ms tick and console.drain() stop existing, and something else reports
    the daemon's exit -- the tick does that too today.
  - console.py is renamed to the output window, code side included. README and
    the View menu already say Output Window; "console" reads as a terminal and
    has already produced a wrong inference about how it works.
  - pynput leaves the tray. Both Settings captures become an event filter on
    the dialog reading ordinary Qt events -- no global hooks, no
    root.after(0, ...) marshalling. UX unchanged: the armed button greys via
    the stylesheet, left-click ends the capture, Escape still means two
    things. pynput survives in the daemon only.
  - Single instance is enforced through Qt. win32event.CreateMutex goes.
  - geometry.py and dpi.py are deleted. Window state persists through Qt.
  - The hotkey message pump runs in Qt's event loop, if the spike says it can.
    hotkey.py keeps RegisterHotKey either way.
  - Modals are Qt. The crash-path ones are open in DESIGN.
  - Clipboard reads and writes are Qt. pyperclip goes, and so do the console's
    two Tk clipboard paths.
  - Config keeps its current pydantic shape unless the spike says otherwise.
  - Every non-Qt survivor carries the fact that keeps it.

AFTER PASS 1 -- INDEPENDENT, IN ANY ORDER

AUDIO. Separable because it owns no windows. Must land before input-device
work, or portaudio_io.py gets wired and a deletion becomes a rework.
  - Capture and playback run through Qt. sounddevice goes.
  - Tones are numpy into a QAudioSink, generated with a 1ms cosine tail.
    Deleted, not ported: vdict/sounds' three wav files, _load_tone, the wave
    import, _resolve_output_device, the persistent OutputStream, _tone_queue,
    _current_tone, _current_tone_pos and _output_callback.
  - Pitch is C5 and G5 at A443, a perfect fifth -- 526.82Hz and 789.34Hz. The
    shipped WAVs measure A440; generating the tones is what turns pitch into a
    number rather than an asset. A preference, not a constraint: the interval
    carries the meaning, so do not "correct" it back to A440.
  - Device changes arrive as signals rather than being polled for.
  - Settings has a mic test with a live level meter. Reference
    implementation is Qt's own examples/multimedia/audiosource.

APPEARANCE. Pass 1 ships the mechanism without the polish.
  - Dark and light follow the system.

EVIDENCE
==============================================================================
READ FROM THIS TREE  (grouped by the surface being rebuilt. A new fact files
into a group; cross-cutting is for facts no single surface owns.)

OUTPUT WINDOW
  - console.py zoom is hand-built: set_font_size, zoom_step, _zoom_wheel and
    the key bindings in Console.__init__. Re-derive their number from the
    bind() calls, never from a figure written here
  - THREE things write to the text widget, not one. drain() off the queue on
    the 100ms tick; _write_error, installed through install_screen and called
    synchronously by error_log from whatever thread raised, bypassing the
    queue entirely; and _animate_dots on its own 1000ms root.after loop, a
    second timer nothing else records. DELIVERABLES' console bullet names
    only the first. Replace the queue alone and the on-screen half of error
    reporting stops appearing -- silently, because the disk write still
    succeeds
  - worker output: module-level queue, 100ms Tk timer drains it.
    console.drain() is the tray's most complex function
  - the console text widget is permanently DISABLED; every write flips it to
    NORMAL and back. inactiveselectbackground exists only because a disabled
    widget never takes focus, so the inactive colour is the only selection that
    ever draws
  - console.drain decides a toast by reading root.state() != 'normal'

SETTINGS
  - settings.py's tk.OptionMenus are mic, PTT mode, model size and compute
    device. None has an on-open hook. The compute-device one reaches into
    ["menu"] to disable a single entry
  - settings.py opens with withdraw, -topmost on, update_idletasks, screen
    measurement, deiconify, update_idletasks, -topmost off, focus_force. All of
    it prevents a position flash
  - settings.py guards against stacked windows with a module global,
    winfo_exists and a caught TclError
  - two unrelated key-capture paths. hotkey_capture binds <KeyPress> on the
    button; ptt_capture runs global pynput hooks because it disables the button
    first, and a disabled widget receives no events
  - ptt_capture marshals every pynput callback back to the Tk thread with
    root.after(0, ...). pynput's listener runs on its own thread
  - Escape means cancel-capture or close-dialog depending on focus. The capture
    handler returns "break" so the dialog never sees it

MENU
  - menu.py: tk accelerator= is display text only, bound separately. The Help
    menu refreshes via tk.Menu postcommand
  - menu mnemonics are underline= character indices, and accelerator= is
    separate from the binding that implements it, so a label can disagree with
    its key
  - the live instance of that: Control-Key-equal zooms in and no menu shows
    it, so Ctrl+= works and is undiscoverable. Ctrl+MouseWheel and the
    right-click Copy menu are reachable with no menu entry at all

TRAY AND APP
  - app._tick does two jobs on that same timer, not one -- console.drain()
    and daemon_proc.poll(), which reports the daemon's exit once
  - app.py raises the window via
    win32gui.SetForegroundWindow(int(window.wm_frame(), 0)), and detects
    minimize via <Unmap> plus state()=='iconic'
  - icon.py picks an .ico frame via GetSystemMetrics(SM_CXSMICON) plus PIL
  - pystray runs its own background thread
  - "Show Output" carries pystray's default=True, and that is what makes a
    click on the tray icon raise the window. Nothing else records that
    behaviour; QSystemTrayIcon expresses it as an activation reason instead

MODALS AND CRASH PATH
  - faults.py builds modality from Toplevel + transient + grab_set
  - mic-fault recovery spans TWO launches. Close writes MIC_FAULT_FLAG_PATH
    and force-quits; the next launch reads the flag, logs a note, opens
    Settings and deliberately does not start the daemon. Rebuild the modal
    from the dialog alone and the resume half is lost with no symptom
  - app.py assigns report_callback_exception -- Tk routes every exception
    raised inside a callback there. It reports through a native MessageBoxW,
    not a Tk modal, because Tk may be what broke
  - a Tk modal runs a nested event loop; hotkey_capture unbinds before opening
    one. Qt dialogs do the same, so this hazard survives the port

WINDOW STATE AND DPI
  - geometry.py: Tk persists no window state, and it parses the geometry
    string with a regex. Windows keeps its own restore rect --
    update_idletasks() between geometry() and state("zoomed")
  - dpi.py: Tk exposes no scaling. Inverse trap -- Tk already scales point
    sizes, so fonts must NOT go through scale()
  - dpi.py's scale() wraps every pixel dimension in settings.py and faults.py.
    Deleting dpi.py touches all of them

ENTRY POINT
  - vdict_tray.py enforces single instance with win32event.CreateMutex and
    an ERROR_ALREADY_EXISTS check
  - vdict_tray.py builds a throwaway Tk root and messagebox for the
    already-running path, separate from app's

AUDIO
  - the daemon holds ONE sd.OutputStream open for the whole process life and
    queues tones into its callback, which writes silence when the queue is
    empty. The persistence is the point: closing and reopening puts a click
    on the first tones. That architecture is a workaround, not a preference
  - portaudio_io.py is built but unwired -- vulture flags every function

CROSS-CUTTING
  - appearance is set per widget in console.py (bg, fg, selectbackground,
    inactiveselectbackground, font) and in settings.py (the banner font, the
    version label's fg and font). No central definition
  - a symbol grep cannot see Tk's string-shaped API: the sequences passed to
    bind(), "break" returned to stop propagation, text indices "1.0" and END,
    the state() values normal/iconic/zoomed, "WM_DELETE_WINDOW", and widget
    state strings. Re-derive by reading the tray modules, never by grepping
    tkinter's names
  - three clipboards, not one: console.copy fires the <<Copy>> virtual event,
    console.copy_all uses root.clipboard_clear/clipboard_append, and
    daemon/keyboard.py uses pyperclip
  - the dead-widget test is tk.TclError plus winfo_exists, in console.copy and
    settings.open_settings
  - layout is pack() throughout. No grid, no place
  - deferred imports hide from a leading-import grep. Re-derive by searching
    for import lines that are INDENTED, never by reading the tops of files.
    That search returns: pyperclip and pyautogui in daemon/keyboard.py,
    huggingface_hub in stt.py, ctranslate2 AND sounddevice in settings.py,
    pynput in tray/ptt_capture.py, and tkinter itself twice -- ttk inside
    settings.py's _build_window, and a whole second tkinter plus messagebox
    in vdict_tray.py's already-running path.
    sounddevice, pynput and tkinter are all things this port removes or
    moves, so a dependency sweep that reads only file tops reports them gone
    while they are still there. This line previously named three of these and
    was itself written without running the search it prescribes.
  - three deliberate decisions the rebuild must carry, none of them in a code
    comment today. They become comments when the rebuilt code is written:
      "Loading model" is left unterminated on purpose -- the console appends
        the dots one at a time, so no periods belong in the text
      CATEGORIES["transcript"] has an empty marker and no colour on purpose --
        bare text is the point, it must stay copy-paste clean
      app._force_quit's showerror is a direct call, not category dispatch --
        it is the half guaranteed to be seen when the console may be gone
  - the tray reaches into the daemon. tray/ptt_capture.py imports BUTTON_MAP
    from vdict/daemon/keyboard.py, and the ptt.button strings its capture
    writes -- "key:<name>", or a bare mouse name -- are parsed back by the
    daemon's PTTListener. A Qt capture emitting a different string breaks
    dictation with nothing in the console to explain it. PTT is not outside
    this port's scope; it is the most user-reachable behaviour in the app
  - session.py, const.py and transcript.py contain no Tk mechanisms

MEASURED  (one session, one machine, default input 'Microphone (PDP Audio
Device)'. Re-run against a different device before trusting any of it.)
  - press-to-first-sample, five trials each, same device same session:
    QAudioSource 13-17ms, sounddevice 40-52ms after a 157ms first call that
    is PortAudio cold init. Qt is faster and pays no cold penalty.
  - a beep through QAudioSink does not block capture. 121 reads across 1.2s,
    largest gap 11.9ms which is the read cadence itself. No error either side.
  - QCoreApplication is enough. No GUI application object is needed to
    capture or play.
  - the default input accepts 16kHz mono Int16 directly, isFormatSupported
    true, so nothing resamples.
  - QAudioDevice.id() is a Windows MMDevice endpoint id, shaped
    {0.0.1.00000000}.{guid}. Whether it survives a replug is still open.
  - tones need a cosine fade over the final 1ms or they click. A QAudioSink
    built and destroyed per tone is clean, so no persistent stream.

READ FROM PYSIDE6  (clone: .reference/pyside-setup, and the type stubs at
venv/Lib/site-packages/PySide6/*.pyi. Both gitignored. The stubs are what
make a Qt symbol checkable instead of recalled.)
  - theming: QApplication.setStyleSheet(qss) is app-wide.
    doc/tutorials/basictutorial/widgetstyling.rst
  - window state: saveGeometry/restoreGeometry.
    examples/widgets/mainwindows/application
  - dpi: on by default in Qt 6, cannot be disabled.
    doc/faq/porting_from2.rst
  - threads: default AutoConnection runs the receiver in the receiver's
    thread. doc/tutorials/basictutorial/signals_and_slots.rst
  - tray: QSystemTrayIcon -- context menu, activated with
    Trigger/DoubleClick/MiddleClick, showMessage for toasts
  - audio out: QAudioSink.start() returns a QIODevice to write, plus
    setVolume()
  - audio in: QMediaDevices audioInputs, defaultAudioInput,
    audioInputsChanged
  - console: QTextEdit.zoomIn/zoomOut
  - menus: QAction.setShortcut wires the shortcut; QMenu.aboutToShow replaces
    postcommand
  - key capture: QKeyEvent.nativeVirtualKey() hands back the Windows VK
    directly, so the existing Windows naming code needs no mapping layer.
    QKeySequenceEdit yields a QKeySequence instead, which does
  - mouse buttons: Qt.MouseButton names XButton1/XButton2 (also BackButton/
    ForwardButton) and ExtraButton1 upward. QSinglePointEvent.button() reports
    which one fired
  - Qt.ShortcutContext.WidgetShortcut scopes a shortcut to a focused widget
  - QObject.installEventFilter/eventFilter see events on the way to their
    target; returning False passes them through untouched
  - icons: QIcon reads multi-resolution .ico natively
  - QDataWidgetMapper maps widgets to a QAbstractItemModel, not to a plain
    QObject

DESIGN
==============================================================================
Four things hold open work, and they close in order. SCRATCHPAD is discovery
not yet run -- it drains first. JUDGMENT waits on nobody and closes next,
because settling it may collapse items below. ASSUMED is a fact we need and
lack; each closes by spike or by an explicit decision to build without it.
BLOCKED waits on a named ASSUMED item and cannot close before it. The plan is
done when all four are empty -- not when the scratchpad is.

SETTLED
  - All in on Qt, not a GUI-only port. Beat: moving only widgets, which leaves
    two device vocabularies to map between. Both overturn conditions have
    been tested and neither held -- see MEASURED.
  - Audio moves to Qt and can be its own sheet. All three gates cleared:
    latency, QCoreApplication, and the tone click. Beat: keeping sounddevice
    because the beeps worked -- they worked through forty lines of machinery
    that a 1ms fade makes unnecessary.
  - pynput stays in the daemon. PTT must fire while the app is unfocused with
    the cursor anywhere, which no widget event can do. Not the button naming --
    Qt names XButton1/XButton2. Beat: hand-rolled SetWindowsHookEx.
  - pynput leaves Settings. Both captures become ordinary Qt events, read by an
    event filter on the dialog. Global hooks were only ever needed because
    ptt_capture disables the button, and a disabled widget receives no events.
  - the capture UX is unchanged -- the button greys while armed, the captured
    key appears on its face. Greyed is a stylesheet state, not a disabled
    widget, or it cannot receive the press.
  - left-click anywhere in the dialog is not a valid binding: it restores the
    previous value and ends the capture, while still doing whatever it was
    going to do. Clicking the armed button toggles the capture off, so "left
    click ends the capture" holds everywhere with no exception to teach.
  - Escape stays two things. The armed filter marks it handled; unhandled keys
    reach the dialog on their own.
  - pyautogui keeps synthesising the Ctrl+V. Qt injects no keystrokes.
    QGuiApplication.clipboard() does replace pyperclip.
  - geometry.py and dpi.py are deleted. Qt 6 has high DPI on by default and
    cannot disable it; restoreGeometry takes an opaque blob, so the regex
    parse and _clamp_to_desktop both go.
  - Appearance comes from one QSS file. Beat: per-widget setStyleSheet.

BLOCKED ON EVIDENCE
  - Does hotkey.py survive at all, and if so does it keep its own thread.
    Blocked on what Qt exposes for a system-wide key press, then on whether
    the dispatcher sees WM_HOTKEY.
  - Is pass 1 atomic, and therefore is the SEAMS cut the only one available.
    Blocked on whether two event loops exclude each other.
  - Where does a Qt app persist window state, and is config.json the right
    home. Qt's own example uses QSettings, and splitting -- app settings in
    JSON, window state in QSettings -- is what Qt apps normally do. Blocked
    on the QByteArray round-trip only if we keep it in config.json.
  - Does config persist a device id instead of matching on a name. Blocked on
    whether QAudioDevice.id() is stable.
  - Config object shape. Blocked on which shape survives a real Settings
    dialog.

JUDGMENT, NO SPIKE NEEDED
  - Do the crash-path modals convert to Qt. The startup crash fires before
    any window exists; the callback handler fires when the toolkit may be what
    broke.
  - Does daemon_proc become QProcess. core-arch deletes the subprocess soon
    after, so the question is whether the window between them pays.
  - FLAC. QMediaRecorder records a capture session to a file; audio_io.py
    encodes a numpy buffer after transcription. Keep soundfile, or restructure
    to record-during-capture.

SEAMS
==============================================================================
  - The entry-point switch is the one hard cut. Qt is built alongside the Tk
    tray, importing nothing, until that switch. Everything before it is inert.
  - Consequence of that cut, for whoever writes the sheet: every step before
    the switch produces code nothing runs, so the template's per-step launch
    gesture has nothing to launch. ALREADY WEIGHED: build a throwaway
    launcher that opens the Qt windows on their own, so each step has
    something to look at, and delete it at CLEANUP. Beat: accepting one large
    moment of truth at the switch, and flipping the switch early with a
    degraded app in between. Abandonment safety was never what was at risk --
    the Tk app keeps working untouched either way. Incremental verification
    was.
  - Audio cuts away from the rest because it owns no windows, and needs no
    GUI application object to do it.
  - Appearance has no cut of its own; it lands on the stylesheet pass 1 ships.
  - Later work has no predetermined cuts. What replaces them: each piece must
    be independently shippable, so any one can be skipped without stranding
    the others.
