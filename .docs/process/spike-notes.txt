VOICE DICTATION - SPIKE NOTES

Findings from real investigation, kept for reference. Not a task list.


WHISPER (faster-whisper, large-v3, cuda)

Short clips (~140-180ms) of real captured audio can produce confident,
plausible-but-false text ("Let's go.", "Thank you.") instead of an empty
result. Pure synthetic silence or random noise of the same length does not
reproduce this -- only real mic transients did.

transcribe() latency does not scale with clip length. 10ms-2000ms clips all
took ~190-200ms after model warm-up. First call after model load pays a
one-time ~500-700ms warm-up cost, unrelated to input length.

Two concurrent transcribe() calls on the same loaded model instance do not
crash or corrupt output, but serialize -- a concurrent pair takes ~2x one
call's time, no parallel speedup.

MIN_RECORDING_SAMPLES stays at 6400 (0.4s): it already filters the exact
duration range where hallucination was observed.


CPU CORE TOPOLOGY (Windows, hybrid P/E chips)

Windows reports performance versus efficiency cores through
GetLogicalProcessorInformationEx with RelationProcessorCore. Each record
carries an EfficiencyClass byte at offset 9 of the record; higher is faster.
Walk the buffer by each record's own Size field. Verified working on an
i7-9700K: eight physical cores, all reporting class 0.

The rule that falls out needs no special cases: count physical cores per
efficiency class and request the count in the HIGHEST class as cpu_threads.
All-performance chips return everything. All-efficiency chips -- the modern
N-series Celerons are built entirely from them -- also return everything,
correctly, because they are homogeneous. Only mixed chips return a subset.

Chosen against a hard affinity mask, which would guarantee placement where a
thread count only hints at it. Reasons: the barrier argument for excluding
efficiency cores assumes CTranslate2 partitions work statically, and its
threading is compiled C++ that cannot be inspected from the venv. With
dynamic scheduling a slow core simply takes fewer chunks and excluding eight
real cores becomes a straight loss. A thread count is correct under either
model. Overturned by a hybrid machine measuring pinned against unpinned --
neither machine here is hybrid, so this cannot be settled locally.

Windows migrates threads between core types continuously while they run, so
a thread count is a hint and never a guarantee. That is a known limit of the
choice above, not an oversight.


AUDIO CORPUS AND TRANSCRIPT LOG (cannot be paired)

The FLAC corpus and transcript_log.txt cannot be joined, and no later effort
recovers it. FLAC filenames carry a microsecond timestamp; transcript lines
carry nothing at all. The counts do not reconcile in either direction: the
console writes a blank line after every transcript, FLAC files are written
for captures too short to ever be transcribed, and the log predates FLAC
capture being switched on.

Consequence for any tuning work: there is no ground truth. The usable
substitute is a pseudo-reference -- run the highest-quality configuration
over a sample, treat its output as truth, and measure every other
configuration as divergence from it.


VRAM MEASUREMENT (Windows, consumer NVIDIA)

Per-process VRAM cannot be read on Windows consumer cards. nvidia-smi
--query-compute-apps returns used_memory as [N/A] for every process under
the WDDM driver model, and no permission level changes it. Do not spend time
on it again.

What works: nvidia-smi --query-gpu=memory.used sampled before a load and at
peak, taking the delta. Whole-GPU, so anything else changing on the desktop
during the sample pollutes it.

The trap underneath: Windows lets CUDA allocations spill into system RAM
rather than failing when VRAM runs out. A model that does not fit still
runs, slowly and silently. Measured on this machine, an RTX 3070 Ti reports
8192 MiB total with roughly 6000 MiB already held by the desktop -- so any
timing run has to record free VRAM at its start, or a spilled run gets
recorded as a slow configuration.


COMPUTE TYPES (CTranslate2 4.8.1)

Supported sets differ by device and by GPU generation. Re-derive with
ctranslate2.get_supported_compute_types(device) rather than trusting a list.
On this machine, CPU offered int8, int8_float32, int16 and float32; an RTX
3070 Ti additionally offered float16, bfloat16, int8_float16 and
int8_bfloat16.

bfloat16 requires Ampere. Pre-Ampere cards -- a 2070 and anything else in
the Turing generation -- do not have it. So a compute type measured as
fastest here cannot ship as a constant: the shipped code has to probe what
the device supports and walk an ordered preference list.


DISPLAY DPI (Windows, Tk)

A process that has not declared DPI awareness reads the system DPI as 96,
whatever the display is set to. Tk shares the trap -- winfo_fpixels('1i')
and tk scaling both report ~96 there too. No library avoids this;
awareness is a process-level declaration, so a probe must run under the
same conditions as the app or the number is fiction that looks plausible.

Windows and Tk disagree on the figure even with awareness set:
GetDpiForSystem() reports the configured setting, Tk derives its own from
reported physical screen dimensions (measured 168 vs 167.876). Reading DPI
from Tk instead of ctypes would shift every scaled dimension by a pixel or
two, and would make vdict/tray/dpi.py depend on a live Tk root.

This whole finding expires with the Qt port, which deletes dpi.py -- Qt 6 has
high DPI on by default and cannot disable it.


AUDIO PLAYBACK (sounddevice/WASAPI)

sd.play() opens a new WASAPI stream per call -- that stream-open is what
causes an audible click on every play. A single persistent sd.OutputStream,
written to repeatedly, has no click.

WASAPI auto_convert (sd.WasapiSettings(auto_convert=True)) correctly
resamples a fixed-rate source (tested 192000 Hz) down to a device's native
rate (tested 48000 Hz) -- correct duration and pitch, confirmed both from a
live numpy array and from a real WAV file round-tripped through disk.

A crashed process (unhandled exception, stream never closed) does not lock
the output device -- Windows reclaims the WASAPI session on process exit,
confirmed by immediately reopening the same device from a fresh process.

An open but unfed WASAPI stream was suspected to click on the next real
write after idling. WRONG, or at least incomplete: feeding it silence
continuously (never idle) did not fix it. The artifact persists -- a brief
burst of white noise, not a clean click/pop, landing specifically right
after a tone plays. White noise (not a pop) points at a buffer underrun
(driver has nothing valid to output for an instant) rather than a waveform
discontinuity. Leading theory: the writer thread is a blocking-write push
model (Python decides when to hand off each chunk); a pull model (PortAudio
calls back for more data on its own real-time thread, same pattern already
used for microphone input) would remove the Python-scheduling dependency
entirely. Not yet implemented or confirmed.

Checked and ruled out as causes: np.empty() uninitialized memory (never
used anywhere in this codebase -- everything is np.zeros/.astype()),
dtype mismatch (every array reaching .write() confirmed float32, matching
the stream's own dtype="float32"). Confirmed real but likely too small to
be the cause: the shipped tones' fade-out never reaches exactly 0 at the
last sample (off-by-one in the fade math, ~0.05% of full scale residual) --
worth fixing whenever the WAV assets get regenerated, not the prime suspect.


TONE CLICK -- TWO INDEPENDENT CAUSES

sd.play()'s per-call stream open, above. And the waveform ending on a non-zero
sample, which the driver reproduces as a step.

The second is audible only on a high-resolution chain with well-damped
drivers; ordinary speakers mask it. A no-click result on cheap equipment is
not evidence.

A cosine fade over the final 1ms removes it, and a QAudioSink built per tone is
then clean. The WAV assets and the persistent OutputStream are workarounds for
that cause, which is why neither survives the port.


DICTATION CAPTURE RATE

Roughly 570 clips a day on this machine, swinging between 120 and 956. That
projects to about 208,000 captures a year: tens of megabytes of database rows,
and roughly 34 GB of FLAC.

Re-derive rather than trusting these figures -- count files under
FLAC_CORPUS_DIR, or rows in captures, across a known span. The rate is one
person's habit and moves with it.

Rows are permanent at that size; audio is the only store worth rotating, and
nobody has measured how much of it voice-ID actually needs.
