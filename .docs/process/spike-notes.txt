VOICE DICTATION - SPIKE NOTES

Findings from real investigation, kept for reference. Not a task list.


WHISPER (faster-whisper, large-v3, cuda)

Short clips (~140-180ms) of real captured audio can produce confident,
plausible-but-false text ("Let's go.", "Thank you.") instead of an empty
result. Pure synthetic silence or random noise of the same length does not
reproduce this -- only real mic transients did.

transcribe() latency does not scale with clip length. 10ms-2000ms clips all
took ~190-200ms after model warm-up. First call after model load pays a
one-time ~500-700ms warm-up cost, unrelated to input length.

Two concurrent transcribe() calls on the same loaded model instance do not
crash or corrupt output, but serialize -- a concurrent pair takes ~2x one
call's time, no parallel speedup.

MIN_RECORDING_SAMPLES stays at 6400 (0.4s): it already filters the exact
duration range where hallucination was observed.


CPU CORE TOPOLOGY (Windows, hybrid P/E chips)

Windows reports performance versus efficiency cores through
GetLogicalProcessorInformationEx with RelationProcessorCore. Each record
carries an EfficiencyClass byte at offset 9 of the record; higher is faster.
Walk the buffer by each record's own Size field. Verified working on an
i7-9700K: eight physical cores, all reporting class 0.

The rule that falls out needs no special cases: count physical cores per
efficiency class and request the count in the HIGHEST class as cpu_threads.
All-performance chips return everything. All-efficiency chips -- the modern
N-series Celerons are built entirely from them -- also return everything,
correctly, because they are homogeneous. Only mixed chips return a subset.

Chosen against a hard affinity mask, which would guarantee placement where a
thread count only hints at it. Reasons: the barrier argument for excluding
efficiency cores assumes CTranslate2 partitions work statically, and its
threading is compiled C++ that cannot be inspected from the venv. With
dynamic scheduling a slow core simply takes fewer chunks and excluding eight
real cores becomes a straight loss. A thread count is correct under either
model. Overturned by a hybrid machine measuring pinned against unpinned --
neither machine here is hybrid, so this cannot be settled locally.

Windows migrates threads between core types continuously while they run, so
a thread count is a hint and never a guarantee. That is a known limit of the
choice above, not an oversight.


AUDIO CORPUS AND TRANSCRIPT LOG (cannot be paired)

The FLAC corpus and transcript_log.txt cannot be joined, and no later effort
recovers it. FLAC filenames carry a microsecond timestamp; transcript lines
carry nothing at all. The counts do not reconcile in either direction: the
console writes a blank line after every transcript, FLAC files are written
for captures too short to ever be transcribed, and the log predates FLAC
capture being switched on.

Consequence for any tuning work: there is no ground truth. The usable
substitute is a pseudo-reference -- run the highest-quality configuration
over a sample, treat its output as truth, and measure every other
configuration as divergence from it.


VRAM MEASUREMENT (Windows, consumer NVIDIA)

Per-process VRAM cannot be read on Windows consumer cards. nvidia-smi
--query-compute-apps returns used_memory as [N/A] for every process under
the WDDM driver model, and no permission level changes it. Do not spend time
on it again.

What works: nvidia-smi --query-gpu=memory.used sampled before a load and at
peak, taking the delta. Whole-GPU, so anything else changing on the desktop
during the sample pollutes it.

The trap underneath: Windows lets CUDA allocations spill into system RAM
rather than failing when VRAM runs out. A model that does not fit still
runs, slowly and silently. Measured on this machine, an RTX 3070 Ti reports
8192 MiB total with roughly 6000 MiB already held by the desktop -- so any
timing run has to record free VRAM at its start, or a spilled run gets
recorded as a slow configuration.


COMPUTE TYPES (CTranslate2 4.8.1)

Supported sets differ by device and by GPU generation. Re-derive with
ctranslate2.get_supported_compute_types(device) rather than trusting a list.
On this machine, CPU offered int8, int8_float32, int16 and float32; an RTX
3070 Ti additionally offered float16, bfloat16, int8_float16 and
int8_bfloat16.

bfloat16 requires Ampere. Pre-Ampere cards -- a 2070 and anything else in
the Turing generation -- do not have it. So a compute type measured as
fastest here cannot ship as a constant: the shipped code has to probe what
the device supports and walk an ordered preference list.


DISPLAY DPI (Windows, Tk)

A process that has not declared DPI awareness reads the system DPI as 96,
whatever the display is set to. Tk shares the trap -- winfo_fpixels('1i')
and tk scaling both report ~96 there too. No library avoids this;
awareness is a process-level declaration, so a probe must run under the
same conditions as the app or the number is fiction that looks plausible.

Windows and Tk disagree on the figure even with awareness set:
GetDpiForSystem() reports the configured setting, Tk derives its own from
reported physical screen dimensions (measured 168 vs 167.876). Reading DPI
from Tk instead of ctypes would shift every scaled dimension by a pixel or
two, and would make vdict/tray/dpi.py depend on a live Tk root.

This whole finding expires with the Qt port, which deletes dpi.py -- Qt 6 has
high DPI on by default and cannot disable it.


AUDIO PLAYBACK (sounddevice/WASAPI)

sd.play() opens a new WASAPI stream per call -- that stream-open is what
causes an audible click on every play. A single persistent sd.OutputStream,
written to repeatedly, has no click.

WASAPI auto_convert (sd.WasapiSettings(auto_convert=True)) correctly
resamples a fixed-rate source (tested 192000 Hz) down to a device's native
rate (tested 48000 Hz) -- correct duration and pitch, confirmed both from a
live numpy array and from a real WAV file round-tripped through disk.

A crashed process (unhandled exception, stream never closed) does not lock
the output device -- Windows reclaims the WASAPI session on process exit,
confirmed by immediately reopening the same device from a fresh process.

An open but unfed WASAPI stream was suspected to click on the next real
write after idling. WRONG, or at least incomplete: feeding it silence
continuously (never idle) did not fix it. The artifact persists -- a brief
burst of white noise, not a clean click/pop, landing specifically right
after a tone plays. White noise (not a pop) points at a buffer underrun
(driver has nothing valid to output for an instant) rather than a waveform
discontinuity. Leading theory: the writer thread is a blocking-write push
model (Python decides when to hand off each chunk); a pull model (PortAudio
calls back for more data on its own real-time thread, same pattern already
used for microphone input) would remove the Python-scheduling dependency
entirely. Not yet implemented or confirmed.

Checked and ruled out as causes: np.empty() uninitialized memory (never
used anywhere in this codebase -- everything is np.zeros/.astype()),
dtype mismatch (every array reaching .write() confirmed float32, matching
the stream's own dtype="float32"). Confirmed real but likely too small to
be the cause: the shipped tones' fade-out never reaches exactly 0 at the
last sample (off-by-one in the fade math, ~0.05% of full scale residual) --
worth fixing whenever the WAV assets get regenerated, not the prime suspect.


TONE CLICK -- TWO INDEPENDENT CAUSES

sd.play()'s per-call stream open, above. And the waveform ending on a non-zero
sample, which the driver reproduces as a step.

The second is audible only on a high-resolution chain with well-damped
drivers; ordinary speakers mask it. A no-click result on cheap equipment is
not evidence.

A cosine fade over the final 1ms removes it, and a QAudioSink built per tone is
then clean. The WAV assets and the persistent OutputStream are workarounds for
that cause, which is why neither survives the port.


DICTATION CAPTURE RATE

Roughly 570 clips a day on this machine, swinging between 120 and 956. That
projects to about 208,000 captures a year: tens of megabytes of database rows,
and roughly 34 GB of FLAC.

Re-derive rather than trusting these figures -- count files under
FLAC_CORPUS_DIR, or rows in captures, across a known span. The rate is one
person's habit and moves with it.

Rows are permanent at that size; audio is the only store worth rotating, and
nobody has measured how much of it voice-ID actually needs.


VOCABULARY IS THE CHEAPEST SETTING TO MAKE LIVE

initial_prompt is a per-call argument to STTEngine.transcribe(), and the
vocabulary string is read from vocabulary.txt rather than config.json. It is
not baked into the loaded model. Vocabulary is therefore the cheapest setting
to make live, not the most expensive -- it only looks expensive because it is
hoisted into a local before the daemon's loop starts.

Read while B1 was written. Re-check against STTEngine.transcribe's signature
rather than trusting this line.


QT NATIVE EVENT FILTER RECEIVES WM_HOTKEY

RegisterHotKey(None, ...) on the main thread posts WM_HOTKEY to the thread
queue, and a QAbstractNativeEventFilter installed on the application
receives it: 6-8ms from synthetic key press to filter, four of four runs,
under QCoreApplication and QApplication alike. Read the message with
MSG.from_address(int(message)). hotkey.py needs no thread and no pump of
its own under Qt.


WHISPERMODEL SWAP RELEASES CUDA MEMORY

Four cycles of load small/float16, transcribe, del, gc: each load +808 MiB,
each delete back to +165 MiB over baseline, loaded peak drifting 3 MiB
across the four. The 165 MiB is the CUDA context and cuBLAS workspace, paid
once per process and never growing. Reload in place is safe.


EMBEDDABLE PYTHON LOADS CUDA FROM THE TREE

python-3.12 embeddable zip, site enabled in python312._pth, pip
bootstrapped, faster-whisper plus nvidia-cublas-cu12 and nvidia-cudnn-cu12
installed into its own site-packages. With CUDA_PATH removed and every cuda
and nvidia entry stripped from PATH, ctranslate2 found the device and
transcribed on the GPU. The mechanism is stt.py's existing prepend of
site-packages/nvidia/*/bin to PATH; ctranslate2's own add_dll_directory
covers ROCm only. Only the driver comes from the machine.

FILE-CENTRIC AUDIO: STREAM QAUDIOSOURCE INTO SOUNDFILE, NOT QMEDIARECORDER

QMediaRecorder records real FLAC and shares the mic with a raw
QAudioSource and with the live daemon at once, but it has no sample-format
setter. The default FFmpeg backend writes 24-bit at every quality setting
and its constant-bitrate mode writes a file nothing can open.
QT_MEDIA_BACKEND=windows writes 8-bit at 44.1kHz and ~270 bytes for 1.5s:
broken in this Qt build. QAudioSource Int16 frames written into a
soundfile FLAC as they arrive: 16-bit, 27KB for 3s against ~92KB from the
recorder. Hard-killed with the file still open, PyAV decoded 2.82 of 3.00s;
only the encoder's last buffer is lost, and faster-whisper reads the path
directly. One capture path serves PTT and ambient.


QMEDIADEVICES SEES HOTPLUG; THE ENDPOINT ID SURVIVES REPLUG AND REBOOT

audioInputsChanged fired on every plug and unplug across four cycles of a
USB microphone, the device left audioInputs() on unplug and returned on
replug, and QAudioDevice.id() was byte-identical every time, and again
after a reboot with the device left plugged in. Plug fires twice with the
same list. The test device is "Microphone (USB Audio Device)"; the PDP
device stays enumerated whether or not anything is attached to it, so it
cannot test hotplug.


UNPLUG MID-STREAM: QAUDIOSOURCE STOPS WITH IOERROR AND DOES NOT RESUME

A QAudioSource reading Int16 at 16kHz from a USB microphone, unplugged
mid-stream: within the same second the state went StoppedState, error()
went IOError, delivery stopped, and audioInputsChanged fired with the
device gone. Replugged six seconds later: audioInputsChanged fired with
the device back, the source stayed StoppedState/IOError and delivered
nothing. Recovery is the app's job: treat IOError as the end of that
capture with an error outcome, and on audioInputsChanged with the
configured device present, build a new QAudioSource. QAudioSource's
stateChanged signal cannot be connected from Python in PySide6 6.11.1
("QAudio::State cannot be converted"); poll state() and error() instead.


PUNCTUATION RESTORATION (B13)

rpunct is a dead end: it hard-pins pandas==1.2.4 and torch==1.8.1, 2021
exact versions with no Python 3.12 wheels, and the source build fails
against current Cython. Unmaintained, do not retry it.
oliverguhr/fullstop-punctuation-multilang-large via the
deepmultilingualpunctuation package, CPU-only: model load ~3s once at
startup, restoration call ~88ms average. Threshold tested at 25
words/sentence, an untuned placeholder. 52 real transcript_log.txt lines
flagged only 1; HOLD mode's release-and-re-press between thoughts may
already prevent the run-ons this targets. Toggle mode has no such
discipline.


PHONETIC CODES COLLIDE ON ORDINARY WORDS (B21)

jellyfish (maintained, MIT, prebuilt wheels, Rust-backed) gives metaphone,
soundex, nysiis and match_rating_codex as pure algorithms. "Trey" and
"Tray" share a metaphone code, so the mechanism works for the motivating
case. Bare code equality is not safe: "cloud" and "clod" both collide with
"Claude", "true" with "Tray", "pity" with "PTT". A bare match silently
rewrites an everyday word to a name.


WHISPER MODEL LADDER (B22, Mike's GPU testing, i7 9th gen + 3070 Ti)

VRAM watched live. GPU curated three: small.en / medium.en / large-v3,
one per card tier (4GB+/6GB+/8GB+), biggest-that-fits. large-v3-turbo is
a nuanced alternate, not a fourth tier. CPU by compute concept, not
measured: tiny.en / small.en / medium.en, same family, no distillation.
large-v3-turbo on CPU: its speedup prunes only the decoder (32 layers to
4); the encoder, which is what CPU struggles with, stays large-size, so it
costs about what large-v3 costs. Reopens if the workload becomes
decoder-bound, which ambient mode's long chunks would do. distil-small.en
rejected: a distillation tradeoff to explain for marginal gain. Reopens if
a CPU user reports small.en too slow. Per-tier speed on real hardware is
unverified; inference tuning measures it.

AUDIO SPIKES -- measured, input "Microphone (USB Audio Device)", output "Speakers (USB Audio CODEC )", app left running on the PDP mic. Scripts under scratchpad/spikes2/.

1 QAudioSink push mode. Three sink formats tried: 16 kHz mono Float (numpy resample), preferred 48 kHz stereo Float, 192 kHz mono Int16 (WAV bytes untouched). bufferSize 16000 / 96000 / 96000 B, all exactly 250 ms; bytesFree before write = bufferSize. high (80 ms) and low (90 ms): one write() took everything, 0.01-0.97 ms, IdleState at 81-100 ms after write. low_double (330 ms) exceeds the buffer: first write took only bufferSize, 8 top-ups, IdleState at 331-340 ms. NoError throughout. Design: one write is fire-and-forget for high and low; low_double needs setBufferSize(>= its bytes) before start() or a bytesFree top-up loop; "done" = ActiveState then IdleState, 7-10 ms after nominal length.

2 Format support. defaultAudioOutput preferred 48000 Float 2ch, min/max rate 8000-192000, formats UInt8/Int16/Int32/Float. isFormatSupported(192000 mono Float)=True, (192000 mono Int16)=True, 12/12 True across 16k/48k x mono/stereo x Float/Int16. Input USB Audio Device preferred 48000 Float 2ch; 192k/48k/16k mono Int16 all True. Design: hand the 192 kHz WAVs to QAudioSink as-is; Qt's Windows backend converts.

3 start() to first readyRead, 16 kHz mono Int16, five processes. cold: start() blocked 34.2-36.9 ms, first readyRead at 56.3-58.0 ms. warm: start() blocked 21.0-22.3 ms, first readyRead at 45.8-47.5 ms. First chunk 258 B (129 samples, ~8 ms). bufferSize 8000 B (250 ms at Int16). Design: press to first audio ~57 ms cold / ~47 ms warm; keeping a source warm buys ~11 ms.

4 Tail after stop(). Default 8000 B buffer, last 300 ms unread before stop: bytesAvailable before stop 8000 (1600 B already dropped by overrun); readAll() after stop() returned 8000 B immediately, after processEvents, after 300 ms; io.isOpen() True; StoppedState NoError; QAudioSource.bytesAvailable() reads 0 after stop while the QIODevice still reports the tail. setBufferSize(64000): tail 9600 B before and after stop, total 63298 B vs 63296 expected, zero loss. Design: read the tail through the QIODevice after stop(); the loss mechanism is any read gap longer than bufferSize.

5 Who resamples. Simultaneous 16 kHz mono Float and 48 kHz mono Float captures of played white noise. qt16k minus pref48k per band: 200-1k +0.2 dB, 1-3k -0.1, 3-5k -0.1, 5-6k -0.1, 6-7k -0.1, 7-7.5k -0.3, 7.5-8k -5.0 dB. Reference: brick-wall lowpass at 7.6k then decimate gives -6.2 dB in 7.5-8k; naive [::3] decimation gives +9.6 to +22.8 dB. The 48k capture had content above 8 kHz 27 dB below its 3-5k band, and Qt did not fold it. Design: Qt's 16 kHz capture path is a proper lowpass resampler; capture at 16 kHz directly, no numpy resampling.

6 Main-thread stall, 16 kHz Int16, 3 s wall, 48000 expected. No stall: 47649 samples, shortfall 21.9 ms (startup). 0.5 s sleep at t=1 s, buffer 8000: 43649 samples, 250.0 ms lost = exactly bufferSize; after the stall error()=NoError, state IdleState, bytesAvailable pinned at 8000. setBufferSize(64000): no loss. Design: overrun is silent, no error(); size the buffer for the worst stall (1-2 s = 32-64 KB) or read from a thread that never blocks.

7 Is error() synchronous. Null QAudioDevice(): start() returned a QIODevice in 37 ms, NoError/IdleState at every check, and it captured real audio (30338 B in 1 s, rms 3.7e-3): Qt silently fell back to the default input. Real device: NoError/IdleState, ActiveState once reads begin. Unsupported formats (9 ch, 0 Hz, Unknown, 1 MHz): isFormatSupported False; start() returned None in 0.03 ms; error()=OpenError, StoppedState immediately. Design: format failures are synchronous; a null or missing device never errors, it records from the default mic, so check isNull / membership in audioInputs() before start().

8 QAudioSource in a QThread (worker QObject moved to the thread). Case A, slot blocks in time.sleep(2) after start(): readyRead fired 0 times during the block; after it, 8000 of 64000 B (1.75 s lost, NoError, IdleState); capture then resumed on its own, 101 readyRead / 31680 B in the next second, all on the worker thread. Case B, thread runs exec() with no block: 197 readyRead, 62978 B in 2 s, ~320 B every ~10 ms, all on the worker thread. Design: readyRead is delivered through the owning thread's event loop and the buffer is bufferSize deep, so the audio owner must spin its event loop and never block. Resolves ledger disagreement 2: a blocking run() gets nothing; the capture worker is event-driven.


THREAD AND GUI SPIKES -- measured, Windows 11 10.0.26300, PySide6 6.11.1, display scale 175%. Scripts under scratchpad/spikes2/.

1 queryKeyboardModifiers from a worker thread, Shift held via keybd_event: returns ShiftModifier from a plain thread and from the GUI thread; the cached keyboardModifiers() returns NoModifier because no key event reached a Qt window. Design: queryKeyboardModifiers() is a live read, correct from any thread; keyboardModifiers() is unusable for a hotkey daemon.

2 QClipboard from a worker thread. Main blocked in join/wait: both a threading.Thread and a QThread DEADLOCK inside setText()/text(). Main pumping exec(): setText from a worker returns with no exception, a qWarning "OleSetClipboard: CoInitialize has not been called", and the text is NOT set; text() reads the main thread's value; when the worker called setText right after main had set the clipboard, both then read empty, 3 of 3 runs: the failed call WIPED the clipboard. pythoncom.CoInitialize() in the worker changes nothing. Design: clipboard writes must be marshaled to the GUI thread; off-thread writes fail silently at best, deadlock or wipe at worst. Closes ledger disagreement 3.

3 Exceptions in QThread.run(). RuntimeError: sys.excepthook IS called, the thread finishes, the process survives, exit 0. SystemExit(1): no hook is called, the process does NOT exit, the thread never ends (isRunning True at 4.65 s; it sits in threading._shutdown blocking on the main thread); a later sys.exit(0) from main dies with 0xC0000409. Design: a worker that wants the process to stop must signal the GUI thread to quit; SystemExit off-thread hangs the thread and turns shutdown into a crash. Closes ledger disagreement 1.

4 Hotkey foreground. Notepad focused; WM_HOTKEY arrived at the native filter as a thread message (hwnd 0). show()+raise_()+activateWindow(): GetForegroundWindow == winId after 500 ms, isActiveWindow True. Same with win32gui.SetForegroundWindow. Design: on WM_HOTKEY the receiving process has foreground rights; activateWindow() is enough, no AttachThreadInput trick. hotkey.py's SetForegroundWindow can go.

5 DPI. GetDpiForSystem 168 = 1.75. SetProcessDpiAwareness(1) before QApplication: awareness stays 1 (system-aware, Qt cannot raise it); dpr 1.75, logical 96, screen 2194x1234, window frame 400x330. Qt default: awareness becomes 2 (per-monitor); every Qt number identical. Design: the SetProcessDpiAwareness line in vdict_tray.py buys nothing on one screen and pins the process to system-aware, silently blocking per-monitor mode. Delete it; leave DPI to Qt. Mixed-scale monitors remain a first-launch check on the son's laptop.

6 restoreGeometry off-screen. move(20000,20000) was clamped by Windows to (18731,18724); the saved blob restored to (1793,885), fully inside availableGeometry, restoreGeometry returned True. Design: Qt pulls an off-screen saved position back onto the primary screen; no hand-written clamp. Closes ledger disagreement 4 and the UNVERIFIED in the Pos and _clamp_to_desktop rows.

7 QPlainTextEdit read-only context menu: no selection: Copy disabled, Select All enabled, nothing else present. With a selection: both enabled. Design: the stock read-only menu already matches today's right-click menu plus Select All; no custom menu.

8 QComboBox().model(): QStandardItemModel, isinstance True, parent is the combo. Using the model after the combo is garbage-collected raises "Internal C++ object already deleted". Design: usable for per-item enabling; keep the combo referenced.

9 Tray icon: QIcon(vdict.ico) availableSizes 16, 32, 48, 256; actualSize(16)=16x16, (32)=32x32. QSystemTrayIcon geometry after show: 32x48 logical at dpr 1.75. Design: the .ico's frames serve the tray at 175%; no PNG set.

10 Minimize then hide. hide() called directly inside changeEvent is IGNORED: 1 s later the window is visible, iconic, a taskbar entry. hide() deferred via QTimer.singleShot(0): hidden, IsWindowVisible False, windowState still WindowMinimized. Design: minimize-to-tray defers hide() one event-loop turn, and restore must clear the minimized state, not just show().

TOOLKIT GAPS

Hand-rolled because a library did not do it. One line each: what was
hand-rolled, which library gap forced it, and why a package was not used.
Read when a plan is converted to a build sheet.

  - hotkey.py register/unregister/_claim/_release: Qt has no system-wide
    hotkey API (grepped every PySide6 stub); RegisterHotKey via pywin32,
    received through QAbstractNativeEventFilter. No package wraps it better
    than the four win32 calls.
  - hotkey_capture.py _state_to_mods: Qt.KeyboardModifier has no map to
    RegisterHotKey's MOD_* flags; six lines, no package.
  - app.py _raise_window: whether QWidget.activateWindow() is granted the
    foreground after WM_HOTKEY is unverified; SetForegroundWindow stays
    until the spike says otherwise.
  - settings.py _has_cuda and stt.py PATH prepend: ctranslate2's own
    add_dll_directory covers ROCm only, not the nvidia pip wheels; the
    PATH prepend is the fix, done ONCE at import by the module that loads
    ctranslate2 first, not twice.
  - config.py _delete_at_path: pydantic validates whole or fails whole; no
    per-field fallback to default exists (model_validate takes no such
    option), so the per-field repair is hand-rolled.
