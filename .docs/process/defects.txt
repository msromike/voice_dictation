D7. vdict_tray.py crams tray icon, Settings dialog, console window and hotkey
    registration into one file. Surfaced while counting config-model-build's
    call sites -- one file absorbing the whole blast radius of an unrelated
    refactor is the tell. Not a behavior bug, a module-boundary one. Formal
    split build sheet AFTER config-model-build and build-v2 both land --
    not before, not folded into either.

D9. load_settings() is called from SIX places in vdict_tray.py
    (_log_session_block, open_settings, _build_hotkey_row, _rebind_on_close,
    _save_console_state, run), each an independent fresh read of config.json.
    No shared in-memory config anywhere in the class. Same shotgun-surgery
    shape as the ptt/stt alias finding in config-model-build -- one thing,
    touched independently in six places.

    Only run() captures and reports reset_reason. The other five discard it
    with `config, _ = load_settings()` -- a corrupt config.json reset at any
    of those five happens completely silently.

    CAUGHT LIVE: corrupted config.json while the app was running, then
    exited. _save_console_state's load_settings() call caught the corruption,
    reset the file, and discarded reset_reason -- silently. The NEXT session's
    boot found an already-valid file and had nothing to report, even though a
    reset genuinely happened one session earlier.

    NOT a simple fix: _rebind_on_close's fresh read is deliberate, not
    redundant -- "Settings is gone -- put the hotkey back from whatever is on
    disk now. Saved or abandoned, disk already holds the right answer." A
    single shared self.config would need to preserve that discard-on-close
    behavior specially, not just get read once and trusted.

    TWO CANDIDATE FIXES, not decided: (a) small -- report reset_reason at all
    six sites, no architecture change. (b) bigger -- one shared self.config,
    handling the discard-on-close case on purpose. (b) is adjacent to D7 --
    same file, same "too much happening in one place" root cause.

D15. config.json's reads and writes have no explicit encoding -- five sites
     in vdict_tray.py (load_settings()'s three open(CONFIG_PATH, "w") calls,
     its CONFIG_PATH.read_text(), and save_settings()'s
     open(CONFIG_PATH, "w")), all relying on Windows' platform-default
     locale encoding. Inconsistent with every other file operation in the
     app, which are all explicit encoding="utf-8" (vocabulary.txt, the
     error log, the Save As log export). Only matters if a config value
     itself contains non-ASCII text (a microphone device name with unusual
     characters, for instance) -- found while confirming the transcript
     pipeline itself is UTF-8-safe end-to-end (it is; this is the one gap).
