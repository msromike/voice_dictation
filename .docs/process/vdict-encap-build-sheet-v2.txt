VOICE DICTATION - BUILD SHEET: SPLIT vdict_tray.py INTO vdict/tray/ -- V2

Design lives in vdict-encap-plan.txt. This sheet does not repeat it -- read
SKELETON and DECISIONS there before starting, and treat the plan as the
authority if the two ever disagree.

Done = vdict_tray.py holds only the entry point, every piece named in the
plan's SKELETON is its own module, and the app behaves as it does today.

ORDERING RULE: riskiest first, EXCEPT where a dependency forces otherwise.
The only thing here that can genuinely fail is the wiring rule holding
against the measured cycle (console -> faults -> settings ->
daemon-subprocess -> console), and that is exercised at step 4. Everything
before it is there because the console cannot be extracted without it.

A leaf that a later step consumes must be extracted BEFORE that step, not
after. Otherwise the consumer has to import the entry file that imports it
back, which is the cycle the wiring rule exists to prevent. That is why
const, session, ptt_capture and hotkey_capture come before faults and
settings rather than at the end -- V1 had them last and was wrong.

EVERY STEP IS A VERTICAL SLICE: create the module, move the code, rewire
every caller, delete the original -- all inside the step. Never move in one
step and rewire in the next. Full sweep at the end.

"APP" MEANS THE ORCHESTRATOR, NOT app.py. Steps below say app registers,
app hands in, app assembles. Until step 12, that is the VoiceDictationTray
class still living in vdict_tray.py -- it is already the thing that owns
the Tk root and wires the pieces together. Step 12 relocates it to
vdict/tray/app.py without changing what it does. Do not create app.py
early; the ordering depends on the extractions happening out of the class
while it stays put.

VERIFYING AND COMMITTING. Every step ends with a launch, exercising only
the gesture that step's code owns. Mike runs the app -- never launch
vdict_tray.py; report what is ready and what to look for, then wait.
Commits execute ON COMMAND only: finish the step, report, and wait for Mike
to say "commit per protocol", which runs the commit-per-protocol skill.
Never commit autonomously, however routine a step looks.

GATES. This sheet predates .docs/templates/build-sheet.txt. Steps 1 and 2
carry the blocks; each later step gets them when it starts.
  ENTRY  Every box in the prior step is [x]. Stop and close it if not.
  EXIT   Mark this step's action boxes [x] -- here, never at the next ENTRY,
         since a gate that marks its own boxes cannot audit them. Then
         ruff, pyright, check_docstrings at zero, reported separately from
         the launch gesture. The gesture box is marked only after Mike
         confirms, so ticked action boxes over an open gesture box reads as
         "code in, unverified, waiting on him".
DOC POINTERS. A step that moves a symbol fixes every forward doc naming its
old home, in that step. Deferring them all to 13 means a sheet abandoned at
step 9 ships nine steps of stale pointers -- the same abandonment-safety
argument that puts a launch at every step boundary. 13b verifies, it does not
repair.
vulture is NOT a step gate -- unreferenced is the normal transient state
while code is moving, and its findings that stand red on purpose are
decisions, not failures. It runs at step 13 and at commit.
The next sheet gets written from the template instead of retrofitted.

STEP 3  geometry.py -- THE REGISTRY
==============================================================================
This is the one step that changes behavior rather than relocating it. See
the plan's WINDOW GEOMETRY.

ENTRY
  [x] Every box in STEP 2 is [x]. Stop and close it if not.

  [x] 3a  Create vdict/tray/geometry.py: manage(), save_all(config),
          set_flush(), plus _clamp_to_desktop and _geometry_parts moved
          verbatim and now internal to the module.
  [x] 3b  track() takes the shape it is persisting, not just a field name.
          The console stores a full "WxH+X+Y" string into
          ui.console_geometry; Settings stores a Pos(x, y) into
          ui.settings_pos. Those are different pydantic types and
          UiConfig validates on assignment, so a registry that caches one
          shape and writes it to both fields raises ValidationError on the
          first save. Cache the raw geometry string either way and convert
          at write time, per tracked field.
          A cached string that does not parse leaves the config field as
          it is rather than writing None -- _geometry_parts returns None
          before a window is placed, and save_all has no live window to
          fall back on the way _get_pos falls back to winfo_x/winfo_y.
          Writing None on a failed parse silently discards the last known
          good position.
  [x] 3c  track() caches on <Configure> while the window is in normal
          state. <Destroy> marks the window gone but reads nothing -- the
          cache already holds the last valid value. Without retaining the
          cache past teardown, Settings closes before exit and
          settings_pos is silently dropped.
          Whether Tk reports degenerate geometry (1x1+0+0) during teardown
          is UNVERIFIED. It is not in the UNVERIFIED block because nothing
          here depends on the answer -- this design never reads geometry
          at <Destroy> either way.
  [x] 3d  save_all(config) writes every cached entry. Called at exit, at
          hide, and when a tracked window is destroyed.
          Exit-and-hide alone shipped and failed: those are the CONSOLE's
          trigger points. Settings restores from disk on every open, so a
          position living only in the cache was invisible to the very next
          open and Settings reopened where it used to be. The destroy flush
          is registry-level -- one set_flush(fn) app registers once -- never
          a save call put back onto Settings. See the plan's WINDOW GEOMETRY.
  [x] 3e  Console window and Settings both register through track().
          _remember_geometry and Settings' two _get_pos writes go away.
          _save_console_state goes away whole, not half. app owns one
          save-state function that calls save_all(config), writes
          console_font_size, and saves once; console's hide calls it and
          _run_shutdown_steps calls the same one. Keeping the method
          alive with only its font half leaves exit doing two independent
          read-modify-write cycles against config.json, ordered by
          nothing.
  [x] 3f  REVERSED -- the registry owns restore too. See the plan's THE
          REGISTRY OWNS RESTORE TOO. Save-only shipped, broke Settings, and
          its fix broke the console; both failures were the gap between the
          cache and the disk. manage() closes it. The text below is the
          superseded decision, kept only so the reversal is legible.
          The registry saves; it does not restore. Both restore sites
          stay hand-rolled -- run() for the console, open_settings for
          Settings -- each reading its own config field and clamping
          itself, now importing _clamp_to_desktop and _geometry_parts
          from geometry.py. A new window costs one track() call to
          persist and a hand-written restore to come back.

POTENTIAL DEFECT -- A CAPTURE OUTLIVING THE DIALOG THAT OWNS IT
Found while step 4's gesture was running, not caused by it. Closing Settings
during a PTT rebind appears to leave the capture listening: the dialog was
closed mid-capture and a later "e" pressed elsewhere showed up on the bind
button. Symptom, not diagnosis. Nothing persisted -- ptt.button stayed
key:f13 throughout.

The trigger was environmental: G HUB was not running, so F13 reached nothing
and the capture was never handed a key. That is what exposes it -- a capture
that is opened and then abandoned with no keypress. The defect is that it
survives the window closing at all.

_PTTCapture.start already binds <Destroy> on tk_btn to _unhook, with a
comment naming this exact failure, so either that guard does not fire or the
leak is elsewhere. The architectural smell either way: pynput's hooks are
process-wide, and nothing in the dialog's close path cancels a capture in
flight -- it finds out its owner is gone second-hand, through widget
teardown.

  [x] 7-pre  RESULT: the guard is viable. Build as specified, no explicit
          cancel() needed. <Destroy> fires for a button nested inside a
          Frame -- the real layout -- and again for a direct child. _unhook
          sets a flag and calls listener.stop(), touching no widget, which
          matters because the test also showed a <Destroy> handler CANNOT
          touch its widget: TclError, invalid command name, already torn
          down. end() does touch tk_btn, but only ever behind its
          if self.done guard, which _unhook sets first.
          So the leak is NOT the guard failing to fire. Remaining suspects,
          both local: whether _unhook stops both listeners in the real
          case, and whether _rebind_key can start a second capture over a
          live one -- it constructs a fresh _PTTCapture per click with no
          check for one already running.

          CLOSED at step 13. Both suspects cleared, no defect in current
          code, nothing to fix. Neither was reachable:

          Suspect one, stop(). pynput's AbstractListener.stop() documents
          "when this method returns, no more events will be delivered", and
          guards its body with if self._running -- synchronous, and safe to
          call twice, which _unhook does when <Destroy> and end() both run.

          Suspect two, double capture. start()'s second line disables
          tk_btn, and only end() re-enables it. A disabled Tk button does
          not invoke its command, so the button needed to start a second
          capture is dead until the first one finishes.

          Watched, not just traced: a headless test drove the real
          _build_ptt_row and the real PTTCapture with pynput faked into
          sys.modules, so no global hook was installed. Capture goes live,
          <Destroy> sets done and stops both listeners, and a late end() --
          the deferred call from _on_key landing after teardown -- is a
          no-op rather than a TclError. Four assertions, all passed.

          What the original report actually was: the capture stayed open
          because F13 never arrived (G HUB was not loaded), which is
          correct behaviour -- a capture waits for a key. Settings was
          never destroyed, so a later keypress was captured normally.

          ESCAPE ASYMMETRY, found here, not a defect. Escape during a
          hotkey capture cancels and leaves Settings open; Escape during a
          PTT capture cancels and also closes Settings. Both preserve the
          previous binding. The cause is that hotkey_capture binds Tk and
          returns "break", while ptt_capture is a pynput OS hook that has
          no way to break a Tk event, so settings_win's own Escape binding
          fires too. The comment on that binding claimed a capture always
          swallows Escape first, which held only for the hotkey case; it
          now names both.

  Run this BEFORE moving any code, because the answer changes
          what ptt_capture.py should look like. Ten lines, headless, no
          pynput and no global hooks: a Toplevel, a button nested inside a
          Frame the way the real one sits in main_frame, a <Destroy>
          binding, then destroy() the Toplevel.
          Fires -> the guard works and the leak is elsewhere; look at
          whether _unhook actually stops both listeners, and whether a
          second capture can be started over a live one. Local fix.
          Does not fire -> the guard was never viable. ptt_capture.py gets
          an explicit cancel(), and step 9 has Settings call it on close,
          rather than shipping the fragile version into a new file.
          Do NOT reproduce the leak with real pynput hooks -- that means
          installing global keyboard capture to watch it misbehave, and
          this test already picks the fix.
          _capture_hotkey is a different shape and probably NOT affected:
          it binds <KeyPress> on the button, a Tk binding that dies with
          the widget, and installs no global hook. Confirm, do not assume.
