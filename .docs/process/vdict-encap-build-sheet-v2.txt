VOICE DICTATION - BUILD SHEET: SPLIT vdict_tray.py (P4) -- V2

Design lives in vdict-encap-plan.txt. This sheet does not repeat it -- read
SKELETON and DECISIONS there before starting, and treat the plan as the
authority if the two ever disagree.

Done = vdict_tray.py holds only the entry point, every piece named in the
plan's SKELETON is its own module, and the app behaves as it does today.

ORDERING RULE: riskiest first, EXCEPT where a dependency forces otherwise.
The only thing here that can genuinely fail is the wiring rule holding
against the measured cycle (console -> faults -> settings ->
daemon-subprocess -> console), and that is exercised at step 4. Everything
before it is there because the console cannot be extracted without it.

A leaf that a later step consumes must be extracted BEFORE that step, not
after. Otherwise the consumer has to import the entry file that imports it
back, which is the cycle the wiring rule exists to prevent. That is why
const, session, ptt_capture and hotkey_capture come before faults and
settings rather than at the end -- V1 had them last and was wrong.

EVERY STEP IS A VERTICAL SLICE: create the module, move the code, rewire
every caller, delete the original -- all inside the step. Never move in one
step and rewire in the next. Full sweep at the end.

"APP" MEANS THE ORCHESTRATOR, NOT app.py. Steps below say app registers,
app hands in, app assembles. Until step 12, that is the VoiceDictationTray
class still living in vdict_tray.py -- it is already the thing that owns
the Tk root and wires the pieces together. Step 12 relocates it to
vdict/tray/app.py without changing what it does. Do not create app.py
early; the ordering depends on the extractions happening out of the class
while it stays put.

VERIFYING AND COMMITTING. Every step ends with a launch, exercising only
the gesture that step's code owns. Mike runs the app -- never launch
vdict_tray.py; report what is ready and what to look for, then wait.
Every step ends with a commit too, but commits execute ON COMMAND only:
finish the step, report, and wait for Mike to say "commit per protocol",
which runs the commit-per-protocol skill. Never commit autonomously,
however routine a step looks.

STEP 1  log.py -- THE LEAF EVERYTHING REPORTS THROUGH
==============================================================================
Nothing else can move first: every module extracted later calls log() or
error_log(), and both live on the tray object today.

  [ ] 1a  Create vdict/tray/log.py. Owns the output queue outright.
          log(category, text) enqueues. error_log(context, text) writes
          disk via common.output.write_error_log FIRST, then calls an
          installed screen-writer if one exists -- synchronously, never
          through the queue. install_screen(fn) registers that writer.
          The disk write happens whether or not a writer is installed.
  [ ] 1b  vdict_tray.py installs a screen-writer that inserts into
          self.text, replacing the body of the old error_log method.
  [ ] 1c  Rewire every self.log() and self.error_log() call site to the
          module functions, and delete both methods. _PTTCapture's
          self.tray.log/self.tray.error_log calls go too.
  [ ] 1d  The drain reads log.py's queue instead of self.output_queue.
  [ ] 1e  _read_output is the other producer and is neither a log() nor an
          error_log() call site -- it puts on self.output_queue directly.
          Rewire it too. Missed, it feeds an orphan queue and every line
          of daemon output disappears with no exception.

VERIFY: launch. Session block prints with correct colors and markers.
Dictate once -- the session block reaches the queue through log() and
prints even with _read_output left behind, so only real daemon output
exercises that producer. Trigger an error_log path -- rebind PTT and press
a key pynput cannot name, or force model-fault -- and confirm the error log
file gets the entry AND the console shows it.

==============================================================================
STEP 3  geometry.py -- THE REGISTRY
==============================================================================
This is the one step that changes behavior rather than relocating it. See
the plan's WINDOW GEOMETRY.

  [ ] 3a  Create vdict/tray/geometry.py: track(), save_all(config), plus
          _clamp_to_desktop and _geometry_parts moved verbatim.
  [ ] 3b  track() takes the shape it is persisting, not just a field name.
          The console stores a full "WxH+X+Y" string into
          ui.console_geometry; Settings stores a Pos(x, y) into
          ui.settings_pos. Those are different pydantic types and
          UiConfig validates on assignment, so a registry that caches one
          shape and writes it to both fields raises ValidationError on the
          first save. Cache the raw geometry string either way and convert
          at write time, per tracked field.
          A cached string that does not parse leaves the config field as
          it is rather than writing None -- _geometry_parts returns None
          before a window is placed, and save_all has no live window to
          fall back on the way _get_pos falls back to winfo_x/winfo_y.
          Writing None on a failed parse silently discards the last known
          good position.
  [ ] 3c  track() caches on <Configure> while the window is in normal
          state. <Destroy> marks the window gone but reads nothing -- the
          cache already holds the last valid value. Without retaining the
          cache past teardown, Settings closes before exit and
          settings_pos is silently dropped.
          Whether Tk reports degenerate geometry (1x1+0+0) during teardown
          is UNVERIFIED. It is not in the UNVERIFIED block because nothing
          here depends on the answer -- this design never reads geometry
          at <Destroy> either way.
  [ ] 3d  save_all(config) writes every cached entry. Called at exit and at
          hide -- both of today's trigger points, not exit only.
  [ ] 3e  Console window and Settings both register through track().
          _remember_geometry and Settings' two _get_pos writes go away.
          _save_console_state goes away whole, not half. app owns one
          save-state function that calls save_all(config), writes
          console_font_size, and saves once; console's hide calls it and
          _run_shutdown_steps calls the same one. Keeping the method
          alive with only its font half leaves exit doing two independent
          read-modify-write cycles against config.json, ordered by
          nothing.
  [ ] 3f  The registry saves; it does not restore. Both restore sites
          stay hand-rolled -- run() for the console, open_settings for
          Settings -- each reading its own config field and clamping
          itself, now importing _clamp_to_desktop and _geometry_parts
          from geometry.py. A new window costs one track() call to
          persist and a hand-written restore to come back.

VERIFY: launch. Move and resize the console, hide to tray, restore -- size
and position kept. Move Settings, close it, reopen -- position kept. Exit
and relaunch -- both kept. Then confirm a window closed but not exited
still persists: move Settings, close it, exit without reopening, relaunch.

STEP 4  console.py -- THE CYCLE STEP
==============================================================================
The risk this whole ordering exists for. console must NOT import faults.
app registers fault handlers into the console's dispatch, so the measured
cycle has no edge to close on.

  [ ] 4a  Create vdict/tray/console.py. Owns the text widget, color tags,
          context menu, zoom and font sizing, select/copy/copy-all/clear,
          save-log-as, the queue drain and category dispatch, the loading
          animation, and hide/unmap. Installs log.py's screen-writer.
  [ ] 4b  Constructor takes the Tk root, the tray icon (for toasts), a
          handler map for box-category dispatch, and a save-state callable
          it invokes on hide. At this step app populates the handler map
          with the fault methods still living in the tray class -- they
          move out in step 8.
  [ ] 4c  Expose set_loading(bool). start_vdict assigns is_loading_model
          directly today; step 10 forbids that, so the console needs a way
          to be told from outside before daemon_proc is extracted.
  [ ] 4d  transcript_only_mode, _swallow_set, COLOR_TAGS, CONSOLE_FONT_*,
          TRANSCRIPT_LOG_ENABLED, TRANSCRIPT_LOG_PATH and the transcript
          logger all move with it. Missing either TRANSCRIPT_LOG_ name
          leaves transcript_log() raising NameError on the first
          transcript.
  [ ] 4e  Delete every console method from the tray class.

VERIFY: launch. Console shows output with correct colors. Ctrl+scroll and
Ctrl+0 zoom. Copy, Select All, Copy All, Clear. Save As writes a file. Hide
to tray and restore. Dictate once and confirm the transcript reaches
transcript_log.txt. Force model-fault -- the modal must still appear, which
is what proves the handler map works. Minimize to confirm unmap still hides
rather than iconifies.

STEP 9  settings.py
==============================================================================
The most entangled piece. settings_win is read from outside by the fault
modals and by the bare-key confirmation.

  [ ] 9a  Create vdict/tray/settings.py: the window builder, all five row
          builders, the hotkey row, on_close, and _rebind_on_close.
  [ ] 9b  The dialog does NOT own the save flow. It reads its own widgets
          into the config object exactly as save_and_restart does today,
          then calls an on_save(config) callable and stops. Writing to
          disk, destroying the window, and restarting the daemon all move
          to app.py. A dialog that destroys itself and restarts a
          subprocess is a second orchestrator, which the wiring rule
          forbids -- and input-device-plan needs the window to stay open
          when a device fails to open, which is impossible if the dialog
          tears itself down unconditionally.
  [ ] 9c  Receives the Tk root, on_save, and the hotkey re-register
          callable. It does not import daemon_proc.
  [ ] 9d  Exposes the live window so faults.py can parent to it, through
          whatever app hands faults in 8a rather than a direct import.
  [ ] 9e  sounddevice stays imported inside _build_microphone_row and
          ctranslate2 inside _has_cuda. Hoisting either to module level
          drags heavy dependencies into tray startup.
  [ ] 9f  The version label reads __version__ from vdict/__init__.py,
          which already holds it. Not from vdict_tray.py -- that copy dies
          at 12b, and reaching for it makes settings.py import the entry
          file that imports settings.py back.

VERIFY: launch. Open Settings from the tray menu and from File. Change each
control and Save -- values persist, the window closes, and the daemon
restarts. Escape closes without saving. Close and reopen from the fault
path. Rebind the output-window hotkey, close Settings, confirm the new
hotkey works -- that is _rebind_on_close.


==============================================================================
STEP 10  daemon_proc.py
==============================================================================
Core-arch deletes this module whole. Keep its surface minimal; do not give
it a polished API it will never need.

  [ ] 10a Create vdict/tray/daemon_proc.py: start, stop, restart, the
          stdout reader thread, and the exit poll. _exit_reported moves
          with it; _fault_shown is set through the callable from 8c.
  [ ] 10b Fix the path math. start_vdict uses Path(__file__).parent for
          both the vdict_daemon.py path and cwd. From vdict/tray/ that
          resolves to vdict/tray/vdict_daemon.py -- Popen raises
          FileNotFoundError. Needs THREE .parent steps.
  [ ] 10c It must not set console state directly. Today start_vdict assigns
          is_loading_model -- that becomes the console's set_loading from
          4c, handed in by app. This is the edge that closed the measured
          cycle.
  [ ] 10d The exit poll drains a second time, after joining the reader
          thread, so the daemon's last lines land ahead of the exit line.
          That is a second console edge alongside 10c: daemon_proc takes a
          drain callable from app. Reaching for the console directly is
          the cycle; dropping the call reorders the exit line ahead of the
          traceback that explains it.
  [ ] 10e app owns the 100ms tick: drain the console, then poll the
          subprocess for exit, then reschedule. Core-arch later deletes the
          second call and the tick becomes console-only.

VERIFY: launch. Session block prints with the daemon PID. Save & Restart in
Settings swaps the daemon and reprints the block. Kill vdict_daemon.py from
Task Manager -- the console reports the exit code once, not repeatedly,
and anything the daemon had already written appears above that line rather
than after it. No config-forced gesture reaches 10d's ordering on its own:
both box-category faults set the fault flag, which suppresses the exit line
entirely, and a Task Manager kill usually leaves nothing in flight. Read
10d's wiring instead of trying to trigger it.
