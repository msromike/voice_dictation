  [x] scale(N) returns values identical to int(N * self.dpi_scale).
      Checked directly against the formula for every literal the file
      uses (5, 10, 15, 20, 60, 360, 600, 900) across factors 1.0 through
      3.0 -- no mismatches. This rules out an int()-vs-round() slip,
      float drift, and a cache that ignores what it was set to. It cannot
      rule out more, because _factor() and the __init__ read it replaces
      are the same expression with the same fallback.
  [x] The lazy read cannot fire before SetProcessDpiAwareness. First
      scale() call is __init__'s main_w/main_h line, which is the same
      moment the old code read GetDpiForSystem. Confirmed by launch.

THIS MACHINE IS 96 DPI -- factor 1.0, so int(N * 1.0) == N and the whole
scaling path is an identity function. Wrong-literal errors (scale(15)
where scale(20) belongs) still show, because 15 and 20 differ. Errors in
the factor itself cannot show at all. Nothing observed on this display is
evidence about behavior at any other DPI -- that is a separate spike, on
the single-file app, before P4 splits it.

ALREADY WEIGHED
  - scale() caches the DPI on first call. Today's value is read once in
    __init__ and never refreshed; caching preserves that exactly. Not
    caching would silently change behavior on a monitor switch.
  - dpi.py owns the DPI read. VoiceDictationTray keeps no dpi_scale
    attribute once step 3 lands.
  - Fonts never go through scale(). CONSOLE_FONT_* are point sizes and Tk
    already scales points by DPI. This goes in dpi.py as a comment, at the
    point someone would otherwise be tempted.
