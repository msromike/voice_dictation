B3. TONE VOLUME CONTROL -- REFINEMENT
==============================================================================
Sequenced after core-arch's build (not its plan -- LIVE-READ SETTINGS
already names play_tone() as this exact pattern; the mechanism just has
to exist).

THE PROBLEM
Tone volume is hardcoded. vdict.py:
    generate_tone(TONE_START, freq=783.99, duration_ms=80, volume=0.22275)
    generate_tone(TONE_STOP,  freq=523.25, duration_ms=90, volume=0.18225)
Ear-tuned constants from one machine, imposed on every user.

WHY NOT JUST USE THE WINDOWS VOLUME MIXER
The daemon is pythonw.exe, the tray is ALSO pythonw.exe, and the venv
redirector stub means each appears TWICE. The mixer shows up to four
identical "pythonw" entries with no way to tell them apart.

THE WORK
  - The Config model gains two volumes, 0-100, defaults matching the
    current 0.22275 and 0.18225 so existing behaviour is unchanged.
  - Settings dialog gains two sliders, start tone and stop tone. Zero is off,
    which is how someone silences one and keeps the other.
  - play_tone scales by them.
  - The timeout double-tone is 523.25Hz at 0.18225 -- same frequency and
    volume as the stop tone, and it fires only after a 120s toggle timeout.
    It follows the stop slider. No third control.
  - The two defaults are not equal because equal amplitude at 784Hz reads
    louder than at 523Hz. Do not normalise them.

  Tones are pre-generated WAVs at import; play_tone() already scales the
  in-memory tone data by a volume argument right at the moment it's queued
  for playback -- no regeneration involved, nothing currently passes it a
  real value. The work is reading the two config fields at each
  play_tone() call site through core-arch's shared live Config object.
  A standalone per-call config.json re-read is NOT a substitute:
  save_settings() writes non-atomically (truncate then write), so a read
  landing mid-write raises.

  Move it to vdict/tones.py -- generation, play_tone, the file constants.
  ~80 of vdict.py's 222 lines, and importing vdict.py currently writes three
  WAVs to temp. Carry this comment with it:
      # winsound refuses SND_MEMORY with SND_ASYNC. Async playback needs a file.
  Without it someone rewrites the temp files into memory, and the only
  in-memory path is synchronous -- an 80ms block on the dictation loop.
  The three WAVs are never cleaned up.

B8. WINDOW CONTROLS -- MINIMIZE, X AND EXIT SHOULD DIFFER -- REFINEMENT
==============================================================================
The confirm dialog needs icon=WARNING.

THE PROBLEM
X kills the daemon. app.py maps WM_DELETE_WINDOW to exit_app, so closing
the output window stops dictation. The confirm dialog exists to guard a
behavior users do not expect; conventional actions do not need one.

ALREADY TRIED AND REJECTED
X -> tray while minimize -> tray. That was the pre-release behavior. Two
controls, one outcome. Do not go back to it.

THE ARRANGEMENT
  Minimize -> taskbar, native behavior. Not configurable.
  X        -> hide to tray. Default.
           -> confirm dialog (icon=WARNING), then exit, when
              ui.close_button_exits is on.
  Exit     -> tray menu and File > Exit, both already exist, no dialog --
              deliberate, conventional actions, nothing to guard.

THE WORK
  - Remove the <Unmap> binding and _on_unmap (app.py) so minimize
    is native.
  - Repoint WM_DELETE_WINDOW from exit_app to hide_window, or to a
    confirm-then-exit path when ui.close_button_exits is set.
  - The Config model gains ui.close_button_exits, default False.
  - Settings gains "Close button exits the app". The label names X, not the
    minimize button.
  - exit_app needs to know which entry point called it. The confirm dialog,
    icon=WARNING, fires only on the X-triggered path -- that's the one case
    where a conventional-feeling gesture still has an easy-to-forget
    consequence (the setting was flipped once, muscle memory doesn't know
    it's on). Tray menu Exit and File > Exit call the same underlying quit
    logic without the dialog.

exit_app's entry-point-aware gating sits on app's _force_quit and
_run_shutdown_steps, whose daemon-stopping half disappears rather than
relocating once the subprocess merges away -- this logic gets re-pointed
at core-arch's shutdown sequence then, not rebuilt.

app's _save_state already runs inside hide_window. Geometry tracking is bound
to <Configure> inside geometry.manage() and is unaffected.

Re-verify the hotkey raises a taskbar-minimized output window.

SIDE EFFECT, WANTED
An open output window means a taskbar button exists, which answers "I lost the
tray icon". The app only disappears when the user asks it to.

B14. LOG TRANSCRIPTS TO A FILE -- REFINEMENT
==============================================================================
A View-menu toggle (working title: "Log Transcripts") exposing user
control over transcript logging -- useful on its own (a plain record of
what was dictated), and separately feeds the real corpus B13 and B21 are
both waiting on before their own ROI can be judged. Not gated on either
shipping; the toggle has value independent of what, if anything, ends up
built on top of the data.

Mechanism built 2026-07-31 as part of the unified output-logging
redesign -- transcript.write(text), a dedicated logger with one RotatingFileHandler
(maxBytes=100MB, backupCount=5, encoding="utf-8"), LOG_DIR /
"transcript_log.txt". Gated on vdict/tray/transcript.py's ENABLED (a module
constant, not a Settings checkbox) -- what's left here is only the
View-menu toggle itself, still not built.

V1.2 TUNING WORKFLOW, only if B13's shipped defaults prove insufficient:
a separate, explicit tuning session -- PTT disabled, Whisper unloaded, the
largest local Ollama model that fits loaded in its place. Ollama reads the
B14 transcript corpus, runs it through B13's model, evaluates the output,
and iterates -- a guided, step-by-step interaction is fine, does not need
to be fully autonomous. Human reviews the result (e.g. opens the
transformed text file) before anything is "locked in." Whatever gets
decided is written back as B13's tuning parameters, Ollama unloads,
Whisper reloads, dictation resumes.

Human-in-the-loop review is what makes this trustworthy -- without it,
"tuned" only means "Ollama liked its own output," not "matches what was
actually said."

Two different amounts of work hiding under "write tuning parameters,"
not yet distinguished because B13 has no chosen model yet: adjusting a
handful of hyperparameters/thresholds (Ollama reasoning over candidates,
genuinely tractable) versus actually fine-tuning the small model's
weights (a real training loop with a loss function -- Ollama could help
produce labeled examples for that, but would not run the training itself).

Prototype as a standalone sidecar script first, not in-app. Cheapest way
to prove the risky part (does this actually improve punctuation quality)
without touching the app's menu, process management, or model-
loading code at all. Integrate into the app later only if it earns it --
could just as easily stay a documented external tool in the README.

THIS TOGGLE IS ALSO THE DISCLOSURE CONTROL, which the item was not written
for. transcript_log.txt records every transcript on any machine that runs
the app, with no flag and nothing telling the user it exists. It stays out
of dev-flags.toml -- portable-folder-build-sheet.txt 1f settled that, and
for a reason that still holds: this is an unfinished feature waiting on
Settings, not dev tooling. But that question was "is it a dev flag," never
"should a handed-out copy write it silently." So the toggle carries a second
job, and B5's "what this records" section names the file whether or not the
toggle exists yet.
DECIDE ITS NAME AND PLACE WHEN THE TOGGLE IS BUILT, not before.
userdata/logs holds the app's own diagnostics -- tray_error.log and the
console log -- and this is the only file in there containing the user's own
words. Three ways out: the PRIVATE label like the database and the
recordings folder, a move up out of logs/, or leave it. Unlike those two,
this filename is already self-describing, so the label adds posture and no
information. Cost of a rename, derived by grep, not recalled: two code sites
in vdict/tray/transcript.py and nine doc references.

B6. PTT CYCLE COMPLETION -- CLIPBOARD DELIVERY, GATED RE-TRIGGER, TONE SIGNAL -- NEW FEATURE
==============================================================================

DELIVERY
Clipboard + Ctrl+V stays the delivery model. Delayed rendering replaces the
blind sleep(0.05): register CF_UNICODETEXT with a NULL handle, send Ctrl+V,
wait for WM_RENDERFORMAT. Arrives -> serve real text, restore old clipboard.
Timeout backstop (50ms starting point) -> leave dictated text on clipboard,
no restore, no other recovery mechanism. One signal covers elevated
windows, unfocused cursor, remapped Ctrl+V alike -- no separate elevation
preflight check needed.

FORMAT HANDLING
Swap pyperclip for win32clipboard (already a dependency) in save/restore:
EnumClipboardFormats, GetClipboardData/SetClipboardData per format.
pyperclip only speaks CF_UNICODETEXT -- an image or file selection on the
clipboard is silently destroyed by any dictation today. CF_HDROP (file-drop
lists) doesn't round-trip through generic handle copying -- detect it,
note it, leave it unrestored.

Format order is significant, not just metadata -- EnumClipboardFormats
returns formats in the order they were originally placed, and a target
app that supports more than one picks the first one it recognizes from
that order. Snapshot into a plain ordered list (what EnumClipboardFormats
already hands back) and replay SetClipboardData in that same order on
restore. Free as long as nothing reorders it in between -- no dict keyed
by format ID without preserving insertion order, no sorting, no
set-based dedup.

PTT GATING
press_event/release_event are level flags, nothing consumes them -- a
press-release during a busy transcription/delivery window leaves the same
flag state as if nothing happened, so it's silently dropped. Shared busy
flag: set on cycle start, cleared on this item's completion signal. Clear
also drains both events before the next wait_for_press.

TONES -- four conditions, existing high/low/double-low tones only, no new
asset, no new slider:
  happy path              high, low
  captured not delivered  high, double-low
  nothing captured        high, high+double-low (bundled close, fires
                           where too-short/timeout already fire)
  busy                    double-low alone, no leading high -- fires from
                           the PTT callback the moment busy is checked, not
                           delayed to gate-reopen
play_tone("stop") moves from firing right after capture to firing only once
delivery outcome is known.

FILE-DROP NOTE
One output-window note when CF_HDROP can't be restored. No tone.

RULES THAT ARE EASY TO GET WRONG
  - Do NOT OpenClipboard inside the WM_RENDERFORMAT handler -- the
    requesting app holds it open, the call fails. SetClipboardData alone.
  - WM_RENDERALLFORMATS is the opposite: open the clipboard first.
  - Clipboard calls belong on the window's thread.
  - Target's GetClipboardData blocks while the handler runs -- keep it short.
  - Message-only windows miss broadcast messages; WM_RENDERFORMAT is sent
    directly to the owner, so it arrives.
  - Restoring formats out of order doesn't error -- it just makes a target
    app that supports several of them silently pick a worse one than it
    originally had. No exception to catch, no way to notice but a garbled
    paste later.

THE WORK
  1. Message-only window in the daemon, own thread, GetMessage loop.
  2. OpenClipboard/EmptyClipboard/SetClipboardData(CF_UNICODETEXT, None),
     CloseClipboard, then Ctrl+V.
  3. WM_RENDERFORMAT -> serve text via SetClipboardData. Timeout -> leave
     dictated text, no restore.
  4. win32clipboard replaces pyperclip for save/restore, all formats,
     CF_HDROP excluded.
  5. Shared busy flag; gate PTTListener's next cycle on it; drain both
     events when it clears.
  6. Move play_tone("stop"); add the busy-tone in the PTT click callback.
  7. Delete keyboard.preserve_clipboard from Config and config.json --
     only key in that block, block goes too.
  8. Delete KeyboardInjector's preserve_clipboard arg and call site.

SendInput IS NOT DEAD
Retained as a possible second delivery mode, user-selected, never
automatic. Not scheduled. Original design notes in git history.

TESTING
Not verifiable headlessly. Dictate into VS Code, browser address bar,
terminal, Notepad. Copy text then dictate then paste -- old clipboard
returns. Copy an image, dictate -- image survives. Dictate into an
elevated window and into no-text-field -- same failure tone+note both
times, text stays on clipboard. Dictate long, press PTT again before the
transcript shows -- busy tone, earlier press not absorbed into next cycle.

Build plan first -- encapsulate only what it calls for, as a reusable
API. Cross-check other new-feature plans before sizing that extraction
-- not extra process, avoids rebuilding the same shared piece
narrower-then-wider one feature at a time.

B13. PUNCTUATION-RESTORATION POST-PROCESS -- UPTALK PRODUCES RUN-ONS -- NEW FEATURE
==============================================================================
Whisper's punctuation prediction reads rising terminal intonation (uptalk)
as "not finished" rather than a completed statement, even across genuine
pauses -- produces long run-on transcripts with little or no punctuation
for speakers with this pattern.

Spiked 2026-08-02. Dead end first: rpunct hard-pins pandas==1.2.4 and
torch==1.8.1 -- 2021 exact versions with no Python 3.12 wheels, source
build fails against current Cython. Unmaintained, don't retry it.

Working candidate: oliverguhr/fullstop-punctuation-multilang-large via
the deepmultilingualpunctuation package (pip install, loose version
floors, no pandas dependency -- installs clean). Its own __init__ calls
pipeline(..., grouped_entities=False), removed from current transformers
in favor of aggregation_strategy="none" -- one-line patch needed, rest of
the package's logic is untouched and correct.

Hybrid design, not blanket replacement: stripping and rebuilding every
transcript's punctuation risks losing correct punctuation Whisper already
had, and the restoration model has its own real failure modes (verified:
misplaced question marks, comma-for-period swaps on ambiguous phrasing).
Gate with pysbd (pip install pysbd, pure rule-based, no model) --
segment() the transcript, compute words-per-detected-sentence. Below
threshold, trust Whisper, skip the restoration model entirely. Above
threshold (unpunctuated run-ons collapse to one giant "sentence"), invoke
restoration as a targeted rescue.

Measured, CPU-only: model load ~3s (one-time, startup, same category as
Whisper's own load). Restoration call ~88ms average, paid only on
flagged lines. Threshold tested at 25 words/sentence -- untuned
placeholder, not validated against real run-on examples.

Corpus problem: 52 real transcript_log.txt lines flagged only 1. Not
enough signal to judge true incidence or ROI, and the low count may not
be a sampling artifact -- HOLD mode's continuous physical contact
naturally bookends fragments (release and re-press between thoughts),
which may already prevent the long continuous recordings this problem
needs to occur. Toggle mode doesn't have that discipline. Wait for
transcript_log.txt to accumulate real volume across varied conditions
(mood, fatigue, background noise) before deciding whether to build this
at all -- logging is already flowing, nothing to set up when that time
comes.

Build plan first -- encapsulate only what it calls for, as a reusable
API. Cross-check other new-feature plans before sizing that extraction
-- not extra process, avoids rebuilding the same shared piece
narrower-then-wider one feature at a time.

B22. SETTINGS MODEL DROPDOWN -- DEVICE-AWARE + SHOW-ALL ESCAPE HATCH -- NEW FEATURE
==============================================================================
Two related ways B17's static curated list falls short, both requiring
the dropdown to react rather than just list:

DEVICE-AWARE FILTERING
CPU and GPU users want different curated sets, not one list serving
both. The dropdown's model options should follow whichever compute
device is currently selected in the same dialog.

THE AXIS IS IN QUESTION. Both lists sort by hardware budget. The user is
choosing how good and how fast their English is; VRAM is a filter, not a
choice. Turbo fell into the show-all hatch because it fits no budget tier,
which is the taxonomy failing rather than the model. Reconsider the axis
before rebuilding the dropdown -- a language picker may replace the model
picker for most users.

MODEL LISTS, LOCKED 2026-08-02 (Mike's empirical GPU testing, i7 9th
gen + 3070 Ti, VRAM watched live via a monitoring widget; CPU picked by
compute concept, not measured yet):

GPU -- small.en / medium.en / large-v3. VRAM-budget-vs-accuracy ladder:
three real breakpoints (4GB+/6GB+/8GB+ card tiers), biggest-that-fits is
the strategy since VRAM is the actual gate and GPU has speed headroom to
spare. large-v3-turbo excluded from the curated three -- near-large-v3
accuracy at less compute is a nuanced alternate pick, not a fourth
distinct budget tier; it lives in the show-all escape hatch below.

CPU -- tiny.en / small.en / medium.en. Same family, no distillation, on
purpose: tiny = fastest, even if inaccurate. small = the sweet spot,
slightly slow but usable. medium = the ceiling for CPU on an interactive
press-and-wait dictation tool, even if it turns out not meaningfully
more accurate -- that's for the user to find out themselves. Rejected:
large-v3-turbo -- its speedup only prunes the decoder (32 layers to 4);
the encoder, which is what CPU actually struggles with, stays full
large-size, so it costs about what large-v3 costs on CPU regardless of
RAM headroom. distil-small.en rejected too -- correct on paper (smaller
encoder, genuinely faster), but adds a distillation tradeoff to explain
for marginal gain over the plain three; not worth the complexity here.
Actual per-tier speed on real hardware is unverified -- confirm when
this gets built, adjust the ladder if reality disagrees.

ENGLISH-ONLY VARIANTS, LOCKED 2026-08-02: every size above uses its
.en variant, not the multilingual one -- app isn't localized, Whisper's
.en models are smaller, faster, AND slightly more accurate on English
audio than their multilingual counterpart of the same size, no tradeoff
either direction. large-v3 is the one forced exception: OpenAI only
ever trained .en variants for tiny/base/small/medium -- large-tier
models (including large-v3-turbo, in the show-all list) are
multilingual-only, no .en version exists to switch to.

CUDA detection already exists -- settings._has_cuda() (Compute
Device section) already probes and disables the GPU option when no CUDA
device is found. Reuse it, don't reinvent the probe.

SHOW-ALL ESCAPE HATCH
Neither curated set exposes turbo variants outside their bucket, older
large versions, or the rest of the distil-* family. An "advanced" or

Both likely share one population function, called with a different

B21. PHONETIC VOCABULARY CORRECTION -- HOMOPHONE SPELLING DRIFT -- NEW FEATURE
==============================================================================
Whisper sometimes picks the wrong spelling of a word it heard correctly --
homophone confusion, not mishearing (e.g. "Trey" instead of "Tray"). This
is a disambiguation problem: Whisper hears the right sound, picks the
wrong written form because it has no way to know which one is meant.

vocabulary.txt already exists for this, but only works at decode time via
initial_prompt -- adding a term means restarting the engine, which is
cumbersome enough that it doesn't get used in the moment a term is missed.

Spiked 2026-08-02. jellyfish (actively maintained, MIT, prebuilt wheels,
Rust-backed) provides phonetic encoding -- metaphone(), soundex(),
nysiis(), match_rating_codex() -- pure algorithm, not a model. Confirmed
"Trey" and "Tray" produce the same metaphone code, confirming the core
mechanism works for the case that motivated this.

Naive version is NOT safe: bare phonetic-code equality against every
transcribed word produces real false positives on ordinary vocabulary --
confirmed "cloud" and "clod" both collide with "Claude", "true" collides
with "Tray", "pity" collides with "PTT". "Cloud" specifically is a
plausible everyday word in a tech-dictation context; a bare match would
silently rewrite it to a name. Needs a second signal before trusting a
swap (e.g. requiring the transcribed word to already look name-like, or
be otherwise unrecognized) -- not designed, real remaining work, not
solved by this spike.

Would read vocabulary.txt live, as a text post-process after every
transcription -- never touches Whisper's decode path or initial_prompt,
so adding a term is live on the next dictation, no restart. Solves the
reload-cumbersome complaint as a side effect of the approach, not a
separate fix.

Same corpus problem as B13: no real data yet on how often this ambiguity
actually occurs, or what a safe second signal should look like in
practice. Wait for transcript_log.txt to accumulate before deciding
whether to build this -- logging already flowing, nothing to set up when
that time comes.

Build plan first -- encapsulate only what it calls for, as a reusable
API. Cross-check other new-feature plans before sizing that extraction
-- not extra process, avoids rebuilding the same shared piece
narrower-then-wider one feature at a time.

TWO CONDITIONS, both load-bearing.

==============================================================================
B24. AMBIENT LISTEN MODE -- CONTINUOUS TRANSCRIPTION, OPTIONAL SPEAKER ATTRIBUTION -- NEW FEATURE
==============================================================================
A second, selectable mode alongside today's PTT dictation -- mutually
exclusive, not simultaneous, not a separate app. Same engine
(STTEngine, model selection, tray shell), different capture loop and
different output target.

MOTIVATION
Passive background transcription for meeting-heavy roles -- a
searchable, timestamped record of a day's conversations without
active note-taking. Validated against a real use case (management
role, back-to-back meetings), and market-precedented (Otter.ai,
Fireflies.ai, Read.ai already succeed doing exactly this). Legal/
consent questions are the user's to navigate, not this tool's to
gate -- same posture as any dual-use recording capability.

PIPELINE
  - Continuous capture, no PTT trigger. Async double-buffer: capture
    never blocks on transcription -- next chunk records while the
    current one transcribes.
  - 5-minute chunks flushed to disk as timestamped FLAC files, not
    passed in-memory. Decouples capture cadence from transcription
    cadence. FLAC, not raw WAV -- lossless, encode cost is sub-second
    even at max compression on modern hardware (no reason to trade
    size for it), and Whisper never reads the file directly either way
    (already decodes to a raw sample array before transcribing), so
    there's no compatibility cost to writing compressed from the start.
    No WAV anywhere in this path, not even as an intermediate -- FLAC
    decodes in one step straight into the same raw sample array Whisper
    already consumes, on the way out of the queue, same as it comes in.
  - Disk-based FIFO queue, oldest-first, plain directory scan -- no
    scheduler package needed (one producer, one consumer, one
    machine). Backlog bounded by disk space, not memory; self-
    revealing if it falls behind (stale timestamps visible to user).
    Real per-chunk throughput unverified -- confirm on real hardware
    when built.
  - No overlap, no dedup between chunks. A sentence split across two
    timestamped entries is acceptable -- cut doesn't mean lost.

SILENCE HANDLING
  - Whole-chunk pre-check (RMS/amplitude heuristic) before calling
    Whisper at all -- near-total silence skips transcription entirely,
    logs "[silence, skipped]" instead of risking hallucinated filler
    text (the well-known "thank you"-on-silence phenomenon).
  - vad_filter=True stays on for this mode too -- different
    granularity than the pre-check (trims partial silence within a
    chunk that has real speech), not redundant with it.

OUTPUT
Timestamped disk log only. No cursor injection -- that's PTT mode's
delivery mechanism, not this one's.

ATTRIBUTION -- THREE INCREMENTAL TIERS, each independently shippable
  Tier 1: Pure transcription. No speaker awareness at all.
  Tier 2: Diarization without attribution. Speaker A/B/? labels,
    always on by default -- privacy-safer than tier 1 (structure
    without PII), no enrollment system, no added risk.
  Tier 3: Diarization with attribution. Persistent voice-ID via
    embeddings, each distinct voice assigned a permanent GUID.
    Separate GUID-to-name lookup table (empty until user labels it) --
    naming is just filling in one row, never touches the embedding-
    matching layer. UI: present a snippet of an unresolved "Speaker ?"
    voice, prompt for a typed name. Same person surfacing as two GUIDs
    (different mic, sick voice, etc.) self-corrects for free -- typing
    the same name for both produces an identical-looking transcript
    to an actual merge, no explicit merge operation needed.

ACCEPTED LIMITATIONS, NOT BUGS
  - No retroactive relabeling. Naming a "Speaker ?" only applies going
    forward; past log entries using that placeholder stay as-is.
  - False merges (two different real people collapsing into one GUID)
    have no correction lever, unlike false splits (which self-correct
    via re-naming) -- mitigated by biasing the similarity threshold
    conservative (favor staying unresolved over confidently guessing
    wrong). For voices that are genuinely hard to tell apart, the
    realistic steady-state is mostly-correct with a persistent
    "Speaker ?" residue, not silent misattribution -- self-explaining
    to the user, accepted as-is, not designed around further.

NOT DESIGNED IN DETAIL YET
Exact chunk duration and silence threshold tuning, which diarization/
embedding library, the naming-snippet UI itself, Settings integration
for the mode toggle. No gate, no P-item.

SUPPLEMENTARY SPIKE IDEA, REVISED 2026-08-03: play YouTube (or any
audio source) out loud and let ambient mode's own mic capture it,
instead of yt-dlp. Superseded, not just an alternative -- yt-dlp's ToS
question disappears entirely (nothing touches YouTube's servers or
download restrictions; this is just watching a video normally while a
mic that's already listening happens to pick it up), and mic-captured
audio is arguably the better test anyway -- real room acoustics and
speaker response baked in, matching what production ambient mode
actually encounters, not pristine directly-extracted audio. Same
coverage as the yt-dlp idea: a single video only tests Tier 2 (telling
concurrent speakers apart within one file); validating Tier 3's actual
hard problem (same person recognized across separate sessions) needs
the same identifiable voice across multiple separate videos/sessions,
not one clip -- just play a different video from the same channel each
session instead of downloading a batch.

DEV-ONLY CAPTURE FLAG, same pattern as FLAC_CORPUS_CAPTURE_ENABLED:
a bare code constant, not Settings, gates whether ambient mode's
processed chunks are retained instead of deleted. Needed to feed real
multi-speaker corpora (including the spike above) through the actual
ambient pipeline and keep the output for validation -- production
default is always delete (retention has no shipped-feature use), this
flag is dev-only. On for building/testing, off before any push
(pre-push.txt P9).

TWO-STEP SPIKE TEST: segmented clips as-is (per-sample consistency),
then grouped into ~5-minute assemblies with realistic silence gaps
(production-chunk accuracy). Don't merge the whole corpus into one file
for either step.

Build plan first -- encapsulate only what it calls for, as a reusable
API. Cross-check other new-feature plans before sizing that extraction
-- not extra process, avoids rebuilding the same shared piece
narrower-then-wider one feature at a time.

The dev-only capture flag above copies a pattern that turned out to be
broken. A bare code constant ships with the source, and "off before any
push" never fires for a folder handed over on a USB stick -- the recipient

portable-folder-build-sheet.txt introduces -- absent file means every flag
off -- not a new constant and not a config field. That file is dev tooling
only; it is gitignored and never on the copy list.

==============================================================================
B27. SELECTION TRANSFORM -- NEW FEATURE
==============================================================================
Speak at selected text and have it replaced. Mechanically cheap: copying does
not deselect, so Ctrl+C then Ctrl+V lands the replacement on the live
selection with no cursor bookkeeping, and the app already owns both halves.

Three hazards to design against. The selection can die while the user is
still talking, so the copy happens at press and not at release. The paste
replaces whatever is selected AT PASTE TIME, which may not be what was
copied. An empty selection silently transforms a stale clipboard, so clear it
first and check something arrived.

Windows UI Automation reads and replaces text without the clipboard, which
avoids all three and keeps formatting -- but coverage across applications is
inconsistent, so clipboard stays as the fallback.

This edits documents rather than appending to them. A bug here destroys work
rather than leaving a stray word.


==============================================================================
B28. SEARCH THE CORPUS BY MEANING -- FUTURE / MAJOR EXPANSION
==============================================================================
Ask a question in English and get back what you actually said about it,
months ago, from a corpus that never left the machine. Embeddings in SQLite
via the sqlite-vec extension, retrieval by pure vector math, a local LLM
(Ollama) reading the retrieved rows and answering.

Design lives in vector-analysis-investigation.txt. Read its provenance
header first -- it is outside work and nothing in it was measured here.

WHY IT IS NOT QUEUED. It adds an embedding model and a generative model to
a dictation tool, which changes what the product is. It also assumes a
corpus of ambient transcripts, and ambient mode is B24, unbuilt.

WHAT MAKES IT POSSIBLE LATER IS ALREADY BEING BUILT. Text tied to a
timestamp tied to an audio file is the whole substrate, and that is
corpus-database-build-sheet.txt. Embeddings are derived from the text and
can be computed over the entire history at any time, so the embedding model
is not chosen now and choosing it early is the worse decision -- vectors
from two models do not share a space, so any model change discards every
vector ever stored.

THE HARD PART IS NOT THE DATABASE. Measured over the existing corpus:
median capture 7.3 seconds, 85 percent under fifteen. Those are utterances,
not documents, and one embedded seven-second fragment carries almost no
meaning on its own. Deciding what a retrievable unit is -- grouping
consecutive captures, embedding windows rather than single rows -- is the
feature. The storage and search half is arithmetic at this scale.

FIRST CONCRETE STEP, whenever it is pulled: prove sqlite-vec loads, then
backfill vectors over whatever rows have accumulated. Both run without
touching the daemon, and the backfill improves the longer it waits.
