# Process-Level Defects in qt-port-plan.txt

Based on the project's templates (`plan.txt`, `build-sheet.txt`) and house style rules, `qt-port-plan.txt` contains several methodological errors and gaps that must be resolved before it can be converted into a build sheet. 

## 1. GOAL Formulation Fails the "Pitch" Test
* **Rule:** `plan.txt` states the GOAL must explain "Why this is worth doing, one paragraph, pitched at whoever decides to fund it rather than whoever builds it."
* **Defect:** The current GOAL ("Make this a Qt app...") describes *what* is being done (the engineering directive) but fails to explain *why* it provides value. It lacks functional or business justification (e.g., lower latency, native audio hooks, etc.) needed for a pitch.

## 2. DELIVERABLES is Polluted with SEAMS and DESIGN
* **Rule:** DELIVERABLES must strictly be "What ships, checkable by someone else. The sheet's Done line comes from here."
* **Defect:** The section is structured around phased execution ("PASS 1", "AFTER PASS 1"), which belongs in **SEAMS**. It also includes non-observable implementation details (e.g., "geometry.py and dpi.py are deleted", "The hotkey message pump runs in Qt's event loop"), which belong in **DESIGN**.

## 3. SEAMS Defeats Its Own Purpose
* **Rule:** SEAMS defines "Where to cut so every piece leaves a working app. Risk boundaries, not feature boundaries."
* **Defect:** The "AND ON" / "Everything after" seam states: "No predetermined cuts." This explicitly violates the rule, as without predetermined cuts, there is no guarantee each piece will leave a working app.

## 4. HOUSE STYLE Violations
* **No Counts:** The rule "No counts. Write how to re-derive it." is violated multiple times (e.g., "It found eight...", "The three WAVs", "two crash-path ones").
* **Saying It Twice (Arguing):** `input-device-plan` and `core-arch-plan` are mentioned in both the **SCRATCHPAD** and **TRUE-UP**, duplicating the effort. "Pass 1 being atomic" is argued in both **DELIVERABLES** and **DESIGN**. 
* **Breadcrumb Length:** `plan.txt` specifies that **BREADCRUMBS** should be "one line each." The breadcrumbs for `input-device-plan.txt` and `core-arch-plan.txt` span 4-5 lines each, turning into justifications rather than simple flags.

## 5. Unresolved Spikes and Assumptions (Methodological Gap)
* **Gap:** The **DESIGN** section heavily relies on unresolved spikes ("BLOCKED ON A SPIKE" and "JUDGMENT, NO SPIKE NEEDED"). While this is acceptable for a draft, a build sheet cannot be written until these are run, answered, and moved to "SETTLED".
* **Gap:** Many spike items read like assumptions. The methodology states assumptions belong in **EVIDENCE** as `[ ]` questions naming the method that answers them, rather than crowding the DESIGN section.

## Conclusion
To make this plan actionable, the author needs to rewrite the GOAL for value, strictly separate observable outcomes (DELIVERABLES) from internal wiring (DESIGN) and phasing (SEAMS), resolve the spikes, and strictly adhere to the structural constraints (no counts, one-line breadcrumbs).

## 6. Exhaustive Code Dive Findings (Missed Dependencies)
A deep code dive reveals several architectural Tkinter touchpoints and Win32 couplings that the plan's "recalled pattern list" completely missed. These represent hidden scope that must be spiked or designed for:

* **Thread/Event Loop Interactions (`after(0)`):** `ptt_capture.py` relies heavily on `self.root.after(0)` to marshal background `pynput` listener callbacks back onto the main Tk thread safely. The plan asserts that `pynput` "stays for PTT," but misses that crossing the thread boundary in Qt requires `QMetaObject.invokeMethod` or explicit Signals. Blindly porting this without a signal bridge will crash Qt.
* **Win32 Mutex (Single Instance):** `vdict_tray.py` uses `win32event.CreateMutex` to enforce a single running instance. The plan misses this entirely. A proper Qt port should replace this Win32-specific coupling with Qt paradigms like `QSharedMemory`.
* **Deep Data Binding (`tk.StringVar`):** The plan states "Config keeps its current pydantic shape," but `settings.py` is entirely wired using `tk.StringVar` for its internal state bindings. The UI state is structurally coupled to Tk, requiring a complete rewrite of the binding layer, not just the widget drawing.
* **Daemon Polling Loop:** The plan lists the 100ms Tk timer (`self.window.after(100, self._tick)`) as being solely for "worker output". However, `_tick()` also runs `daemon_proc.poll()` to monitor the background daemon's exit status. The Qt port must redesign this daemon lifecycle monitoring (e.g. via `QProcess` signals).
