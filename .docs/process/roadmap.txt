VOICE DICTATION - ROADMAP

Order of the work and why. Not design -- plans hold that. Not tasks -- build
sheets hold those. Living document: edit it when the order changes.

A phase's deliverables belong here only when the delivery is part of why the
phase sits where it does. Everything else is backlog.

ORDER advances and never empties -- there is always a NOW. Why a phase sits
where it does belongs here too, and lives until that phase ships.

Anything else is jotted seed for a plan not yet written, and writing that plan
DELETES it. The plan does the real investigation -- requirements, methods,
packages, impact on existing code and on forward dependencies -- and reaches
these conclusions itself or contradicts them. A note copied forward instead
entered the plan unverified, which is how a wrong line survives three
documents.

The exception is a fact that cost real measurement and that no later step
would think to re-measure. That goes to spike-notes.txt, never forward into a
plan.

==============================================================================
WHY QT BEFORE CORE-ARCH
==============================================================================
core-arch's open log() blocker -- what carries worker-thread output to the
console widget -- is a Tk problem. Qt answers it with signals and slots: no
queue, no 100ms tick, no drain. Solving it in Tk first builds the thing the
port deletes.

input-device-plan's WIDGET GAP (tk.OptionMenu has no on-open refresh hook) is
the same shape: a Tk deficiency that stops existing in Qt.

What this beat: core-arch first, on the claim that porting would rebuild the
tray UI twice. It would not -- core-arch touches orchestration, not widgets.

Overturn it if the Qt port needs core-arch's threading model settled first.
It should not: Qt's model is that answer.
