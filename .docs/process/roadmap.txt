==============================================================================
WHY QT BEFORE CORE-ARCH
==============================================================================
core-arch's open log() blocker -- what carries worker-thread output to the
console widget -- is a Tk problem. Qt answers it with signals and slots: no
queue, no 100ms tick, no drain. Solving it in Tk first builds the thing the
port deletes.

input-device-plan's WIDGET GAP (tk.OptionMenu has no on-open refresh hook) is
the same shape: a Tk deficiency that stops existing in Qt.

What this beat: core-arch first, on the claim that porting would rebuild the
tray UI twice. It would not -- core-arch touches orchestration, not widgets.

Overturn it if the Qt port needs core-arch's threading model settled first.
It should not: Qt's model is that answer.
