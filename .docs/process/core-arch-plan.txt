VOICE DICTATION - PLAN: CORE ARCHITECTURE (ORCHESTRATOR REFACTOR)

Reference for the core-arch build sheet.

SEQUENCING: the vdict_tray split has landed. roadmap.txt holds what comes
before this build and why. Splitting first was safe because each piece
presents an API rather than just relocating code, so this refactor is one
more caller of interfaces that already exist instead of a rewrite. That is
also why Settings takes an on_save callable rather than owning its own save
flow -- the Save handler being a separate actor, per ARCHITECTURE below,
was built into the split rather than retrofitted here.

STTEngine.reload's vulture finding stays overridden at commit time until the
orchestrator calls it. Nothing calls .reload( anywhere today -- measured
2026-08-04. Its caller is already designed, in COMMON TO BOTH and BLOCK A
below, so unlike portaudio_io.py's six there is no question of whether this
one survives.

BLOCKERS -- resolve before build sheet, not during:
  - log()'s new mechanism. What replaces print()+reparse for getting
    output from a worker thread onto the console widget. Not decided yet.
    REQUIREMENT, measured 2026-08-05: one event has to carry both a human
    sentence and a traceback, with each destination deciding whether to
    render the traceback -- what logging's own exc_info plus per-handler
    formatters give. Today log() and error_log() are separate functions
    and every site wanting both must call both. Re-measured after
    error_log gained its screen flag: of its five call sites, two pair an
    explicit log() sentence with screen=False, and three rely on
    error_log's own screen dump. That flag is itself a per-call-site
    convention -- the kind this requirement says does not hold -- so the
    capability still belongs in the mechanism.
  - Whisper/GPU-cleanup spike -- whether swapping WhisperModel objects in
    place actually releases GPU/CUDA memory cleanly across repeated
    loads. Same treatment PortAudio got: source plus real hardware
    verification, not source alone. Not verified yet.
  - What absorbs a device swap while a recording is already in progress
    (rebuild() racing an active start_capture()) -- a bad transcribe()
    call is already handled, but a stream replaced out from under an
    active recording is a different failure entirely. Not resolved.

OPEN ISSUES -- worth tracking, does not gate the build sheet
==============================================================================
  - Field audit incomplete. Every config field needs classifying against
    the real reconfigure categories (instant-cast, Model, Audio Device,
    Listener, or genuinely no mechanism needed) -- PTT button and the
    output-window hotkey are both confirmed Listener-category fields that
    weren't in the original inventory. Finish this when the build sheet
    gets drafted, not as a separate pre-step.
  - stt.py's GPU-primer thread: QRunnable on QThreadPool, or left as a
    plain thread? Moved from the Qt port plan -- it is mechanics, and this
    plan is what restructures that code.
  - Hotkey extensibility. hotkey.py's existing register()/unregister()
    (one thread, one Windows message pump) generalizes cheaply to
    multiple registered hotkeys -- _HOTKEY_ID=1 is the only thing
    limiting it to one today. Worth doing now so future hotkeys (e.g.
    toggle transcription without raising the window) are cheap to add,
    not a rewrite. PTT stays on its own separate pynput mechanism
    permanently -- different OS tool for a genuinely different job
    (press/release tracking, mouse-button support), not something that
    unifies with hotkey.py.


==============================================================================
ARCHITECTURE
==============================================================================
  - One process, one entry point. The orchestrator's decision logic -- what
    changed, is it recoverable, what to reload -- runs on the main thread,
    as Tk callbacks (Settings' Save handler, a worker reporting back). It
    is not a separate thread coordinating Tk from outside.
  - Audio capture (audio.py's AudioCapture), STT/model (stt.py's
    STTEngine), the PTT listener (keyboard.py's PTTListener), and the
    global hotkey (hotkey.py) each run on their own thread. Tk owns the
    main thread and is the only thing that touches widgets; every worker
    thread reaches it through .after(). Settings-to-orchestrator needs no
    such bridge -- same thread already.
  - Those worker threads don't begin real hot-path work until first-run
    onboarding has completed at least once -- today's two-process split
    gives this for free (the daemon doesn't start until Save & Restart
    launches it); the merged process has to enforce it on purpose.
    Mechanism is FIRST RUN's own build-sheet work, not decided here.
  - Settings (vdict/tray/settings.py) is a pure view -- returns the raw
    snapshot of what the user picked, no diffing inside it. BUILT: the
    dialog reads its widgets and calls on_save(config), nothing else.
  - The Save handler is a separate actor from Settings, same dialog, same
    thread, different code. Settings' job ends at returning the snapshot;
    the handler around it is orchestrator code -- it writes to disk and
    dispatches to consumers. BUILT as app's _on_settings_save, which does
    save_settings, settings.close and restart. save_and_restart is gone.
  - No central diff step. Each consumer decides for itself, at the point it
    would act, whether its own slice changed -- cheap stuff (beep volume)
    just reapplies, expensive stuff (model reload) checks first.
  - Modules needing both hot-path work and Settings-driven reconfiguration
    expose two entry points, not one -- a work entry point the PTT/daemon
    thread calls (transcribe(), start_capture()) and a reconfigure entry
    point the orchestrator calls (reload(), rebuild()). Same object,
    different callers, different threads.
  - No cross-process signaling needed anywhere -- that whole problem (how
    does the daemon know Save happened) dissolves because there is no
    longer a process boundary to cross.
  - FIRST RUN is gated on ui.first_run, kept independent of audio.device's
    own state -- input-device-plan.txt's AT-LAUNCH FAIL condition is for a
    returning user whose device went missing, not this. Decoupling means
    onboarding can be re-tested by toggling one flag, without nulling a
    real device config to force it.
  - ONE Welcome dialog, not a sequence of message boxes:
    - States the microphone requirement plainly -- not optional, needs a
      pick before anything works. This is the one hard requirement in the
      tour; everything else below is already decided for them.
    - PTT trigger default (middle mouse button) -- explains how to use the
      app at all, since nothing else teaches this.
    - Output window hotkey -- unset by default, real discoverability gap
      (hide the window, no way back except the tray icon) -- nudge to bind
      one while already in Settings.
    - Compute device and model size -- mention a sensible default exists,
      point at Settings if they want to change it.
    - Minor settings (beeps, etc.) -- barely worth a sentence, they'll find
      them in Settings regardless.
    Then opens Settings once, same as before -- not three separate boxes
    each ending in "you can change this in Settings."
  - Depends on knowing whether a device is already configured (same
    enumerate/resolve mechanism as input-device-plan.txt), but does not
    reuse that plan's fault modal -- a first-time user isn't told "can't
    find your device," which presupposes a prior choice they never made.
    Two different dialogs, sharing only the underlying check.
  - Not designed in detail yet -- exact copy, dialog structure, and whether
    ui.first_run needs any changes beyond staying as-is are build-sheet
    work.

CONFIG PERSISTENCE
==============================================================================
  - JSON only at the disk boundary -- config.json in, config.json out,
    same as today. In memory it's always the same object --
    vdict.common.config.Config, the existing pydantic model, not a new
    type -- passed by reference, never serialized just to move between
    Settings, the Save handler, and consumers.
  - Written at checkpoints -- Settings Save, window hidden, tracked window
    destroyed, and at exit. Three of those four are app's _save_state(),
    which calls geometry.save_all() to flush every window the registry
    tracks and then save_settings(). Save is its own path, app's
    _on_settings_save.
  - Checkpoint flush, not a per-settle write. geometry.manage() caches on
    <Configure>, and disk is touched only at a checkpoint, so dragging a
    window costs nothing until one of those four fires. That is what the
    split built, and it is what this section's earlier "geometry settled"
    wording would have meant instead -- a write per settle, putting disk
    I/O on every drag. Revisit only if a checkpoint proves too coarse to
    survive a crash with the layout intact.
  - STANDING VULTURE OVERRIDE: ui.settings_pos and ui.console_geometry are
    reported unused at every commit, and that is expected. geometry.py's
    registry reaches both by name rather than by attribute, so vulture
    cannot see the usage; config.py carries a comment at the fields saying
    the same thing. No whitelist entry: a bare name there exempts the
    identifier everywhere and forever, and this finding ends on its own
    when the Qt port deletes geometry.py. What that beat: making the
    registry attribute-addressable so the scan goes quiet, which trades a
    working design for a clean tool run.
  - One shared, live Config object instead of seven independent stale
    reads -- three in app.py, four in settings.py. Settings overwriting a
    change made elsewhere while open is NOT among the things this fixes --
    that landed separately, as the re-read in the dialog's two writers,
    both since gone. What is left here is collapsing the seven reads into
    one.
  - Every checkpoint write uses the same atomic write (temp file, then
    os.replace()) -- already required by B1, applies to all of them here,
    not just Save. Every one of those writes is explicit encoding="utf-8",
    matching every other file operation in the app -- config.json's
    reads/writes are the one place that wasn't (D15), relying on
    Windows' platform-default locale encoding instead.
  - load_settings()'s existing per-field healing (missing file seeds
    fresh, invalid JSON resets wholesale, one bad field heals via
    pydantic without touching the rest) replaces load_config()'s
    raise-on-any-of-these -- one shared function, Tray owns it.
  - ptt.button gets a real validator (checked against BUTTON_MAP plus
    the key: pattern) instead of staying a bare str. An invalid value
    becomes a genuine pydantic ValidationError, caught by the same
    per-field healing above -- resets to the default ("middle"), logs
    a note. No fault type, no modal, no Settings-routing needed.


==============================================================================
LIVE-READ SETTINGS (no reconfigure entry point)
==============================================================================
  - Today, main() reads config once at startup and hoists values into
    local variables before the loop starts -- nobody re-reads config.json
    again, which is why every change needs Save & Restart today. This
    section is what replaces that.
  - The orchestrator holds one live Config instance for the whole process
    lifetime. The Save handler mutates its fields in place -- it never
    replaces the object with a new instance. Every thread needing a live
    value holds a reference to that same object, not a copy.
  - Consumers read the field directly, at the point of use, every time --
    play_tone() reads the live value right where it's called. No entry
    point, no flag, nothing to call.
  - Safe without a lock: attribute get/set on a shared object is atomic
    under the GIL.
  - Inventory (B1's CONFIG RE-READ tier): vocabulary.txt, audio.feedback,
    ptt.mode, keyboard.preserve_clipboard.
  - Persistence is still the Save handler's job, same checkpoint
    mechanism as CONFIG PERSISTENCE -- mutating the field live doesn't
    write it to disk by itself.
  - vocabulary.txt specifically: parsed fresh on every PTT cycle, not
    hoisted once like today's prompt = load_vocabulary() before the
    loop. Every successful read also copies what was just read into
    vocabulary.txt.bak -- costs the same as the read itself.
  - Recovery priority if vocabulary.txt is missing at read time: restore
    from vocabulary.txt.bak if it exists (preserves curated words), else
    reseed from the template. Either way, log a note -- never silent.
  - The reseed-if-missing logic consolidates into one shared helper in
    vdict/common/config.py, replacing two separate implementations that
    only existed because tray and daemon used to be different processes
    (common/config.py's reseed_vocabulary_if_missing, which copies from the
    template, and load_vocabulary()'s current raise-if-missing). Both the
    tray's boot-time reseed and File > Vocabulary's reseed become thin
    callers of the same function the live-read path uses.


==============================================================================
MODEL RELOAD / AUDIO DEVICE
==============================================================================
COMMON TO BOTH
  - Two-entry-point pattern (see ARCHITECTURE): STTEngine gets
    reload(config) alongside its existing transcribe()/wake_gpu();
    AudioCapture gets rebuild(config) alongside start_capture()/
    stop_capture(). Two real methods per class, not a branch inside one --
    different names on purpose, so "reload" always means the model and
    "rebuild" always means the device.
  - Orchestrator calls both reconfigure entry points unconditionally,
    every time Settings returns -- not gated on the orchestrator
    detecting a change itself. Whether real work happens is each
    method's own decision.
  - One shared flag protects the PTT loop's single gate -- don't start a
    new cycle. reload(), rebuild(), or a cycle's own pending-delivery
    confirmation can each set it before starting real work; whichever set
    it clears it in a finally covering both success and failure.
    start_capture() only reads it, checked once, before starting a new
    cycle. Not three independent flags -- there's only one decision being
    protected, three things that can hold it closed.
  - STTEngine.reload(config) already exists, landed as prep work
    2026-08-02 -- its busy_flag constructor param (defaults to its own
    threading.Event() when nothing is shared in) is this exact flag. The
    orchestrator doesn't invent it; it constructs one Event and passes the
    same instance into both STTEngine and AudioCapture.

BLOCK A -- MODEL (STTEngine.reload)
  - Download, if needed, happens as part of this same call, with its own
    progress feedback, before the reload itself runs.
  - Uses the shared flag from COMMON -- sets it before starting real
    work, clears it in a finally regardless of outcome.
  - The contrived edge case (reload while a recording is already in
    progress) is absorbed by wrapping the transcribe() call so one bad
    transcription logs one line and continues instead of ending the
    session -- now a real dependency of this design, not leftover scope.

BLOCK B -- AUDIO DEVICE (AudioCapture.rebuild)
  - Uses the shared flag from COMMON -- sets it before swapping the
    device, clears it in a finally regardless of outcome.


==============================================================================
FATAL VS RECOVERABLE
==============================================================================
  - Orchestrator's call, no watchdog/survivor process.
  - Unrecoverable means the whole stack exits -- red error, "Unrecoverable
    error" modal, log captured to disk first (generalizing
    app._report_callback_exception's existing pattern -- native MessageBoxW,
    not Tk, since Tk itself might be compromised), a bug-report link.
  - User re-clicking the desktop icon is the accepted recovery gesture.
  - threading.excepthook gets built (cheap, catches silent
    thread-death-by-exception).
  - Every unhandled exception feeds the same path: threading.excepthook
    (background threads), the generalized app._report_callback_exception
    pattern (main thread, Tk and .after() callbacks alike), and a raw
    try/except around startup itself before Tk exists (today's
    _log_startup_crash). Three catch points, one destination.
  - The generic fatal category is called fatal, not daemon-crash -- that
    name presupposed a process split that's going away. Red, ERROR
    marker, box=True, same modal mechanism as mic-fault/model-fault.
    Concrete triggers: missing Python dependencies, any unhandled
    exception. Unlike mic-fault/model-fault, it has exactly one outcome
    -- nothing Settings can fix for either, so the modal never routes
    there. Message, bug-report link, exit.


==============================================================================
LOGGING MIGRATION
==============================================================================
  - GENERAL RULE: when a function or branch gets rewritten or removed by
    this refactor, any log() call inside it must be explicitly carried
    into whatever replaces it. Logging does not survive by default just
    because the code around it does -- check it at every site being
    touched, don't assume it follows along.
  - Survives unchanged: the CATEGORIES table (color/marker/box/toast),
    error_log()'s disk-write-first pattern (vdict/tray/log.py),
    transcript.write()'s dedicated
    logger. None of these need to change in their own definitions, only
    in how they get called.
  - The disk-write half (write_error_log, formerly tray-only
    _write_error_log) already moved to vdict/common/output.py as that
    prep work, 2026-08-02 -- vdict_daemon.py already calls it directly
    today. This refactor doesn't need to invent that cross-process bridge,
    it already exists.
  - At real risk: vdict_daemon.py holds roughly a dozen log() call sites
    (loading, ready, block, rec/note/done, transcript, plus
    _resolve_output_device()'s two error calls) that all need a home in
    whatever the new thread-body version of this file looks like.
  - session.log_session_block() currently reports the subprocess's PID
    and fires on every start/restart -- under this design a restart is
    rare (unrecoverable fault only), so this block's trigger point and
    content need redefining, not just relocating verbatim.
  - mic-fault/model-fault survive as categories, but their modal/dispatch
    bundles don't carry over as-is -- they need to match FATAL VS
    RECOVERABLE's recoverable-vs-unrecoverable split. Open for the mic-fault
    modal specifically, once the daemon no longer exits on a mic fault: does
    Close just dismiss, with the daemon already running and Settings already
    open underneath, and does MIC_FAULT_FLAG_PATH get deleted outright?
  - log()'s actual new mechanism is still the BLOCKERS item at the top --
    this section doesn't resolve that, it's why that blocker matters.
