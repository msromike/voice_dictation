time_info is a sixth vulture finding and is NOT waiting on a call site. It
is a positional parameter in sounddevice's callback signature (indata,
frames, time_info, status) -- PortAudio passes all four whether the body
reads them or not, and vulture flags only this one of the three the body
ignores. It ends as an inline suppression beside start_hold's callback,
never as a caller; deleting the parameter to clear the warning breaks the
callback. Overturned only by start_hold not surviving the decision below,
which takes the whole function and this note with it.

==============================================================================
CONFIRMED FROM SOURCE, VERIFIED ON HARDWARE EXCEPT WHERE NOTED
==============================================================================
Read from PortAudio's and sounddevice's actual source (.reference/), then
confirmed or refined against real hardware, per bullet below.

  - Pa_Initialize's WASAPI backend does a fresh IMMDeviceEnumerator query
    every single call -- reinit sees whatever is currently connected, not a
    cached answer. Confirmed on real hardware: MIXER appeared and
    disappeared correctly across enable/disable cycles.
  - A failed stream never says why. 16 different WASAPI failure paths
    (device gone, format changed, buffer error, etc.) all collapse into
    one generic thread-death signal -- PortAudio's real-time callback
    contract forbids the slow work (allocation, classification) needed to
    preserve which one occurred. Build ONE response to any mid-stream
    failure, not different ones per cause. Confirmed on real hardware:
    stream.active goes False on its own, no exception, no status flag --
    even less specific than a generic exception, just the flag flipping
    unprompted.
  - Pa_Initialize/Pa_Terminate must be called from the same thread every
    time (COM apartment affinity; get it wrong and there's no error, just
    a silently-skipped cleanup that leaks). No new thread is needed to
    satisfy this -- sounddevice already auto-initializes on import, on
    whatever thread first imports it, which today is vdict_daemon.py's
    main() thread (the only place AudioCapture is ever constructed). STAYS
    SOURCE-ONLY -- no hardware test isolates this, and deliberately violating
    it just to watch a silent leak doesn't prove much without dedicated
    diagnostic tooling. Genuinely unverified, not just unstated.
  - A failed open/start always raises PortAudioError, uniformly, regardless
    of cause -- including a host-specific WASAPI conflict such as another
    app holding the device in exclusive mode (WASAPI supports exclusive
    mode on input, confirmed symmetric with output in the same source).
    Traced both sides: sounddevice's Pa_OpenStream and Pa_StartStream both
    route through one _check() function that raises PortAudioError for any
    negative PortAudio error code, no separate exception class for host
    errors; and audio.py's existing code already wraps the open+start call
    in except sd.PortAudioError. STRONGER than the other three here -- this
    traces our own calling code together with the library's exact
    exception path, not just the library's general design intent. Confirmed
    on real hardware: a real WASAPI exclusive-mode hold on MIXER caused a
    second open attempt to raise PortAudioError.

If real hardware ever contradicts a source claim, that's a new spike -- not
locked, just not guesses anymore.


==============================================================================
TESTED ON REAL HARDWARE
==============================================================================
Real hardware: PDP mic (main), Behringer mixer input (stands in for the DAW
guy's second device), webcam mic (stands in for the hourly-switcher's
second device). All exercised through vdict/daemon/portaudio_io.py for
real, not a simulation of it.

  reinit latency -- validates whether "fast, in-process restart" (DESIGN)
    is actually fast, or needs a "reconnecting" UI state instead of feeling
    instant. Measured ~0.02-0.03s (5 runs) -- fast enough, no
    "reconnecting" state needed.
  reinit reliability across real changes (mixer/webcam enable-disable) --
    validates the dropdown's "queries fresh every pull-down" claim and the
    recovery flow's reinit-then-retry design. Confirmed: MIXER resolved
    correctly across a disabled->enabled transition.
  multi-device disambiguation -- all three devices enabled at once, each
    resolves to the correct index against the correct name, no cross-
    matching. Confirmed: PDP/MIXER/WEBCAM all three resolved correctly at
    once, no cross-matching.
  live mid-stream failure, via portaudio_io.start_hold/stop_hold -- confirms
    THAT a failure is detectable at all from Python, since we now know it
    won't say why. Confirmed: stream.active goes False on its own when the
    device disappears, no exception, no status flag -- this is the
    daemon's detection signal, and settles the MID-RECORDING truncation
    logging decision below: log the quiet note.
  exclusive-mode conflict, via a real WasapiSettings(exclusive=True) hog
    process -- validates the CONFIRMED FROM SOURCE bullet (a failed open
    always raises PortAudioError) actually holds on real hardware, not
    just in the traced code path. Confirmed: a real exclusive hold caused
    a second open attempt to raise PortAudioError.

DROPPED, 2026-08-01: the "default disappears, does Windows auto-promote a
replacement" test. Moot -- this app no longer reads Windows' default device
at all (see DESIGN). What Windows privately decides is default is no longer
something we act on, so it stopped being worth measuring. Real empirical
finding that drove this, not a guess: WEBCAM auto-promoted itself to
Default Device unprompted, twice, confirmed on this hardware -- Default
Device does not reliably reflect user intent, so nothing here should depend
on it.


==============================================================================
DESIGN
==============================================================================
CONTINGENT ON THE LIVE CONFIG OBJECT. Three pieces of this design assume the
re-read/diff loop and the audio.device in-process rebind tier already exist:
AudioCapture rebuilt in place, Settings' immediate-probe-then-live-or-restart
branch, and the daemon never exiting on a mic fault. Built against today's
full-restart-only daemon, all three get rewritten when that lands. Order is
roadmap.txt's, not restated here.

NO SYSTEM DEFAULT. ANYWHERE. EVER. This app never reads Windows' notion of
a default input device, not even once at bootstrap. The dropdown lists
real device names only -- System Default is not, and never will be, an
option in it.

FIRST RUN IS NOT THIS PLAN'S CONCERN. core-arch-plan.txt's ARCHITECTURE
section owns onboarding entirely -- see FIRST RUN there for the Welcome
dialog's actual content and design. Tangential to this plan, an extension
of it, not duplicated here.

AT LAUNCH (see ERROR CONDITIONS below) means a RETURNING user whose
configured device has gone missing -- not first run, which
core-arch-plan.txt's FIRST RUN resolves before this plan's fault path is
ever reached. That
FAIL modal stays terse ("Microphone 'X' not found, pick another below"),
never the first-run tour -- a returning user doesn't need PTT and hotkey
re-explained to them.

DETECTION, TWO TOOLS FOR TWO DIFFERENT MOMENTS:
  - Is the configured device still around? A cheap list-membership check
    against enumerate_inputs() -- no stream open needed. Used at launch and
    to populate/validate the dropdown.
  - Did the actual recording attempt fail? The real open, at PTT press --
    not a separate check, just handling that attempt's own outcome.

SILENT WAIT AT LAUNCH -- observed, not yet designed. Today AudioCapture
resolves the device in its constructor, before stt.load(), retrying 5 times
a second apart. Nothing is logged before or during that window, so the
console shows the session block and then up to five seconds of nothing --
which reads as the model loading, because that is the next thing that
appears. Observed live while forcing a mic-fault: no output at all until the
fault modal, and no loading dots, because the daemon never reached its
"Loading model" line. Whatever replaces this check should say something
while it works. Open: does the 5-attempt retry survive at all, or does the
sleep/wake USB re-enumeration case need to survive somewhere else once
resolution moves off a cached device_id? Applies either way.

Dropdown queries fresh every time it is pulled down, not once at Settings-
open. Plug in, pull down, device appears. This IS the hot-swap mechanism --
no watcher, no live state. One shared query function, called on demand by
both the dropdown and the launch-time list check -- stateless, not the
rejected watcher/ledger. EXPLICIT, not inferred: that shared function is
reinit() THEN enumerate_inputs()/resolve_by_name() -- enumerate alone
returns stale data (CONFIRMED FROM SOURCE above). A build that calls
enumerate_inputs() by itself, without reinit first, is not this design.

WIDGET GAP: the mic dropdown (settings.py) is
currently a plain tk.OptionMenu
(still offering the now-dead settings.DEFAULT_MIC_LABEL/System-Default
choice --
untouched, real build-sheet work), and tk.OptionMenu has no native
on-open refresh hook -- "queries fresh every pull-down" needs one added.
menu.py already has a working precedent: the Help menu's tk.Menu uses
postcommand (menu._sync_help_menu) to refresh its Error Log state on every
open,
and OptionMenu exposes that same underlying tk.Menu via ["menu"] (already
used elsewhere in settings.py). Copy that pattern, don't invent a new
one or swap widgets.

ONE MODULE OWNS ALL DIRECT sounddevice CONTACT -- enumerate, resolve-by-
name, reinit, open (built: vdict/daemon/portaudio_io.py -- enumerate_inputs,
resolve_by_name, reinit, open_probe/start_hold/stop_hold). No default_input()
anywhere in it -- removed outright, not kept as a convenience, matching
"no System Default, not even for pre-highlighting." Everything else calls
this module; nothing else touches sounddevice directly. This is where the
same-thread rule
(source-confirmed, still unverified -- see above) gets enforced, once, at
the point someone could otherwise violate it by accident. Primitives
exist; not yet wired into AudioCapture's live control flow -- that's
build-sheet work. audio.py's _find_device_id calls sd.query_hostapis()/
sd.query_devices() directly and resolves by substring
(required_device in device['name']) -- both violate "nothing else touches
sounddevice directly" and "exact, not substring" above. The whole function
goes away, replaced by a call into portaudio_io.resolve_by_name -- not
just its dead "no name given, fall back to WASAPI default" branch.

Every mid-stream failure gets the SAME response regardless of cause --
PortAudio never says why (confirmed on real hardware). One response,
period -- no per-cause branching, and no per-mode branching either now
that there's only one mode.

RECOVERY, THE ONLY PATH: stream open fails -> modal -> Settings -> pick
from dropdown (real names only) -> Save -> restart -> ATTEMPT THE REAL OPEN
IMMEDIATELY, right there in Settings, not deferred to the next PTT press.
Opens clean -> beep -> dictate. Fails again -> stay in Settings, show it
inline ("that device exists but can't be opened -- maybe another app has
it exclusively -- pick another"), don't dismiss the dialog. Fail-fast: the
user is already looking at the dropdown with the fix one click away,
rather than discovering it later mid-dictation. PTT-time open-failure
handling still exists regardless -- something can change between Save and
the next PTT press (another app grabs it, it gets unplugged), so this
narrows how often that path gets hit, it doesn't replace it. TRAY-SIDE
CONFIDENCE ONLY: this open attempt runs in the tray process; the daemon is
separate, with its own independent PortAudio state (see the in-process
restart's own reinit, above). A clean open here proves the tray can open
the device, not that the daemon's subsequent PTT-time open will succeed --
the daemon's own reinit-on-restart is what actually makes that true, not
this check. Applies to
voluntary Settings-driven switching too, not just fault recovery. If the
picked device opens fine but doesn't actually work (bad routing, wrong
channel, whatever) that's the user's to notice and fix -- the "no speech
detected" outcome already absorbs the symptom without us needing to detect
the cause. backlog.txt B19 (level meter) is an optional future mitigation
for this, not required for the recovery flow to ship.

THIS APP NEVER REQUESTS EXCLUSIVE MODE. Considered and rejected -- no
latency benefit worth chasing (Whisper's own transcription time swamps
whatever shared-vs-exclusive difference exists), and a real cost: exclusive
mode would lock out every other app using the same mic while PTT is held,
directly breaking the coexist-with-Discord/Zoom/OBS use case this app
exists for. Shared mode only, always. The reason exclusive mode matters
here at all is the reverse case -- SOME OTHER app grabbing it exclusively,
which this app has to fail gracefully against, not request itself.

ERROR CONDITIONS -- self-contained. The build-v2 spec these once pointed at
predated this design and has since been retired, so there is nothing left to
reconcile against. Exactly one FAIL condition, three moments it can trigger:
  AT LAUNCH       named device absent (returning user, not first run --
                  see DESIGN above) -> FAIL
  AT PTT PRESS    named device absent, held exclusively elsewhere, or the
                  open otherwise throws -> FAIL
  MID-RECORDING   device pulled while actively recording -> truncated
                  audio, NOT a FAIL -- accept what was captured
FAIL is the one handler above (modal -> Settings -> dropdown -> Save ->
restart), used identically by all three -- no differentiation by cause
(PortAudio can't tell us why) and no differentiation by mode (there's only
one mode now).

ONE SHARED HELPER, CALLED IDENTICALLY FROM BOTH FAIL POINTS. The daemon
NEVER exits due to a mic fault -- launch or PTT-time, no distinction. AT
LAUNCH used to hard-stop before loading anything. The daemon now always
loads fully regardless of mic state; a launch-time
fault just means the ready double-beep never fires, same as any other
unresolved fault. Both trigger points call the same on_mic_fault(name)-
style helper: log the fault, signal the tray, keep running, wait for
Settings to fix it. No caller-side difference between the two anymore.

OUTPUT LOGGING -- outline only, real category/wording choices are
build-sheet work. Uses the existing vocabulary in common/output.py, not new
categories:
  FAIL (any of the three conditions above) -> "mic-fault" (red, ERROR, box)
    -- already the established category, already used in audio.py today.
    Names the missing device.
  Recovery succeeds, or a voluntary Settings-driven switch -> some
    dim/quiet line naming what changed -- borrows backlog B1's proposed
    pattern ("If nothing in the MODEL RELOAD tier changed, just save and
    log a dim output line naming what changed"), but B1 itself is
    "designed, not started" per its own status line, so this is following
    a proposed pattern, not an established one. Exact category (done vs
    block vs a new one) not picked -- build-sheet decision.
  Which restart happened (full vs PortAudio-only) -> worth surfacing.
    session.py's log_session_block already logs session details on
    every restart -- unrelated to B1, which hasn't started -- so this
    would ride along with that existing mechanism, not need a new one.
  MID-RECORDING truncation -- log a quiet note. stream.active goes False
    on its own when the device disappears mid-recording, distinguishable
    from a normal stop (active is still True right before the code's own
    .stop() call) -- cheap, and tells the user their recording was cut for
    a real reason, not that they did something wrong.

Settings and the recovery modal both get a button that opens Windows'
Sound Recording tab directly: rundll32.exe shell32.dll,Control_RunDLL
mmsys.cpl,,1 -- the classic dialog, not the modern unified one. No new
dependency, one process launch.

Two restart mechanisms, independent, either one shippable alone:
  - full daemon restart -- works today, unconditionally, pays the GPU
    model-reload cost. The baseline; nothing else has to exist for this to
    ship.
  - in-process PortAudio-only restart -- fast, model untouched. Needs the
    daemon to never exit on a mic fault, launch or PTT-time alike (audio.py's
    _exit_no_microphone currently sys.exit(1)s unconditionally -- that call
    goes away entirely, replaced by the shared on_mic_fault helper above)
    and needs config.json re-read per PTT cycle so a Settings Save can
    rebuild AudioCapture without restarting the process. EXPLICIT, not
    inferred: "rebuild AudioCapture" means portaudio_io.reinit() THEN
    re-resolve -- the daemon has its own, separate PortAudio state from the
    tray (different process), so it goes stale the same way the dropdown
    does if this step is skipped. Upgrades the baseline once built; no
    ordering requirement between the two.

audio.device is ALWAYS populated once first run completes -- never empty,
never dormant. The old "empty means System Default" meaning is gone.
