VOICE DICTATION - BUILD SHEET: CORPUS DATABASE (SQLite)

ON THE FLY
  WHY THIS SHAPE
  The FLAC corpus and the transcript log cannot be joined and never will be
  -- see spike-notes.txt. Every capture from here on records one row linking
  audio to text. Started now because ambient mode needs a corpus that already
  exists, and a corpus cannot be back-filled.

Done = every push-to-talk capture writes exactly one row, whatever the
outcome, and the row names the audio file it belongs to.

UNVERIFIED
==============================================================================
  [x] Is full-text search available without a dependency -- YES. SQLite
      3.49.1 in this venv, FTS5 compiled in, verified. Not built here: an
      FTS index can be derived from the base table at any time, so it is not
      urgent work.

  [x] Does the row write add perceptible latency -- NO, and not marginally.
      Measured outside the app, insert plus commit, 200 runs each:
        default (rollback journal, synchronous=FULL)   7.5 ms   worst 18.0
        WAL only                                       2.0 ms   worst  9.4
        WAL + synchronous=NORMAL                       0.021 ms worst  0.15
      The cost was always fsync, never the insert. At the shipped settings in
      1a it is twenty-one microseconds, against a 50 ms sleep already
      hardcoded in keyboard.inject, and it lands after the user has their
      text.
      EXPECT ONE OUTLIER IN ROUGHLY 900. Measured over 20,000 inserts:
      median 0.018 ms, p99 0.065 ms, worst 18.1 ms, with 0.11% above 5 ms.
      That is WAL checkpointing -- folding the -wal file back into the
      database -- and SQLite has no background thread, so it runs inside
      whichever commit crosses the threshold. At the measured capture rate
      that is one spike every day or so, still under the sleep already in
      the paste path. Do not treat it as a regression when it shows up in a
      profile. write_timestamped_flac already puts a 155 KB encoded write
      earlier on the same path. A press arriving mid-write is not lost
      either -- pynput sets the event from its own thread, so the loop finds
      it waiting.


==============================================================================
GOVERNING RULE
==============================================================================
Record observations, never derivations. Anything that can be computed from
the text later -- embeddings, summaries, word counts -- is left out on
purpose. Anything that exists only at the moment of capture is written down,
whether or not there is a use for it today.

RETENTION SPLITS THREE WAYS, because the three stores cost different things.
Rows are permanent: roughly 208,000 a year at the measured rate, which is
tens of megabytes, and every query runs off them alone. Audio is the
expensive one at roughly 34 GB a year and is the only thing worth rotating --
NOT BUILT HERE, deliberately. Deletion features are the ones that go wrong,
nobody has measured how much audio voice-ID actually needs, and you can
delete later but not undelete. When it is built it goes by age, not count:
daily volume swings from 120 to 956, and the date directories make dropping
a month one directory removal instead of a query. The transcript text file
self-maintains and needs no rotation feature at all -- see 1e.

ENTRY
  [x] The prior step's COMMIT exists. git log, not the boxes -- a box is a
      claim anyone can tick in any tool, a commit is a receipt carrying the
      gates that produced it and a message saying what landed. No commit
      means the work was never gated: review the code against the prior step

  [x] Every box in STEP 0 is [x]. The human record, read after the

  [x] 1a  userdata/dictation_history_PRIVATE.db, beside the recordings
          directory. stdlib sqlite3, no dependency. userdata never travels to
          a copy, so a personal corpus cannot leak onto a handed-out stick.
          THE NAME IS THE POINT. Anyone opening this folder learns what the
          file is and that it matters, without reading a line of code. The
          label is posture, not caution -- we know what we are storing, we
          are not hiding it, and we made it easy to find. Not "transcripts":
          transcript_log.txt sits nearby and the two coexist on purpose (1e),
          and a file called transcripts is how a later reader talks himself
          into deleting one of them.
          Named here so it is named once. WAL adds -wal and -shm files beside
          it, inheriting the same name; those are SQLite's, not ours, and
          nothing should ever open them directly.
          PRAGMA journal_mode=WAL and PRAGMA synchronous=NORMAL at connect.
          THEY DO NOT BEHAVE THE SAME WAY, verified: journal_mode is written
          into the database file and every later connection inherits it
          without asking. synchronous is per-connection and reverts to FULL
          on every reopen. Set it on EVERY connect or the 21 microseconds
          quietly becomes 2 ms and nothing reports it.
          Two reasons, and the concurrency one is the load-bearing half:
          WAL lets a reader work while the writer holds the file, which
          ambient mode and anything querying the corpus mid-dictation both
          need, and switching to it later is a migration rather than a line.
          NORMAL stops the commit waiting for the disk, taking the write from
          7.5 ms to 21 microseconds -- measured, see UNVERIFIED.
          THE TRADE, stated so nobody reverts it in a panic: the data leaves
          the process on commit and the OS owns it, so an APPLICATION crash
          loses nothing. A power cut or OS crash can cost the last few rows.
          For a dictation corpus that is not a loss worth 7.5 ms a row.
          It creates -wal and -shm files beside the database. Normal, not a
          leak, and the copy set must not ship them either way -- userdata
          never travels.
  [x] 1b  One table, captures. One row per capture. Columns, all
          observations:
            capture start and end time -- NOT the file-write time the FLAC
              filename already carries, which is later than both
            the FLAC's own timestamp, taken from the SAME value the filename
              was built from and never from a second datetime.now() call.
              write_timestamped_flac generates it internally today; have it
              hand the value back, or the row and the file it names disagree
              by microseconds and stop being reconcilable if the path column
              is ever lost
            audio file path, duration, sample rate
            model, compute device, compute type
            transcript text
            outcome: success, too-short, no-speech, error
            app version, so a row's era is readable after the code changes
            speaker -- empty until ambient mode fills it
            mode -- dictation or prompt. Prompt mode is coming and mixing
              "what I said to type" with "what I asked an AI" poisons both
              voice-ID data and any later analysis. The column costs nothing
              now and cannot be reconstructed afterwards.
            foreground window title and foreground process name, both from
              the same GetForegroundWindow call. WRITTEN FROM THE FIRST ROW,
              not reserved like speaker -- a column nothing populates is a
              column nobody trusts later.
              WHERE a thing was said is the strongest retrieval signal there
              is and the only one that exists solely at the moment of
              capture. Both, not one: the title is what a search matches, the
              process name is the only half that stays stable across a year,
              because the same app rewrites its title constantly.
              The full title, not a sanitised one. Titles leak, and that is
              accepted -- userdata never travels, capture requires a flag
              file that ships with nothing, and local-only is what makes this
              affordable when a cloud product could never take it.
              DECISION: Read the window at BUTTON PRESS. It is the only
              moment all four outcomes share.
              SAFEGUARD: GetForegroundWindow can return 0 (no focus,
              desktop, etc) or fail. The capture MUST wrap this in a
              try/except and gracefully log "Unknown" or empty text. It
              must NEVER throw and crash the dictation daemon.
  [x] 1c  Write AFTER injection, never before. The user is waiting on text;
          nothing goes in front of that.
  [x] 1d  RENAME userdata/flac to userdata/voice_recordings_PRIVATE, and give
          it date subfolders: voice_recordings_PRIVATE/YYYY/MM/DD/, three
          levels. Both halves here, in one pass over the same files.
          The rename first, because "flac" is a codec and this is 34 GB a
          year of someone's voice -- the folder that most needs to say what
          it holds was the one named after a file format. Same reasoning as
          1a's filename.
          One code site defines it, FLAC_CORPUS_DIR in vdict_daemon.py --
          derived by search, not recalled. write_timestamped_flac takes the
          directory as an argument and only chooses the extension, so it
          needs no change for the rename. Rename the constant with the
          directory.
          Measured rate is roughly 570 clips a day, which is about 208,000
          files and 34 GB a year -- Explorer and any recursive glob give up
          long before that. Three levels keeps one folder per year at the
          top and makes age-based rotation, when it is built, a single
          directory removal rather than a query.
          Move the existing flat files into the new layout in the same step.
          Nothing stores a path to them -- the database does not exist yet --
          so this is the last moment either change costs nothing. After rows
          carry paths, both become a data migration.
          ZERO-BYTE FLACS EXIST. One is in the corpus now, measured, so
          write_timestamped_flac can produce a file soundfile cannot reopen.
          DECISION: The writer MUST refuse an empty buffer. No zero-byte
          FLAC is written to disk, keeping the corpus clean.
  [x] 1e  transcript.py: swap RotatingFileHandler for TimedRotatingFileHandler,
          when="midnight", backupCount around 30. It currently rotates on
          SIZE at 100 MB, which is why pruning by time is impossible today.
          Rotating on time makes each day its own file, named with its own
          date, and the handler deletes past the backup count by itself --
          no pass to run, no parsing, ever.
          DO NOT timestamp the lines. The file boundary is the time boundary,
          and CATEGORIES["transcript"] already carries a deliberate decision
          that this text stays bare so it is copy-paste clean. A per-line
          timestamp costs exactly the thing the file exists for.
          This file and the database coexist ON PURPOSE and neither replaces
          the other: the database is for queries and for reaching the audio,
          the text file is for scrolling back twenty lines and copying. A
          later reader will see overlap and want to delete one. Do not.
  [x] 1f  Row writing follows capture_corpus, the flag STEP 0 landed. A copy

==============================================================================
ENTRY
  [ ] The prior step's COMMIT exists -- see the first ENTRY in this sheet.
  [ ] Every box in STEP 1 is [x]. The human record, read after the
      commit, never instead of it.

  [ ] 2a  Four ways a capture ends, and three of them leave the loop early:
          too short, transcription threw, no speech detected, success. A
          write placed beside the success case catches one in four.
  [ ] 2b  One write point every path reaches. The three failures are the data
          that matters most for tuning -- "the model produced nothing here"
          is a finding, and a corpus containing only successes is biased in
          exactly the direction that hides problems.
  [ ] 2c  A row with no transcript is still a row. Outcome carries the reason.
  [ ] 2d  Serialize the brackets (Paragraph Grouping). Add `block_id INTEGER` column
          to the database. Maintain an in-memory dictionary of `active_blocks` 
          mapped by the window's HWND (Handle). When PTT is pressed, grab the 
          active HWND. If it has no block_id, generate an Integer Epoch timestamp. 
          Dictations save with this block_id, while still capturing the literal 
          window title for ambient state tracking. When a global PURE, UNMODIFIED 
          `Enter` keypress is detected (ignoring Shift+Enter, etc), grab the active 
          HWND and wipe its block_id from the dictionary. 
          NOTE: This state machine is intrinsically self-healing. If a keystroke 
          is dropped by the OS, the worst-case scenario is two paragraphs share 
          one ID. The very next `Enter` keypress instantly hard-resets the state 
          to a clean baseline without needing a watchdog timer.
          TRADE-OFF ACCEPTED: If the user clicks "Send" with a mouse instead of
          pressing `Enter`, and never changes windows, the next dictation will 
          fuse into the same block_id. This loss of fidelity is accepted because
          the RAG system can natively split blocks with massive timestamp gaps.
          THE KEYBOARD LISTENER DOES NOT EXIST YET. PTTListener builds either a
          mouse.Listener or a keyboard.Listener, never both, and the default PTT
          is a mouse button. This adds a second, always-on one -- and it tracks
          modifier press/release itself, because pynput's Enter event does not
          carry modifier state. B5's "what this records" section names it.
          BLOCK_ID NEEDS SUB-SECOND RESOLUTION. Epoch seconds collide when two
          windows open a block in the same second. It only has to be unique.
          WINDOWS RECYCLES HWNDS. Entries only leave active_blocks on Enter, so
          a closed window's handle can be reassigned and inherit its block.
  [ ] 2f  WRONG NOW, both writing bad data on every capture. Fix before the
          other items here -- rows are the permanent half of this system and
          neither column can be reconstructed afterwards.
            compute_type is the string literal "float16", passed straight
              into the insert. It reads correctly only on CUDA. On CPU
              stt.py loads float32 while the row keeps claiming float16.
              The cause is that stt.py computes compute_type as a local in
              both load() and reload() and stores it nowhere, so the daemon
              has nothing to read. Fix: STTEngine remembers what it loaded.
            start_time is taken at button press, two calls before
              start_capture(), with a wait_for_release() between them in
              toggle mode. end_time is datetime.now() at row-write, after
              transcription and injection -- measured 1.2 to 2.1 seconds
              past the audio. 1b defines both as capture start and end.
              Fix: bracket stop_capture and start_capture.
  [ ] 2g  A FIFTH exit path, not in 2a's four. Toggle mode's 120-second
          timeout calls stop_capture() and continues -- no FLAC, no row,
          nothing. Decide whether it earns a row. A capture abandoned by
          walking away is a different fact from one the model failed on.
  [ ] 2e  Two ruff findings on STEP 1's code were AUTHORIZED PAST at the STEP 1
          commit, not suppressed -- no noqa was added, so both fire again on
          every commit until they are fixed here.
            _record_corpus_row  PLR0913 / PLR0917, 14 arguments against a
              limit of 5. The row is one record, not fourteen loose values.
            main  C901 complexity 13 against 10, PLR0912 14 branches
              against 12.
          They land here rather than at STEP 1 because 2a through 2d add

          Fixing them first means doing it twice.
          NOT a reshape-to-pass: both numbers are describing the same thing

          extracted and the row wants a type. If the fix does not also make
          the code read better, it is the wrong fix and the number stays.
